# Стандарт написания инструкций, знаний и решений

**Режим:** proposed. Этот стандарт не делает старый текст действующим договором автоматически.

## Одно правило — одна причинная цепочка

Используй такой шаблон только для сложных, предметных правил; для простых команд достаточно одной строки.

```markdown
### RULE-SOURCE-001 — не подменять отсутствие источника нулём
Scope: чтение первичных Sheets и расчёт
Status: accepted-in-docs; runtime-state: unverified
Trigger: источник не прочитан, формула дала ошибку, отсутствует сопоставимая неделя
MUST: показать статус источника и asOf; не вычислять ноль из недоступности.
MUST NOT: публиковать новую сверку как PASS по старому cached-success.
Verify: тест отсутствия одной книги + перезапуск после failed check + readback.
Sources: `docs/decisions/0012-...md:L20-L23`, `docs/decisions/0002-...md`
```

Для каждого нового положения записывай **вид**: `owner_requirement`, `business_invariant`, `implementation_observation`, `research_option`, `historical_incident`, `operational_status`, `external_guideline`.

## Как переводить исторические фрагменты

1. Найди полный контекст, дату, source path, строки и источник исходного утверждения.
2. Раздели одно предложение на атомарные тезисы; не соединяй критерий, наблюдение и план в одну «истину».
3. Сравни тезис с последним принятым решением, кодом и при необходимости свежим источником. Новый по дате документ не обязательно авторитетнее принятого ADR.
4. Выбери судьбу: `KEEP` / `MERGE` / `SUPERSEDE` / `ARCHIVE` / `REJECT` / `OPEN`.
5. Для `KEEP` и `MERGE` напиши конкретное действие, когда оно нужно, и как проверить. Исторические цифры не переносить без asOf.
6. Вынеси доказательство в ссылку; держи обязательное правило коротким. Никаких многокилобайтных примеров в root `AGENTS.md`.
7. Противоречие не скрывай редактурой: присвой ID и оставь открытым до арбитража.

## Примеры исправления содержания

**Плохо:** «Перед любым изменением прочитай все документы, проверь всё, будь профессиональным».  
**Лучше:** «При изменении метрики открой `METRICS_AND_MONEY.md`, запусти относящийся к ней unit test и проверь знак, единицы и границы выборки».

**Плохо:** «PR #93 не работает, не трогай код никогда».  
**Лучше:** «Выпуск Word требует два последовательных успешных цикла worker на утверждённом volume; статус текущего VPS проверять по `release_id`, журналу и readback».

**Плохо:** «Считать экономию по плану и факту».  
**Лучше:** «Считать утверждённую экономию по Z+AA+AB только при `Q` факт и `AD=да`; для отклонения показывать отдельно `факт − план`».

**Плохо:** «Этот PR починил весь интерфейс».  
**Лучше:** «На SHA X пройдены тесты Y, но проверка original HTML, обеих тем и доступности production не выполнялась».

## Как содержать, обновлять и выводить память из обращения

1. **Единый дом для одного правила.** `AGENTS.md` хранит только всегда применимые границы и маршруты. Предметный контракт — единственная нормативная формулировка детали. `CLAUDE.md` и Copilot содержат короткие адаптеры; исторические планы/сырой разговор не конкурируют с контрактом.
2. **Разделяй сроки жизни.** Долгоживущие инварианты (схема, идентичность, запрет потери) сохраняй в Git. Моменты (`PR открытый`, `CI красный`, `на сервере N строк`) — в `STATUS`/журнале со ссылкой, `asOf`, exact SHA и событием, после которого статус требуется проверить вновь. Эфемерный результат сессии не превращай в вечный приказ агенту.
3. **Сначала свидетельство, затем правило.** Источник правила — воспроизводимый дефект, явное решение владельца, код/тест на закреплённом SHA или актуальное нормативное требование. Степень уверенности: `observed`, `proposed`, `accepted`, `implemented`, `tested`, `deployed`, `prod-verified`, `owner-accepted`; переходы подтверждаются отдельно.
4. **Триггеры ревизии.** Меняется A:AH, источник, формула, ID-правило, сборщик Word, маршрут интерфейса, механизм webhook, release/worker или deploy policy — перечитай **только затронутый контракт**, обнови `Sources` и негативный тест в том же PR. После инцидента занеси причину, защиту и диспозицию. Периодическая выборочная ревизия полезна, но календарная дата сама по себе не делает недостоверный тезис истинным.
5. **Удаление — штатная операция.** При снятии правила укажи `superseded_by`, дату, commit и причину; архив остаётся доступным, но не загружается агентом автоматически. Дубли в активных файлах устраняй, а не синхронизируй вручную несколько одинаковых копий.
6. **Приватность и качество.** Локальная auto-memory агента, пути рабочей станции, идентификаторы доступов и сырые записи должны проходить приватный просмотр до любого публичного Git. В инструкции сохраняй способ найти факт, а не сам секрет/большой лог. Проверяй, что агенту разрешён минимум нужного доступа.
7. **Контроль пользы.** Каждое правило должно предотвращать конкретный класс ошибок или ускорять правильный маршрут. Если оно не меняет проверяемое действие, не имеет триггера и дублирует общее пожелание — не добавляй. Измеряй цену чтения, число повторных ошибок и применимость в Codex/Claude/Copilot, а не количество Markdown и токенов.

## Запреты для резюмирования

- Не выводи правовую оценку 44-ФЗ из исторического текста без проверки редакции нормы и основания.
- Не переносить приватные book ID, ключи, имена пользователей, служебные ссылки и персональные данные в универсальные подсказки.
- Не соединять исторически несовместимые источники «по большинству голосов». Сравнивать perimetr, дату, атомы и режим расчёта.
- Не заявлять полную смысловую ревизию только по автоматическим заголовкам или embeddings; отмечать machine-extract отдельно от human/LLM-reviewed.
