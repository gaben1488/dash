# Как вести хронологическую память DASH

**Статус:** предлагаемая методика 23.10.2026. Проверенный источник: 250 архивных MD, 73 поздние редакции на указанном SHA; семантическая вычитка продолжается.

## Обязательная вычитка самим агентом — не машинная классификация

**Прямое уточнение владельца 23.10:** агент читает **полный текст каждого MD**, а затем **каждую датированную запись внутри него**, восстанавливая последовательность событий. Он самостоятельно устанавливает смысл, сопоставляет несовместимые ранние и поздние утверждения и формулирует причину оставления/отмены. Поиск дат, semantic search, CSV-разметка и хэш-проверка — навигация и техническая целостность, а не интеллектуальная вычитка.

Пофайловое `AGENT_FULL_READ` ставится только по конкретной записи с `reviewer`, `asOf`, `path@blob`, подтверждением прочтения всех разделов и собственным разбором внутренних поправок. Следующий статус `AGENT_ADJUDICATED` подтверждается решениями по тезисам и сопоставленными поздними доказательствами; `CURRENT_VERIFIED` и `OWNER_ACCEPTED` — другие, независимые гейты. Дата в имени, отчёте или примере **не заменяет дату события**.

Первый публичный разбор **8 файлов / 18 тезисов**: [AGENT_REVIEW_WAVE_01_2026-10-23.md](AGENT_REVIEW_WAVE_01_2026-10-23.md). Пример, почему нужны оба порядка: старый текст Mulch с внутренней датой 19.04 находится в backup каталоге 04.06; исторический проект Time Machine от 05.06 получил поздние уточнения 13.10 **в начале того же документа**. Исходные оригиналы не удалены. До отдельной агентной проверки **остальные 252 из 260 MD не считаются прочитанными**.

Не создавать ещё одну конкурирующую систему `AGENTS.md` или памяти. Дистиллированное правило уходит в один уже существующий тематический контракт, когда агент может показать источник, границу действия, отменённый вариант и проверку. Всё не подтверждённое остаётся `OPEN/HISTORICAL` без машинного `accepted`.

## Два разных порядка

**Версии документа:** Git commit time (проверенный SHA) → конкретный текст версии, с `supersedes` и статусом. Дата из имени файла — лишь дата документа/протокола, не дата его последней редакции. Поздняя вставка 23 октября в документ «08 августа» относится к 23 октября.

**События внутри файла:** явная отметка даты/времени самого решения → относительный порядок строк в одном протоколе → `time_unknown`, если метки не было. Дата контракта/платежа или тестовая строка с `15.03.2023` — **не** дата решения. Нельзя трактовать номера пунктов `1.10`/`10.11` как даты. Для пересечения нескольких документов без достоверного timestamp сохраняй `order_unresolved`, не выдумывай время.

## Обязательная карточка атомарного вывода

`id, topic, valid_from, recorded_at, source_commit, source_path, start_line, end_line, original_claim, actor, scope, observation_type, implementation_status, evidence_level, supersedes, superseded_by, conflicts_with, decision, open_questions, last_verified_at, verification_method`.

Типы: `owner_requirement`, `decision`, `bug`, `observation`, `proposal`, `test_result`, `release_receipt`; явно различать «сказано» и «реализовано». Не объединять разные сущности только по сходству названий. `valid_from` только при доказанном вступлении, иначе `unknown`.

## Разбор конфликтов

1. Отобразить обе формулировки и даты, ссылки до строки, область действия.
2. Проверить, действительно ли позднее утверждение **заменяет** раннее, либо касается другого периметра/периода. Поздний timestamp сам по себе недостаточен — различаются предложения, решения и сообщения об успехе.
3. Сверить реализацию с Git/контрактом/тестом и отдельно с source readback/live. Код не устанавливает право менять исходные данные; договорённость не доказывает рабочий код.
4. Классификация: `ACCEPTED`, `CONDITIONALLY_ACCEPTED`, `HISTORICAL`, `SUPERSEDED`, `REJECTED`, `UNRESOLVED`, `NEEDS_LIVE_PROOF`.
5. В короткий агентный файл выпускать лишь принятый инвариант и точный тест. Не выписывать старую полемику; оставлять ссылку на ledger. Замена — атомарно: правка канона → обновление трассировки → тест против старого кейса → review.

## Актуализация без бесконечной переплавки

Триггеры: merge в main, изменение схемы/формулы/контроля входов, новое решение владельца, подтверждённый инцидент, изменение production-релиза, рассогласование docs ↔ код. При каждом триггере проверять **дельту**, а не повторно сокращать весь архив. Для неизменённого SHA не проводить повторную семантическую обработку без новой причины.

Правило сохранности: оригиналы immutable; удаление канона допустимо только как отдельный согласованный рефакторинг после readback. Для исторического документа — статус `HISTORICAL`, навигационная ссылка и единственный действующий дом, не параллельные документы «главный канон».

## Минимальная проверка новой инструкции

- Точно указывает существующие файлы/команды на pinned SHA; неизвестное помечено.
- Не создаёт конфликт с `AGENTS.md`, `docs/AGENTS.md`, `CLAUDE.md` и `docs/PLAN.md`.
- Содержит проверяемое действие, триггер и запрет риска; нет слов «всегда» для редких операций.
- Проходит тест на старый баг (неполный снимок, устаревший статус, выбор источника, деньги, фильтр, перенос UUID).
- Указаны `asOf`, владелец правила/область, ссылка на подтверждение, `superseded_by` для отмен.

## Предохранитель публичности

Полный архив первичной переписки, комментарии о должностных лицах, технические адреса, внутренние URL и сырые реестры остаются в закрытом Google Drive. В публичный репозиторий — только безопасный результат и ссылки на уже публичные документы, если их содержимое допустимо.
