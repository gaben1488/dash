## §0. Канон-вводные пользователя (рамка ревью)

1. **Отчёты еженедельные, срез — четверг.** Так организовано сейчас: отчёт делается раз в неделю, отчётная дата (срез данных) — четверг недели.
2. **Единая система периодичности.** «Еженедельность охватывается тем же колесом-фильтром недельных бэкапов. Это всё ОДНА система»: WeekRoller (колесо недель в фильтре, periodMode 'week', focusedWeekStart в store.ts), недельные слепки/бэкапы данных и отчёт-на-четверг — не три механизма, а один. Выбор недели в колесе → отчёт на четверг этой недели; история отчётов = серия недельных срезов. Парадигму не ломать, вторую параллельную систему не строить.

## §1. Карта семейства отчётов

### 1.1 Состав семейства (три жанра + генераторное прошлое)

**A. Основной еженедельный нарратив («Отчёт по закупкам»)** — флагман. Структура стабильна от 20.03 до 26.06 (сверено по трём срезам серии):

1. Шапка: «ОТЧЕТ ПО ЗАКУПКАМ» + «срез на ДД.ММ.ГГГГ»; с мая — **ссылка на СВОД онлайн** с оговоркой «показатели в отчете и в своде могут незначительно отличаться в виду актуальности свода на дату открытия, а отчета на отчетную дату» (260329…26.06.docx, шапка).
2. Блок «ВСЕ ГРБС / ПО КОНКУРЕНТНЫМ ПРОЦЕДУРАМ»: план на год (кол-во + сумма + ФБ/КБ/МБ); планы **всех четырёх кварталов** (в серии; в 260315 — год + Q1); фактически заключено **с оговорками-нарративом** («не включая 8 аукционов УИО, 7 из которых на стадии заключения, 1 — не состоялся» — 260315); исполнение по кварталам с отклонением; **ранжированный список ГРБС по исполнению квартала** (от худшего к лучшему: «УФБП — 0,00% (G132)… УДТХ — 90,00% (G195)»); остаток незаключённых до конца года (F14); «в работе у отдела муниципальных закупок N процедур» с разбивкой **по стадиям** (подготовка извещения / итоговый протокол / подача заявок; в серии — ещё и по ГРБС); **расчётная (прогнозная) экономия по оставшимся незаключённым** с трёхсрезом бюджета.
3. Блок «ВСЕ ГРБС / ЕДИНСТВЕННЫЙ ПОСТАВЩИК»: план год/кварталы; заключено; **распределение доли ЕП по ГРБС с причинами в процентах** («УФБП 100% (G154)… 28% услуги монополистов, 6% обучение, 66% техника…»); счётчик адресных рекомендаций (46 в 260315 → 144 к 26.06) с числом принятых; выводы («низкая заинтересованность контрактных управляющих…»).
4. **8 секций ГРБС** (порядок: УЭР, УИО, УАГЗО, УФБП, УД, УДТХ, УКСиМП, УО), каждая = КП + ЕП: год / план квартала (сумма + ФБ/КБ/МБ) / проведено / **двойное исполнение** (% квартала И % года) / **экономия МБ** жирным (U46, U57, U167…) / **поимённый перечень** «осталось отыграть/заключить» (предмет + сумма + причина/стадия) / «планирует подать N заявок» со стадией («заявка передана в уполномоченный орган») / **рекомендации по позициям** со статусом «Позиция принята / не принята / частично» + обоснование ГРБСа / кейсы совместных закупок (УО: бумага для 35 подведов, НМЦК −24,68%).

**Маппинг текст→ячейка СВОД (только в 260315).** Каждое число эталона несёт адрес ячейки листа СВОД ТД-ПМ: план-кол-во D, факт E, отклонение F, исполнение G, план-деньги H/I/J/K (ФБ/КБ/МБ/итого), факт-деньги L/M/N/O, экономия R/S/T/U. Эта сетка **совпадает колонка-в-колонку** с SVOD_GRID_COLS парсера (packages/shared/src/svod-grid.ts:29-48: planCount=D … economyTotal=U) — parseSvodGrid уже читает структурно всё, на что ссылается эталон, включая startRow блока для трассировки (svod-grid.ts:72-73) и двухлетние итоги «Итого 2025+2026» (svod-grid.ts:74-76).

**B. Допотчёт («Дополнительно к отчёту», 12.07)** — другой жанр: сжатая записка руководителю («Для АВ дополнительно… буду краток, исключительно по основным показателям и проблематике»). ### 1.2 Периодичность и потребители

- **Ритм — еженедельный**, серия непрерывна: 08.05 → 15.05 → 22.05 → 29.05 → 05.06 → 11.06 → 19.06 → 26.06 (папки `Documents\Отчеты по закупкам\`). Канон пользователя (§0.1): срез — четверг. Наблюдение по файлам: даты срезов серии в основном приходятся на пятницу (08.05, 15.05, 22.05, 29.05, 05.06, 19.06, 26.06.2026 — пятницы), 11.06.2026 — четверг; организация среза менялась, текущий канон — четверг. Рассинхрон в планах: EXECUTION_PLAN 6.6 предлагает «**пятничный** авто-снапшот» — расходится с каноном, приводить к четвергу (см. §3, §4.3). Серверный дефолт /api/report уже четверговый (routes/report.ts:59-66).
- **Потребители:** основной отчёт — совещание у руководства («итоговый для АС к совещанию 26.03.2026» в `ПЛАН-РЕЕСТР-*\ОТЧЕТЫ\`) и сами ГРБС (прямые обращения: «Просим коллег перенимать опыт…», 260315, блок ЕП). Допотчёт — персонально руководителю («Для АВ», «С вашего разрешения, Андрей Сергеевич, под протокол совещания…», 260712). Процедурный — начальству от контрактных управляющих (REPORT_STRUCTURE §6). Спека продукта называет тех же пользователей: УЭР/ЦЭР, ГРБС-вьюер, начальство (2026-07-13 §3).
- **Связь с данными:** серия делается из план-реестра; в каждой датированной папке рядом с docx лежат xlsx-выгрузки той же недели (спека §14). Ручная практика УЖЕ живёт парами «недельный слепок данных ↔ отчёт этой недели» — прямое подтверждение вводной §0.2: серия отчётов и серия слепков — одна система.

## §3. Единая система периодичности: колесо недель ↔ слепки ↔ отчёт-четверг

### 3.1 Что есть сейчас (факты по коду)

1. **Колесо недель есть, но неделя теряется на полпути.** WeekRoller (components/Header.tsx:309-352) крутит focusedWeekStart (понедельник недели, store.ts:254-257, 669-683); в режиме periodMode='week' неделя **деградирует в месяцы**: данные фильтруются по getMonthsForWeek (store.ts:39-42, 86, 682-683). До данных доезжает месяц, не неделя.
2. **FilterContext оси недели не имеет.** Контракт фильтров: year / period (кварталы) / months / grbs / subordinates / activities / methods / budgets / search (lib/filter-context.ts:46-65); в URL-схеме недели тоже нет (:179-191). Комментарий в самом файле обещает discriminated union PeriodSel «при смерти legacy-полей» (:10-13) — место для недели уже зарезервировано архитектурно.
3. **Сервер уже знает канон четверга, страница — нет.** GET /api/report без asOf берёт ПОСЛЕДНИЙ ЧЕТВЕРГ: floorToThursday(d)=d−(d%7), день 0 эпохи — четверг (routes/report.ts:59-66, 82); METHODOLOGY проговаривает канон читателю (:35-42). Но страница «Отчёт» asOf не передаёт вовсе (api.ts:222-226; Report.tsx:174) и печатает в заголовке сегодняшнюю дату клиента (Report.tsx:181, 209) — т.е. четверг сервера и «сегодня» страницы расходятся молча.
4. **asOf сейчас — этикетка, не срез.** buildReport кладёт asOfDay только в period-метаданные (build-report.ts:221); quarterExecution даты не принимает (quarter-execution.ts:34-43) — факт = «есть дата в столбце Q» на момент чтения живого кэша (routes/report.ts:110-118, collectRowsByDept → getDeptSheetValues, snapshot.ts:49-55). Запрос отчёта «на прошлый четверг» вернёт сегодняшние данные с прошлой датой на обложке. Настоящий срез прошлой недели возможен только из слепка той недели.
5. **Слепки есть, но не недельные и без строк.** Снапшот пишется в БД при каждом refresh (snapshot.ts, saveSnapshot: полный JSON в snapshots.data); таймлайн жив: GET /api/history/snapshots (routes/history.ts:11), дрейф метрик между снимками жив: GET /api/history/diff (routes/history.ts:16-27). Но DataSnapshot не содержит строк-атомов (shared/src/types.ts:424-452) → buildReport над историческим снапшотом невозможен; и ритм снапшотов — «когда обновили», а не «каждый четверг» (EXECUTION_PLAN 6.6 планирует cron, но пятничный).
6. **changeWindow мёртв, а его идея — недельная.** store.ts:186, 336-337 + единственный потребитель store.test.ts:103-115; спека §13 прямо говорит: идея «изменения с даты» возрождается в шапке Отчёта как «что изменилось за неделю» — дельта к прошлому снапшоту.

### 3.2 Целевая модель — ОДНА ось, пять представлений (без второй системы)

Инвариант: **неделя(колесо) → её четверг(asOf) → слепок(≤ четверга) → buildReport(слепок) → дельта к слепку прошлой недели.** Всё существующее переиспользуется, ничего параллельного не строится.

1. **Неделя — первичная ось периода; её каноническая точка — четверг.** focusedWeekStart уже хранит понедельник; четверг недели = понедельник + 3 дня. Неделя доносится до FilterContext одним полем (week в составе будущего PeriodSel, который контракт уже анонсирует: filter-context.ts:10-13) и в URL (например `w=2026-07-20`). Кварталы/год НЕ дублируются — сервер уже выводит их из даты среза (routes/report.ts:82-107): отчёт на четверг говорит о квартале этого четверга, ровно как эталон.
2. **Отчёт слушает колесо.** Report.tsx передаёт asOf = четверг выбранной недели (параметр роута существует и валидируется: routes/report.ts:72-80); заголовок печатает дату среза из ответа (report.period.asOfDay), а не new Date() (чинит Report.tsx:181, 209). Прокрутка колеса назад = запрос отчёта прошлой недели.
3. **Слепок недели = снапшот четверга.** Weekly-cron из EXECUTION_PLAN 6.6 с исправлением дня (пятница → четверг, канон §0.1). Снапшот расширяется строками-атомами (rowsByDept в data-JSON или отдельная таблица) — тогда «отчёт за прошлую неделю» = buildReport над слепком той недели, буквально как обещает спека §4.1 («проекция над историческим снапшотом»). Правило чтения: текущая неделя — живой кэш; прошлая — последний снапшот с createdAt ≤ её четверга; слепка нет → честная плашка в notes (механизм готов: build-report.ts:161, 215-218).
4. **История отчётов = таймлайн слепков.** /api/history/snapshots (history.ts:11) уже отдаёт серию; страница «Отчёт» не заводит отдельного «архива» — история листается тем же колесом. Ручные xlsx-пары прошлых недель (папки `Отчеты по закупкам\<дата>`) импортируются как backfill-слепки — серия срезов дотягивается назад до 08.05 и одновременно даёт материал реверс-инжиниринга (спека §14).
5. **«Что изменилось за неделю» = дельта слепков.** Шапка Отчёта показывает diff(слепок N−1 → слепок N) через уже живой /api/history/diff (history.ts:16-27); детекты допотчёта строятся на этом же ряду: сдвиг план-квартала строки между слепками = Δ4, появление строки «под факт» в окне между слепками = Δ5 (delta-спека §6). Мёртвый стор changeWindow удаляется (спека §21) — его заменяет серверная дельта, параметризованная той же неделей.

Так закрывается вводная §0.2 без новой сущности: колесо недель, недельные слепки и отчёт-на-четверг становятся тремя видами одной оси, а не тремя механизмами. Единственное изменение данных — слепок обязан нести строки-атомы; единственное изменение UI-контракта — неделя как поле FilterContext вместо немой деградации в месяцы.
