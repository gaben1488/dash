## §2. Находки по точности (по убыванию серьёзности)

### 2.1 КРИТИЧНО. Двухисточниковость строк: rows-страница и дашборд живут в разных вселенных (D1)

Живые числа (2026-07-16, УЭР):

- деп-книга УЭР: **38 строк** (`readDeptSheet` — проба); зеркало «УЭР» в СВОД-книге: **996 строк** (`getSheetData('УЭР')` — та же проба);
- `/api/rows/uer?limit=1000`: **35 строк данных, план Σ 9 953.37, факт Σ 5 182.056** тыс. руб.;
- `/api/dashboard` (year=2026), сводка УЭР: **planTotal 18 384.17, factTotal 12 639.11**; подведы: `_org_itself` 35 строк (factTotal **5 182.0564** — ровно сумма rows API) + **МКУ "ЦЭР" 51 строка (план 9 083.83)**, существующая ТОЛЬКО в зеркале.

Механизм: `createSnapshot` читает строки ГРБС из СВОД-книги (snapshot.ts:186 `getSheetData(sheetName)` корневого модуля = зеркала), деп-кэш — только фолбэк на пустоту (snapshot.ts:214-218). А `/api/rows` наоборот: деп-кэш → зеркало → деп-книга (rows.ts:79-105). Итог: пользователь на дашборде видит 18.4 млн плана УЭР, открывает «строки» — видит 9.9 млн и 35 строк; 51 строка МКУ ЦЭР недоступна построчно вообще.

Хуже: до первого POST /api/refresh деп-кэш пуст, и rows API отдаёт ЗЕРКАЛО (996 строк); после refresh — книгу (38). Одна и та же страница меняет вселенную в зависимости от состояния кэша (rows.ts:79-88).

### 2.2 КРИТИЧНО. Даты доезжают до web сырыми серийниками, и web их ломает

- rows DTO: `planDate: cells.N ?? ''` (rows.ts:153), `factDate` (rows.ts:155) — в API уходит `46034`;
- TableEditor.formatDate (TableEditor.tsx:64-75): `new Date('46034')` → год 46034 → в таблице «01.01.46034»;
- DataBrowser квартальный и месячный фильтры (DataBrowser.tsx:335-348): `new Date(46034)` = 46034 мс от эпохи = **01.01.1970** → месяц каждой serial-строки = «январь» → фильтр по кварталам/месяцам классифицирует ложно.

Канон `parseSheetDate` (shared/parse-sheet-date.ts) существует и подключён в core (signals.ts:181, seasonal.ts:35), но НЕ на границе API и НЕ в web.

### 2.3 СРЕДНЕ. Деньги: binary-float сквозной, шум виден в экспорте

Тыс. руб. с копейками живут как double. Шум приходит УЖЕ из Google (сырая ячейка экономии = `0.4400000000000013` — проба, зеркало УЭР r9) и не гасится нигде: API отдаёт `economy: 146.76999999999998` (живой ответ /api/rows/uer, r7), CSV-экспорт пишет как есть (DataBrowser.tsx:391 `r.economy ?? ''`). Суммы CalcEngine накапливают шум (`planTotal: 18384.168159999997` в живом дашборде). Экранное отображение округляет (formatCurrency), поэтому потеря точности косметическая (<копейки), но: (а) экспортные файлы идут начальству с 17 знаками; (б) сравнения на равенство между слоями требуют epsilon. Побочно: rule-book допуск «1 руб.» фактически равен 1.0 в единицах листа = **1 тыс. руб.** (rule-book.ts:47,53) — маскирует ошибки до 999 руб.

### 2.4 СРЕДНЕ. Столбец U (статус) теряется, подменяясь производным

DTO не содержит сырого U; `status` = STATUS_MAP[classifyRowState(signals)] (rows.ts:120-125,169). Живая сверка §3: U в листе = «Отклонение фактической даты подписания…» — этот текст исполнителя никуда не доезжает. Производный статус — правильная фича, но потеря исходного поля — потеря информации ГРБС.

### 2.5 КРИТИЧНО (для целевой роли БД). Жизненный цикл замечаний фактически не персистится

- issue.id = `nanoid()` на каждый прогон пайплайна (orchestrator.ts:473,606; validate.ts:52,104);
- статус меняется UPDATE-ом по id в таблице issues (issues.ts:203-224), overlay читает по id (issues.ts:37-46);
- через ≤300 с (TTL) или любой refresh снапшот пересобирается → ВСЕ id новые → выставленные статусы орфанятся.

Живая БД: **52 048 issue-строк, 52 снапшота (за 2 дня), 0 строк со статусом ≠ open, issue_history пуст** (запрос better-sqlite3 к data/aemr.db). Плюс рассинхрон бакетов: /api/issues берёт getSnapshot() без года (issues.ts:66) — это кэш-бакет «0», а дашборд — бакет года; одно и то же замечание одновременно имеет разные id в двух бакетах.

### 2.6 СРЕДНЕ. Запись ячейки не инвалидирует снапшоты и портит согласованность кэша

PUT /api/rows/:dept/:idx/field после writeCellValue мутирует кэш деп-книги in-place (rows.ts:483-490), но `cachedSnapshots` НЕ инвалидируется → дашборд до 300 с отдаёт числа до правки, rows — после (два ответа противоречат друг другу в одну секунду). Вдобавок формульные колонки (K=H+I+J, Y, Z-AC) в кэше остаются старыми: Google пересчитает их только в облаке, а кэш узнает при следующем полном refresh — строка в кэше внутренне противоречива (H новое, K старое).

### 2.7 НИЗКО, но системно

- **Молчаливый demo-фолбэк**: любой сбой createSnapshot → демо-данные (snapshot.ts:243-247); id получает префикс `demo-`, но /api/dashboard не сигналит явно — риск принять демо за реальность.
- **Обрезка на AF**: buildCellDict A..AF (column-map.ts:83-97); всё, что появится в AG+ (комментарий schema.ts procurement_rows подразумевал A..AG), молча теряется.
- **Эвристика процентов**: normalize.ts:69-78 — «>2 значит уже проценты, делим на 100»; хрупко для легитимных коэффициентов >2.
- **planYear=0 виден во всех годах** (rows.ts:257-259) — осознанное решение, но в сумме с 2.1 даёт расхождение rows-Σ и календарного среза.
- **Нет NFC-нормализации кириллицы** (grep `.normalize(` по packages — 0 совпадений вне node_modules): совпадение имён подведов/предметов зависит от бинарного равенства; trim/lowercase-каноны есть (org-itself.ts:27-36), составные формы Unicode — нет.
- **Метод-фильтр rows**: строка с легитимным алиасом длиннее 5 символов («ЭА (МЭП)» из METHOD_ALIAS_MAP, method-families.ts:138) отбрасывается как «заголовок» (rows.ts:187) и не матчится exact-фильтром КП/ЕП (rows.ts:205-211), хотя канон classifyMethodGroup это умеет (calc-engine.ts:206).

## §5. Целевая роль БД и топ-5 правок «API/процесс/БД»

### Целевая роль SQLite (то, чего in-memory снапшот дать не может)

1. **История** — тренды метрик по годам и неделям: требует `target_year` в snapshots/metric_history (сейчас смешение годовых срезов, snapshot.ts:310-323).
2. **Реакции ГРБС** — жизненный цикл замечаний (статусы/комментарии/сроки): требует детерминированных issue-id, переживающих пересборку.
3. **Помесячные снимки официала** — лист «СВОД с месяцами» существует только для года AO4 (snapshot.ts:88-96): при переключении AO4 в источнике прошлый год ИСЧЕЗАЕТ физически. Единственное место, где он может выжить, — наша БД.

### Топ-5 правок по ценности (точные, исполнимые)

1. **Стабильные id замечаний + persist статусов.** Заменить `nanoid()` (orchestrator.ts:473,606; validate.ts:52,104) на детерминированный хеш (`checkId|deptId|rowIndex|cell|metricKey`); overlay (issues.ts:37) начнёт находить статусы после пересборки. Разом оживают 52 048 мёртвых строк issues, issue_history и весь workflow реакции ГРБС. Заодно перевести /api/issues на тот же год-бакет, что и дашборд (issues.ts:66).
2. **Один источник строк (закрытие D1).** В `createSnapshot` строки ГРБС брать из деп-кэша/readDeptSheet первично, зеркала СВОД-книги не читать (snapshot.ts:186,214); в rows.ts убрать зеркальную ступень фолбэка (rows.ts:85 и клоны). Дашборд и rows-страница впервые начнут сходиться (сейчас УЭР: 18 384 vs 9 953 тыс. руб. плана); строки подведов (МКУ ЦЭР, 51 строка) либо появятся из деп-книги, либо честно объявятся отсутствующими в источнике.
3. **Дата-канон до края.** В rows DTO конвертировать N/Q через parseSheetDate → ISO (`rows.ts:153,155`), web-парсеры удалить (TableEditor.tsx:64, DataBrowser.tsx:335-348). Чинит отображение «01.01.46034» и ложную классификацию кварталов/месяцев в фильтрах.
4. **Год в БД + дисциплина записи снапшотов.** Колонка `target_year` в snapshots/metric_history; `getMetricTrend` фильтрует по году; `saveSnapshot` вызывать по явному refresh/расписанию, а не на каждый TTL-промах (сейчас 52 дампа × 3.7 МБ за 2 дня); удалить мёртвые procurement_rows/input_errors из schema или начать их писать.
5. **Архивирование помесячного официала.** При каждом успешном чтении «СВОД с месяцами» писать в новую таблицу `monthly_official (year=AO4, month, dept, метрики, loaded_at)` с upsert по (year, month, dept). Это единственная защита от «сменили AO4 — 2025-й исчез»; сверка за прошлый год станет возможной из БД, а не «официала не существует».

Бонус-правка вне топа (дёшево): в PUT field инвалидировать `cachedSnapshots` (rows.ts:490 → вызвать invalidateCache()), пока не сделан пункт 2 — убирает 300-секундное противоречие дашборда и rows после правки ячейки.
