### D8 · Периодное исполнение по количеству вырождено (методологический дефект)
Во ВСЕХ кварталах у ВСЕХ 8 ГРБС `factCount == planCount` → execCountPct = 100%
(Q1: УЭР 14/14, УО 54/54 КП и 844/844 ЕП…). Причина: факт-количество квартала считается по
факт-кварталу строки, план — по план-кварталу; исполнение «из запланированного на Q1 исполнено
N» не считается вовсе. Рейтинг в срезах Q1/март бесполезен (все 100%). Эталонный отчёт считает
«исполнение Q1 = 64%» по другому определению — реализовать его.

## Код-механизмы дефектов (прочитано по коду 2026-07-13)

- **D9 разгадан**: колонка подписана «Δ НЕД.» (tooltip `dept_delta_week`), но
  `Dashboard.tsx:153` кладёт туда `dm.delta.execPctChange`, а `useMultiDimMetrics.ts:256-260`
  считает delta как «current **quarter** vs previous». −50…−81% — это честная дельта Q3-к-Q2
  (Q3 только начался), подпись врёт: не неделя, а квартал.
- **D10 подтверждён кодом**: `useFilteredData.ts:833-834` — `signalCounts` берутся напрямую из
  `dashboardData.signalCounts` с комментарием «from API (full dataset)»; никакие фильтры не
  применяются вообще.
- **D3 механизм**: рейтинг питается `useMultiDimMetrics` ← `fd.depts`, а метод-фильтр в
  `useFilteredData` применяется только к topKpis/totals; dept-структуры (quarters) идут в
  рейтинг сырыми — потому КП/ЕП не влияют.
- **D8 уточнён (важная поправка)**: `calc-engine.ts:216` — квартальная корзина строится по
  **план-кварталу**; `fact_count` = строки корзины с фактом *когда угодно* (гейт GATE_HAS_FACT
  без сравнения дат). Поэтому прошедшие кварталы = 100% у всех (Q3/Q4 показывают нормальные
  15.8%/0%). Метрика не «вырождена», но: (а) факт в мае по строке Q1-плана засчитывается
  кварталу как исполнение — «исполнено В СРОК» не существует, 244 просрочки соседствуют со
  100% Q1; (б) метрика эталона «исполнение Q1 на дату среза» не воспроизводится.
- **D2 = второе лицо D1**: вкладка «По подведам» строится из subordinates (отдельные книги,
  как Реестр), вкладка «По управлениям» — из сводной книги; УАГЗО 111 153,4 ≈ Реестр-число
  111 269,4 против Свод-числа 51 153,4.
- **D14 снят (честность)**: `store.ts:388-411` — resetAllFilters сбрасывает и департаменты;
  сбой в моём тесте не воспроизводится надёжно (клик мог не попасть по кнопке, она рендерится
  только при activeCount>0). Перепроверить руками; из реестра дефектов убран в «не подтверждён».

## Ответ на давний вопрос «почему сверка всегда показывает расхождения»
Сегодня формульная сверка расчёт↔СВОД чиста. То, что выглядит «расхождениями» в UI:
(1) «РАСХОЖДЕНИЯ 210» на Экономии — это AD-конфликты **данных ГРБС** (экономия есть, флаг AD
не проставлен, или наоборот), т.е. замечания к заполнению таблиц, а не ошибки расчёта;
(2) противоречия **между вкладками/страницами продукта** (D1, D2) — двухисточниковость и разные
методологии, а не формулы; (3) исторические расхождения прошлых месяцев — реально были багами
(знак отклонения, «все годы» как база, латиница/кириллица в ключах, легаси-лист ШДЮ) и уже
починены. Что остаётся сделать — §17 спеки: категоризовать видимые «расхождения» прямо в UI
(наш баг / формула листа / методология / ввод ГРБС), чтобы вопрос больше не возникал.
