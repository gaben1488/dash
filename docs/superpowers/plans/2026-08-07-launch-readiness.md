## §1. Первопричина у каждого расхождения сверки

### Требование владельца (07.08)

Сверка перестаёт быть табло из двух чисел и дельты. Каждое расхождение обязано показывать
**первопричину** и **путь до строки-виновника** — лист, номер строки, ячейка, вклад в дельту.
Расхождение без объяснённой первопричины считается не «расхождением», а недоделанной сверкой.

Каскадные расхождения группируются: одна дельта в исходных данных, породившая три производных
несовпадения в разных строках сверки, показывается как **одна первопричина с тремя следствиями**,
а не как три независимые проблемы. Читатель должен видеть один дефект, а не три.

Классы первопричин закрыты списком:

| Класс | Что означает |
|---|---|
| `unfunded` | строка без источника финансирования: попадает в один периметр и не попадает в другой |
| `factQuarterMissing` | факт есть, фактический квартал пуст — строка выпадает из квартальных свёрток |
| `afterSlice` | расхождение возникает после нарезки по периоду: официал считает по всей книге, расчёт — по срезу |
| `знак` | отрицательные значения (прежде всего экономия): один путь суммирует сырое, другой клампит в ноль |
| `метод` | разная трактовка способа закупки (ЕП/ЭА/ЭК/ЭЗК) или доли способа по деньгам против количества |
| `отменённые` | отменённые, незаключённые и аннулированные строки учтены в одном источнике и отсеяны в другом |
| `парсинг` | строка прочитана иначе: отсев по слову, ширина зеркала, битая геометрия листа, иной формат журнала |

### Контракт

```ts
/** Класс первопричины расхождения. Список закрыт вводной владельца 07.08. */
export type ReconRootCauseClass =
  | 'unfunded'
  | 'factQuarterMissing'
  | 'afterSlice'
  | 'sign'          // «знак»
  | 'method'        // «метод»
  | 'cancelled'     // «отменённые»
  | 'parsing';      // «парсинг»

/** Путь до строки-виновника: адрес в исходной книге и её вклад в дельту. */
export interface ReconRootCauseRow {
  /** Имя листа книги-источника, как оно физически называется. */
  sheet: string;
  /** Номер строки листа (1-based, как видит человек в Google Sheets). */
  row: number;
  /** Адрес ячейки-виновницы, напр. 'AD1481'. Внутренний ключ наружу не выводится. */
  cell: string;
  /** Вклад именно этой строки в расхождение, в рублях (со знаком). */
  delta: number;
}

export interface ReconRootCause {
  class: ReconRootCauseClass;
  /** Строки-виновницы. Пустой массив запрещён: причина без адресов не предъявима. */
  rows: ReconRootCauseRow[];
  /** Объяснение человеческим русским: что произошло и почему числа разошлись. */
  explanation: string;
}
```

Каскад описывается на уровне строки сверки: причина получает идентификатор и список
показателей, которые она задевает, поэтому интерфейс собирает три производных несовпадения
под одним заголовком.

```ts
export interface ReconLine {
  /** Показатель сверки: ключ метрики (наружу выводится подпись из словаря). */
  metric: string;
  official: number;
  computed: number;
  delta: number;
  /** Первопричины. Пусто допустимо ровно при delta === 0. */
  rootCauses: (ReconRootCause & {
    id: string;
    /** Ключи других строк сверки, которые ломает та же первопричина. */
    affects: string[];
  })[];
}
```

Инварианты, которые должен проверять тест:

1. `delta !== 0` ⇒ `rootCauses.length >= 1`. Иначе строка помечается как невыясненная и
   выводится красной, а не молча показывает дельту.
2. Сумма `rows[].delta` по всем причинам строки сходится с `delta` строки. Непокрытый остаток
   — не повод округлить, а повод показать его отдельной причиной; предлагается выводить его
   как отдельную запись с пустым классом и подписью «первопричина не установлена» (это
   проектное предложение, а не восьмой класс из вводной).
3. Один и тот же `id` причины в нескольких строках сверки означает каскад; интерфейс обязан
   схлопнуть такие строки в группу.
4. `cell` — адрес листа, а не внутренний ключ колонки. Правило продукта «ни один внутренний
   ключ не доходит до глаз пользователя» (нарушение этого правила прямо сейчас живёт в §3)
   действует и здесь: буква колонки допустима только как часть адреса ячейки.

## §2. Новые экономические метрики

Разведка отобрала 12 кандидатов, каждый из которых считается **строго из имеющихся колонок**:
план и факт денег по источникам ФБ/КБ/МБ, способ закупки (ЭА/ЕП/ЭК/ЭЗК), плановый и фактический
квартал, экономия с гейтом утверждения, оси ГРБС и подведа, changelog правок плана.

Каждая метрика проходит пять этапов: **формула → тест → METRIC_KB → провенанс → UI**. Ни одна
из двенадцати сейчас не пройдена дальше нулевой отметки, поэтому ближайший этап у всех — формула
в `@aemr/core` с характеризационным тестом. Третий этап упирается в долг Д13 (§4): база знаний
заполнена частично, а бриф «Отчёт++» требует карточку у каждого видимого числа — значит
наполнение METRIC_KB для новой метрики входит в её же коммит, а не откладывается.

| Метрика | Формула из наших колонок | Трактовка / порог | Источник | Приоритет |
|---|---|---|---|---|
| Индекс декабрьского навеса | `Σ(факт, факт_квартал=Q4) / Σ(факт за год)` — по деньгам и по числу строк, в разрезе района/ГРБС/подведа | 25–35% норма, 35–45% жёлтый, >45% красный | Liebman & Mahoney, AER 2017 — https://www.aeaweb.org/articles?id=10.1257/aer.20131296 | высокий |
| Точность планирования (PEFA PI-1) | агрегат: `\|Σфакт − Σплан\| / Σплан`; строки: медиана `\|факт−план\|/план` | ≤5% A, ≤10% B, ≤15% C, дальше D | PEFA PI-1 — https://www.pefa.org/node/4762 | высокий |
| Разрыв освоения по источникам | `execution_pct` отдельно по ФБ/КБ/МБ, метрика = максимальная попарная разница в п.п. | <5 п.п. норма, 5–10 жёлтый, >10 красный (риск возврата субсидий) | Santos et al., JCMS 2025 — https://onlinelibrary.wiley.com/doi/10.1111/jcms.13640 | высокий |
| Соблюдение планового квартала | доля строк с фактом, где `факт_квартал ≤ план_квартал`; средний сдвиг `mean(факт_квартал − план_квартал)` | ≥80% норма, 60–80% жёлтый, <60% или сдвиг ≥1 квартала — план на бумаге | MAPS, индикатор 4 — https://www.mapsinitiative.org/en/methodology.html | высокий |
| Просроченный незаторгованный остаток | `Σ(план строк, где план_квартал < текущий и факта нет) / Σ(план года)` | на конец Q2: <10% норма, 10–20% жёлтый, >20% красный | PEFA / IBP — https://internationalbudget.org/wp-content/uploads/budget-credibility-what-can-we-learn-from-pefa-reports-ibp-2018.pdf | высокий |
| Конкурентная премия и цена ЕП | `premium` = средневзвешенная по НМЦК `savings_pct` конкурентных способов минус `savings_pct` ЕП; «цена ЕП» = `Σ(деньги через ЕП) × premium` | 5–10 п.п. конкуренция работает, <3 п.п. — торги формальные | Ohashi, RIO 2009 — https://link.springer.com/article/10.1007/s11151-009-9208-1 ; Bosio et al., AER 2022 — https://www.aeaweb.org/articles?id=10.1257/aer.20200738 | высокий |
| Двусторонний флаг аномальной экономии | доля строк и денег с `savings_pct ≥ 25%` (порог ст. 37 44-ФЗ) и доля конкурентных строк с `savings_pct ≤ 1%` | суммарно >15% строк в хвостах — системный дефект расчёта НМЦК | Decarolis, AEJ:Applied 2014 — https://www.aeaweb.org/articles?id=10.1257/app.6.1.108 ; ст. 37 44-ФЗ | высокий |
| Коэффициент равномерности (CV) | `σ(квартальные факты) / mean(квартальные факты)` по подведу и ГРБС | <0,3 равномерно, 0,3–0,7 сезонность, >0,7 рваное исполнение | Приказ Минфина № 112н от 18.06.2020 — https://base.garant.ru/74563528/ | средний |
| Коэффициент подтверждения экономии | `Σ(экономия, прошедшая гейт утверждения) / Σ(заявленная экономия)` | ≥90% честно, 80–90% жёлтый, <80% устойчиво — завышение | практика procurement-финансов: https://sievo.com/blog/procurement-savings ; https://www.eandi.org/resources/ei-blog/calculate-measure-procurement-cost-savings/ | средний |
| Внеплановые закупки (maverick spend) | `Σ(факт строк, отсутствовавших в плане на начало периода или добавленных менее чем за N дней до размещения по changelog) / Σ(факт)` | <5% норма, 5–10% жёлтый, >10% план оформляет закупки задним числом | Karjalainen et al., JBE 2009 — https://link.springer.com/article/10.1007/s10551-008-9768-2 | средний |
| Волатильность плана (churn) | среднее число правок план-строки по changelog до выхода на торги; флаг — ≥3 правок или правка суммы >20% за 30 дней до размещения | ≤1 правки на строку норма; рекордсмены 5+ — список на разбор | Open Contracting, Red flags 2024 — https://www.open-contracting.org/wp-content/uploads/2024/12/OCP2024-RedFlagProcurement-1.pdf | средний |
| HHI закупочного портфеля | `Σ(доля_i × 100)²` — доля подведа в фактах своего ГРБС и доля способа в деньгах подведа | <1500 низкая, 1500–2500 умеренная, >2500 высокая концентрация | DOJ HHI — https://www.justice.gov/atr/herfindahl-hirschman-index | низкий |

Две оговорки разведки, которые нельзя терять при внедрении. Коэффициент подтверждения экономии
опирается на индустриальную практику, а не на рецензируемую статью — академического канона
измерения procurement savings не существует, и карточка METRIC_KB обязана это сказать. HHI у нас
считается по портфелю **покупателей**, а не поставщиков: классический HHI требует реестра
участников торгов, которого в атоме нет, и подмена одного другим была бы враньём в подписи.

Честно отсеяно как невычислимое из наших колонок: доля торгов с единственной заявкой и среднее
число заявок на лот (нет данных об участниках), HHI и CR4 поставщиков в строгом смысле (нет
реестра участников), разброс удельных цен и price benchmarking (нет цен единиц), полный индекс
коррупционных рисков Фазекаша (нужны сроки публикации извещений и данные о заявках), скрининг
сговора по дисперсии ставок (нет ставок), длительность цикла в днях от извещения до контракта
(у нас кварталы, а не даты этапов процедуры). Эти шесть в план не берём и в интерфейсе не обещаем.

## §3. Чепуха к зачистке

Чистые зоны аудита `packages/web/src`, чтобы не искать заново: заполнителей вроде lorem ipsum нет,
`console.log` в компонентах нет (только `console.error`/`warn` в блоках catch и под DEV-условием),
заглушек «скоро»/«в разработке» нет, пустых обработчиков и `href="#"` нет, деления почти везде под
проверкой `plan > 0`. Найдено 14 реальных проблем.

### Высокий приоритет

1. **Битый класс `-tranzinc-`** — массовая замена slate→zinc задела слово translate, класса
   `-tranzinc-x-1/2` в Tailwind не существует, тултипы над барами не центрируются, иконки поиска
   не выровнены. `packages/web/src/pages/Analytics.tsx:670,693`,
   `packages/web/src/pages/Journal.tsx:111`, `packages/web/src/pages/Issues.tsx:349`.
2. **Заголовок колонки «AD»** — сырая буква листа Excel как подпись колонки конфликтов в таблице
   экономии, прямое нарушение канона `product-dictionary` §6.3. Нужна подпись «Конфликты»
   (метрика `economy_conflicts`). `packages/web/src/components/economy/EconomyDeptTable.tsx:130`.
3. **Мёртвые фильтры Журнала** — `PAGE_FILTERS` объявляет период, способ и вид деятельности, а
   страница шлёт в API только `search/action/deptId`: барабаны крутятся вхолостую.
   `packages/web/src/components/Header.tsx:29` против `packages/web/src/pages/Journal.tsx:44-76`.
4. **Мёртвые период и КП/ЕП на Замечаниях** — фильтрация идёт только по ГРБС, подведу, поиску и
   виду деятельности; кварталы и способ не влияют ни на список, ни на счётчики.
   `packages/web/src/components/Header.tsx:27` против
   `packages/web/src/lib/selectors/issues-filtering.ts:11-59`.
5. **Кнопка КП сбрасывает вместо переключения** — при активном ЕП клик по КП вызывает
   `clearMethods()` и роняет фильтр на «ВСЕ», тогда как соседняя кнопка ЕП переключает корректно.

## §5. Порядок работ до запуска

Шаг равен коммиту. Первым блоком идут первопричины сверки: пока расхождение не объясняет себя
само, всё остальное — украшение недоказанного числа.

### Блок 1. Первопричины сверки

1. Ввести тип `ReconRootCause` и расширение `ReconLine` в `@aemr/shared`, без потребителей.
2. Типизировать шов сверки: убрать `Record<string, any>` из `reconcile.ts` (пункт 13 пирамиды) —
   без этого причину некуда положить.
3. Тест-инварианты на контракт: дельта без причин запрещена, сумма вкладов строк сходится с
   дельтой, повтор идентификатора причины схлопывает строки в группу.
4. Классификатор `unfunded` и `factQuarterMissing` с адресами строк — самые массовые и самые
   механические классы.
5. Классификатор `afterSlice` — на нём же проверяется, что дельта Д21 (год по всей книге против
   среза) действительно распознаётся как класс, а не как «мнимое расхождение».
6. Классификаторы `знак`, `метод`, `отменённые`. Шагу про «знак» предшествует решение Д14 о том,
   чей канон главный, — вопрос владельцу задаётся здесь.
7. Классификатор `парсинг` — сюда сходятся слепые зоны №2, №16, №23, №24 и №25.
8. Группировка каскадов в интерфейсе сверки: одна первопричина, свёрнутые следствия, раскрытие
   до листа, строки и ячейки.
9. Страж-тест покрытия сверкой (Д21, первая половина): у каждого видимого показателя есть
   официальная пара либо явная пометка, что аналога нет.
