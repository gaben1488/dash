## Рабочая постановка

Сначала понять существующий продукт как единую систему: цель пользователя, исходные данные, правила ядра, серверные возможности, действия интерфейса, состояния и визуальный язык. Прочитать все исходные HTML, проверить их поведение и установить статус решений. Затем отобрать лучшие решения по требованиям и предложить целостное улучшение с доказанным сохранением функций. Внешний вид и внутреннее устройство проектируются совместно.

Владелец не обязан заранее написать полное техническое задание. Исполнитель уточняет и улучшает постановку, самостоятельно выводит проверяемые критерии, отмечает противоречия и предлагает решения. Уже заданные требования повторно не выясняются. По одному примеру нельзя объявлять все данные корректными, а по успешной сборке — продукт завершённым.

## Проверяемые результаты этапа

1. JSON прежних проверок в репозитории; исходные таблицы не публикуются.
2. Проверка конкретной ревизии репозитория с точными командами, средой и результатами; разделение локальной ошибки окружения и дефекта проекта.
3. Перепись каждого исходного HTML: версия, все смысловые разделы, состояния и действия, видимые подтверждения, преимущества, недостатки, связь с требованиями и фактическим кодом.
4. Карта «задача человека → источник → расчёт → API → экран → действие → проверка» с разделением реализованного, незавершённого и только предложенного.
5. Консолидация с объяснением выбора: что сохраняется, улучшается, заменяется и почему. Отдельно — порядок реализации, при котором следующий шаг опирается на проверенный предыдущий.

## Как беречь лимиты

- Не перечитывать всё дерево после каждого уточнения. Фиксировать ревизии и отпечатки файлов; повторно проверять изменившееся.
- Разбирать материал по устойчивым единицам: общая оболочка, периоды/отбор, происхождение данных, рабочие действия, экраны. Исторические варианты не смешивать с принятыми решениями.
- Сохранять доказательства и выводы по завершённым блокам. Не подменять этот процесс разрастанием списка документов или установкой десятков навыков.
- Сначала самые дешёвые проверки, выявляющие неверную предпосылку; затем дорогие прогоны. После успешного прогона не повторять его без изменений или новой причины.
- Навыки: Superpowers — постановка, поиск первопричины и доказательство результата; Product Design/Impeccable — смысл, визуальная иерархия, взаимодействие и доступность. Название навыка не служит доказательством качества.

## Первая установленная развилка

Корневое правило «база расчёта — все годы» и требование владельца «по умолчанию текущий год» могут относиться к разным уровням: общая база и начальное явное ограничение интерфейса. Поэтому прежнее замечание о сбросе прототипа к 2026 году нельзя целиком считать доказанной регрессией. Нужно сверить `store`, состояние фильтров, серверный периметр и динамический текущий год. Жёстко зашитый год, ограниченный список годов и отсутствие многолетнего режима — отдельные вопросы, которые нельзя смешивать с выбором начального периода.
