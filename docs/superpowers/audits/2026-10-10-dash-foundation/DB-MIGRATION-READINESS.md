# Dash — допуск к миграции модели данных (проверяемый контракт, не решение о СУБД)

Дата 10.10.2026. **Статус: NOT READY для записи в новую БД и переключения пользователей.** Источники: ревизия main `2461209`, код интеграционного PR [#79](https://github.com/gaben1488/dash/pull/79) (`25842a9` при проверке), ранее проверенные реестры [#69](https://github.com/gaben1488/dash/issues/69) и [#74](https://github.com/gaben1488/dash/pull/74). Проверка в этом документе — чтение кода и прежних зафиксированных результатов, **не новый live-снимок всех восьми книг**. Никакие production-данные или схемы здесь не меняются.

## 1. Что фактически работает

| Участок | Найдено в коде | Почему это не готовая миграция |
|---|---|---|
| Источник истины | Google Sheets → `google-sheets.ts` → pipeline → Fastify → React; `db/index.ts` открывает SQLite WAL, Drizzle, `busy_timeout=5000`, `foreign_keys=ON` | SQLite уже обслуживает кеши, снимки, журнал и настройки. Менять его на PostgreSQL/MongoDB *ради JSON* пока нечем обосновать |
| Сырьё строк | `schema.ts:procurement_rows.cells_json`, `snapshots.data`, формулы недельной версии в `snapshot.ts:sealWeeklyTableContext` | Объектная запись и исторический снимок не равны идентичности закупки; raw, вычисление, отображение и авторский комментарий должны иметь разные поля |
| Идентификатор строки | `procurement_rows.id` — автоинкремент внутри БД; `/api/rows/:deptId/:rowIndex` и `buildRowDto.rowIndex` — адрес позиции в листе | Ни один из них не остаётся неизменным при вставке строки в источнике. Колонка A тоже не уникальна гарантированно |
| Номер из A | В прежнем живом аудите подтверждены точные совпадения A и составные `173/1`, `173/2` | `Number`/`parseFloat` нельзя использовать для ID. Числовая сериализация даты и видимый формат A вроде `23/1` различаются |
| Запись | PR #79: `rowRevision`, повторное чтение Google перед записью, `withRowWriteLock`, журнал намерения; PUT и batch POST по адресу строки | Ревизия — проверка состояния **на момент чтения**, не постоянный ID. Блокировка локальна процессу, Google не даёт общей SQL-транзакции. Batch может примениться частично |
| Нормализация | Shared/Core: `buildCellDict`, классификация, расчёт метрик/сигналов, подведы; PR #74 исправляет 22 лишние позиции выбора подведов без потери строк | Проекцию нельзя заполнять статичным списком подведов или угадыванием вида из свободного текста |
| История | `metric_history`, `issues`, `issue_history`, `audit_log`, `changelog_entries`, `drive_comments`, `webhook_queue`, `book_watermarks`, `journal_gaps` | Это разные доказательные слои. Цитата комментария Drive не устанавливает адрес ячейки, а `audit_log.entityId` для записи строки опирается на текущую позицию |
| Отчётные расчёты | `orchestrator.ts`, rule book, `snapshot.ts`; официальная экономия Z+AA+AB только при AD=`да` | Не проверена воспроизводимость результата нового хранилища по *тем же входам и версиям правил* |

**Отдельная опасность:** `yearlong_kind_overrides` имеет ключ `(dept, pp_num)`. Это существующее предметное правило для конкретной разметки «В течение года», но не универсальный идентификатор любой закупки. Найденные в иных контекстах повторы A не доказывают коллизию именно этой таблицы; перед расширением ключа обязательна проверка её фактических 46 исходных строк и текущих оверрайдов.

## 2. Что именно мигрируем, а чего не делаем

**Не переносим единственную плоскую таблицу на MongoDB и не объявляем это решением проблемы разнородности ГРБС.** Для конкретного набора сначала нужны слои:

1. **Наблюдение источника (immutable):** `source_file_id`, реальный `sheet_id/gid`, версия/время чтения, позиция строки, raw A:AH по типам, формула, вычисленный результат, видимый текст, примечание ячейки, hash входов, флаги полноты/ошибки. Сохранять исходный снимок в том виде, который реально считан; отсутствие формул явно `not_read`, не `no_errors`. Не заменять `null` на 0.
2. **Тождество закупки:** внутренний UUID, связи с версиями наблюдения, история `split/merge/moved/renamed`, статус разрешения. Сопоставление по (книга, A, предмет, организация, иным признакам) — только кандидат, а не автоматическая гарантия; при конфликте/повторе — очередь подтверждения. Старые адреса хранятся как provenance, не как ключ.
3. **Предметные проекции:** общий костяк плана + расширения по специфике ГРБС с версиями схем. Неизвестные/нестандартные поля сохранять в raw и не объявлять нормализованными без правил. Процедура — отдельная сущность. Связь «строка плана ↔ процедура» many-to-many с долями, участниками и основанием; повтор кода не равен повтору закупки.
4. **Организации и справочники:** постоянный `organization_id`, краткое отображаемое имя из согласованного справочника (приоритет R, при пустом R — E согласно текущей миграционной задаче), прежние имена — отдельная история/алиасы. Переименование не порождает новую организацию; при неоднозначности не сливать сущности автоматически.
5. **Смысл и объяснения:** AF, AG, AH — самостоятельные текстовые поля. Cell note, Drive discussion thread, комментарий реестра и журнал изменений — четыре различные структуры с разной полнотой связи и правами. Извлечённые из текста сроки/этапы/объяснения — отдельная версионируемая `interpretation` с источником, правилом, уверенностью и возможностью отмены.
6. **Проверки и сигналы:** хранить `rule_version`, `source_version`, `applicability`, `evidence`, `impact`, `status`, `resolution`. Число предупреждений без охвата/влияния не служит KPI. Старое решение пользователя переживает повторный расчёт и не исчезает после пересоздания snapshot.

Это логический контракт, **не готовые таблицы или подтверждённый DDL**. SQL-проекции, JSONB или документы определяем *после* снятия коллизий и фактического профиля запросов.

### G3. Shadow read и отказные сценарии

- [ ] Держать существующий Google → Core → Dash базовым; новая БД — sidecar read-only. Сравнить JSON ответов реальных endpoints, `GET /api/rows`, панелей, фильтров/детализации, отчетов и архивов на **одинаковых** входах и версиях расчёта. Проверить производительность сравнительно с измеренным старым baseline, а не выдуманным SLA.

## 4. Выбор СУБД — отдельный эксперимент

| Вариант | Что действительно проверяем | Решение сейчас |
|---|---|---|
| SQLite + текущий JSON | Достаточна ли запись в одном процессе, текущие индексируемые ключи, скорость расчётов, нагрузка и хранение снимков | **Оставить текущий runtime**, пока не доказан ограничитель; основной дефект — семантика/ключи, не синтаксис SQL |
| PostgreSQL + JSONB | Конкурентные записи, ограничения уникальности, связи, эффективный аудит и индексация нужных расширений | Кандидат на пилот sidecar; сложность миграции и ops тоже измерять |
| MongoDB | Полиморфные документы наблюдений, массивы сырых данных, составные запросы/индексы, update/transaction semantics для связей и истории | Кандидат на таком же frozen-корпусе; гибкость формы не заменяет идентичность, многосущностные связи и согласованность |

**Критерий выбора:** реальные запросы, изменчивость схем по ГРБС, размер/частота снимков, доказанное удобство исправления сложных случаев, сквозные тесты отказов, эксплуатационная стоимость. Победитель определяется измерениями, не общим тезисом «NoSQL гибче».

## 5. Связь с визуальной консолидацией

Прототип `docs/superpowers/mockups/dash-consolidated` не соединять с новой проекцией напрямую. После G2–G3 интерфейс получает стабильный `entity_uuid`, `source_version`, `provenance` и статусы `unknown/partial/confirmed` через типизированный adapter; прежние компоненты сохраняют маршруты, Word, виртуализацию, фильтры, навигацию и черновики. Демо `model.mjs` никогда не участвует в импорте.

**Текущее решение для следующего этапа:** закрывать тестируемый визуальный/поведенческий контракт в draft #70 и безопасную запись в draft #79 отдельно; одновременно подготовить G0 и набор коллизий G1. Не переключать данные и не объявлять какую-либо СУБД принятой.
