# Реестр сигналов AEMR — полная инвентаризация (20.08.2026)

Назначение: перечень всех сигналов продукта — где вычисляются, куда и под какими
именами выводятся, как связаны, где дублируются, где не выводятся вовсе и где
подача запутана. Ничего в коде не менялось; каждое утверждение несёт адрес файла.

Сокращения путей: `core/` = `packages/core/src`, `shared/` = `packages/shared/src`,
`web/` = `packages/web/src`, `server/` = `packages/server/src`.

## 2. Связи и подавления (п.34)

Подавления, выполняемые ядром (`core/pipeline/signals.ts`):

1. **planYearMissing гасит planWithoutExecution** — первопричина главнее следствия (signals.ts:695–697; продублировано словами в check-registry.ts:582).
2. **planYearMissing и derivedFormulaBroken гасят factQuarterMissing** — остаточная страховка срабатывает только там, где обе первопричины молчат (signals.ts:659–660); та же лестница словами — check-registry.ts:64.
3. **economyConflict (случай б) обрезан сверху порогом 25 %** — выше говорит highEconomy, а пробел флага AD покрывает правило status_on_data_rows; дедупликация 18.08, В-7 (signals.ts:483–494; check-registry.ts:489 повторяет).
4. **lowCompetition гасится точным равенством план=факт** (артефакт заполнения, signals.ts:538) и не трогает ЕП.
5. **Гейты по способу ЕП**: highEconomy/lowCompetition не считаются для ЕП (signals.ts:528), factDateBeforePlan — только конкурентные (signals.ts:680), ветка earlyClosure «>180 дней» — только конкурентные (signals.ts:560), economyConflict (б) — не ЕП (signals.ts:476); зеркально epFactDeviation живёт ТОЛЬКО на ЕП (signals.ts:603).
6. **epRisk гасится законным основанием**: монополисты, поручения губернатора, пункты ч.1 ст.93 без лимита суммы (signals.ts:447–451, 268).
7. **earlyClosure и factDateBeforePlan разведены порогом 30 дней** (signals.ts:683).
8. **tdWithProgram** отфильтровывается на вебе даже из старых снимков — `isRetiredIssue` (`web/lib/diagnostics/mechanism-groups.ts:82`).
9. **Свёртка простыни**: карточка механизма = один класс проверки со списком адресов (mechanism-groups.ts:161); правила row_numbering и text_hygiene дают одну карточку на лист по якорю (rule-book.ts:646, 813); noise map группирует по типам (dataset-signals.ts:462 — но никуда не выводится, §4).
10. **Сверка**: наблюдения (kind='observation') не входят в арифметику дельты (recon-root-cause.ts:65–95); каскады с одним id схлопываются в группу (recon-root-cause.ts:103, groupCascades:253).
11. **Свод**: негорящий бейдж сверки не исчезает, а называет причину (web/lib/svod/recon.ts:40–46).

Связи-цепочки: RowSignals → Issue (checkId через LEGACY_SIGNAL_TO_CHECK) →
компонент качества заполнения (`trustComponent` в CHECK_REGISTRY) → Контроль →
«Качество заполнения»; те же issues → Отчёт (signalsFor) → Пульт (баннер) →
SSE (issues-appeared). Классы первопричин сверки unfunded / factQuarterMissing —
те же смыслы, что сигналы planYearMissing / factQuarterMissing, но живут своим
словарём (recon-root-cause.ts:17–33).

## 5. ЗАПУТАННОСТЬ подачи

1. **Четыре словаря имён одного построчного сигнала** (§3.1) — заявленная цель «названия должны совпадать везде» сегодня не выполняется технически: бейджи, словарь продукта, реестр проверок и Дисциплина никак не связаны, синхронизация ручная (признание в product-dictionary.ts:20–23).
2. **factWithoutDate — смысловое противоречие между вкладками**: Реестр и корзина «В течение года» называют строку законной стадией (канон п.71), а Контроль/Отчёт показывают ту же строку как замечание warning «Факт суммы без даты» с рекомендацией «заполнить дату» (check-registry.ts:527). Читатель на двух вкладках получает противоположные оценки одной строки.
3. **Экономия раскидана по шести местам с разными формулировками**: economyFlag (зелёный бейдж), economyConflict, highEconomy/anti_dumping, status_on_data_rows, economy_sign_check (СВОД), мёртвый economy_hidden — плюс на Мониторинге manual-savings/control-gap. Взаимные подавления описаны только в комментариях кода и kbHint; сквозной страницы «экономия и её флаги» нет (вкладка «Экономия» показывает деньги, не сигналы).
4. **Три разных «сверки» под одним словом**: Контроль→Сверка (официальный лист против пересчёта, с первопричинами), Свод→бейджи сверки (те же числа, другой словарь ReconStatus ok/warning/high), Мониторинг→MatchPanel/внутренняя сверка (книги ГРБС против реестра процедур, третий словарь sums-differ/sheets-only/journal-only). Слово одно, механизмы и словари — три.
5. **Датасет-аналитика без ответа «какая строка почему» (п.119)**: на Аналитике Бенфорд, выбросы, сезонные аномалии и дробление показаны счётчиками; строк-виновниц нет ни у одного (адреса выбросов есть внутри OutlierResult.indices, сезонные несут rowIndex — но до экрана не доезжают). Одновременно 27 проработанных адресных находок (аномалии датасета + anomaly-detection) — сироты §4. То есть адресные механизмы лежат в столе, а на экране висят безадресные счётчики.
6. **Пульт**: карточек «Сигналы проверок» десять, отбор произвольный (нет ЕП-риска, ЕП без обоснования, «не равен плану по ЕП»…), одна карточка мёртвая (stalledContract), легенда KB устарела (Dashboard.tsx:1238), а описания earlyClosure в реестре проверок не совпадает с фактическим детектором (check-registry.ts:320 «>30 дней» против кода signals.ts:549).
7. **Severity-хаос** (§3.3): у одного сигнала три строгих оценки по трём поверхностям, расхождение признано и отложено.
8. **Дисциплина против реестра проверок**: механизм planYearMissing на Дисциплине объясняется через столбец P (actions.ts:76), тогда как канон 20.08 и описание проверки в реестре ведут на N (check-registry.ts:51) — читателю двух вкладок предъявляют разные первопричины.
9. **Пространство category `signal:*` против checkId** — в SQLite замечания живут одновременно с category `signal:stalledContract` (camelCase) и checkId `stalled_contract` (snake_case); веб вынужден держать конвертер signalToCheckId (nature-categories.ts:130) — два способа адресовать один класс.
