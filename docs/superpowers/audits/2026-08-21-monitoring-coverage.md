**Книга стала заметно чище.** За три дня отдел закрыл девять находок: текстовая

**Одно место стало хуже в книге.** Верный код `ЭК03-26` переписан в `ЭЗК03-26` на

следствие того, что список правок не отделял настоящие искажения от верных редких
форм. Урок для следующего списка: у каждой предлагаемой правки должен стоять
признак «проверено, что нынешнее написание неверно».

## 6. Что мешает и блокеры

Порядок — по величине последствий. У каждого блокера названы масштаб в строках и
деньгах, что нужно от людей и что закрывается кодом без правки книги.

### Б-1. Заказчик — свободный текст, справочник не работает

**Масштаб.** На восьми листах управлений **76 различных написаний** заказчика — на
четыре больше, чем три дня назад. Справочник `Перечень ГРБС` даёт 111 ключей. Пару
находят **11 написаний**; в строках — 104 из 374. Не находят **270 строк (72,2 %)**,
за ними **1 180 141 523,39 ₽ НМЦК из 1 299 693 085,85 (90,8 %)**. На листе `25-26` —
281 строка из 391.

**Из чего складывается.** 144 строки — само управление вместо учреждения
(«УД АЕМР» 52, «УИО АЕМР» 31, «УДТХиРКИ» 27, «УЭР АЕМР» 16, «УО АЕМР» 13,
«УФБП» 4, «УКСиМП АЕМР» 1); 27 строк — совместные закупки, где заказчика вообще нет
(«Совместный аукцион ШКОЛЫ» 7, «Совместный (УЭР,УО,УДТХиРКИ, УИО, УКСиМП, УАГЗО,
УФБП)» 5, «Совместный аукцион Д.САДЫ» 4, «Совместный аукцион Д.САДЫ, ШКОЛЫ» 4,
«Совместный аукцион Д.САДЫ+ШКОЛЫ» 3); 99 строк — учреждение, записанное иначе, чем
в справочнике («МКУ ЕРУС» 22, «МБОУ ЕСШ №1 им. М.В. Ломоносова» 6 и
«МБОУ "ЕСШ №1 ИМЕНИ М.В.ЛОМОНОСОВА"» 4 — одна школа двумя способами).

**Что мешает.** Ни одного разреза по учреждению нельзя построить честно: одна школа
считается за две, а больше двух третей строк вообще не привязаны к справочнику. Все
выводы раздела 4.3 держатся на написаниях, а не на сущностях.

**Что нужно от людей.** Три решения владельца: заводить ли в справочник сами

## 8. Как это проверено

Источник — машинная выгрузка книги `E:/aemr-dumps/book-dumps/monitoring-21-08.json`
(момент чтения `2026-08-20T23:30:38.140Z`, то есть 21.08.2026, 11:30 по Камчатке).
Читалась потоково через `ijson`, слой значений (`formattedValue`, `effectiveValue`) и
слой формул (`userEnteredValue.formulaValue`) — раздельно, вместе с метаданными строк
(`rowMetadata.hiddenByUser`), объединениями, условным форматированием и границами
фильтров.

Сравнение велось с дампом `monitoring.json` (момент чтения
`2026-08-17T23:23:52.909Z`) тем же кодом: каждое число прошлого разбора сначала
воспроизведено на старом дампе, и только потом пересчитано на новом. Совпадение с
прошлым разбором дословное — 374 строки, 29 строк «ошибка», разрыв 9 001 582,73 ₽,
шесть искажённых кодов, 201 скрытая строка, 163 ручные ячейки экономии, — поэтому
различия в разделах 1 и 5 отнесены к правкам книги, а не к способу счёта.

Как снят сам дамп и как снимать следующий — раздел
[10](#10-как-снимать-свежий-дамп). Правило волны: разбор книги без даты снимка в
шапке недействителен, потому что книга правится ежедневно и за трое суток в ней
меняется полсотни строк.

Одна оговорка о счёте, относящаяся к обоим дампам одинаково: ячейка `25-26!D390`
хранит «39 382,00» с табуляцией на конце. Формально это сумма текстом, но в
счёт «61 ячейка» прошлого разбора она не попала — при сравнении с прошлыми
числами эту единицу надо держать в уме.

Способ определения поставщика и разбор кода процедуры считались тем же регулярным
выражением, которым их читает продукт (`packages/shared/src/procedure-ref.ts:94`),
включая свёртку латинских омоглифов и границы слова. Деньги — рубли книги без
пересчёта. Все ссылки вида `файл:строка` проверены на текущем состоянии рабочего
дерева.

**Не проверено:**

- фактическое поведение вкладки на проде — разбор вёлся по коду, экран не открывался;
- расхождения с книгами ГРБС по конкретным кодам — книги ГРБС в этот разбор не
  выгружались;
- содержание `.docx`-выгрузок в `C:/Users/filat/Documents/материалы` — их исходники
  лежат в репозитории и читались оттуда.

## 10. Как снимать свежий дамп

Книга правится ежедневно. Этот разбор начинался по дампу от 18.08, и к моменту
проверки половина его блокеров оказалась устаревшей: за трое суток изменилось
53 строки и закрылось пять дефектов из списка. Отсюда правило, которое дороже
любого числа в этом документе: **перед разбором книги снимается свежий дамп, а
дата снимка ставится в шапку документа.** Разбор без даты снимка недействителен.

Скрипт выгрузки — `scripts/dump-books.cjs`, доступ только на чтение
(`spreadsheets.readonly`). Он берёт все десять книг проекта, пишет по одному
JSON-файлу на книгу и льёт поток на диск лист за листом, поэтому пиковая память
равна одному листу, а не одной книге. Слои, которые он забирает: значения
(`effectiveValue`, `formattedValue`), введённое пользователем
(`userEnteredValue`, включая формулы), формат, условное форматирование, защиты,
проверки ввода, объединения, именованные диапазоны, скрытые строки и колонки
(`rowMetadata.hiddenByUser`), автофильтр и виды фильтров, заметки к ячейкам.
Именно из этого слоя берутся скрытые строки и границы фильтра, которых нет в
обычном чтении значений.

Запускается на сервере отдельным контейнером из образа `aemr-server` — так
выгрузка переживает пересборку боевых сервисов:

```bash
docker run --rm \
  --env-file /opt/aemr/.env \
  -e DUMP_ONLY=monitoring \
  -e DUMP_FORCE=1 \
  -e DUMP_OUT=/out \
  -u 0 \
  -v /srv/aemr-dumps/book-dumps:/out \
  aemr-server \
  node /app/scripts/dump-books.cjs
```

| Переменная | Зачем |
|---|---|
| `DUMP_ONLY` | ключи книг через запятую (`monitoring`, `svod`, `grbs-UO`, …). Пусто — выгружаются все десять |
| `DUMP_FORCE` | перезаписать файл, уже лежащий в каталоге. **Без неё книга с готовым дампом больше 1 КБ молча пропускается — и разбор снова идёт по старью** |
| `DUMP_OUT` | каталог вывода внутри контейнера, по умолчанию `/out` |
| `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_PRIVATE_KEY` | берутся из `.env` боевого сервера; в репозиторий не попадают никогда |

Два условия, без которых запуск не даст файла: **каталог монтируется с правом
записи** (обычный bind-mount, не `:ro`) и **контейнер запускается от root**
(`-u 0`) — иначе создание файла в `/out` падает по правам. Успех виден по строке
`BOOK monitoring done bytes=…`; отказы собираются в `_failures.json` рядом с
дампами.

Файл забирается с сервера в `E:/aemr-dumps/book-dumps/` под именем с датой
(`monitoring-21-08.json`), а прошлый дамп **не удаляется**: без него нельзя
посчитать движение, а движение книги — половина ценности разбора (раздел 9
целиком построен на паре дампов).

Читать дамп можно **только потоково**. Файл книги мониторинга — 57 МБ, книги
`grbs-UO` — два гигабайта; `json.load` даёт `MemoryError`. Рабочий приём:

```python
import ijson
with open('E:/aemr-dumps/book-dumps/monitoring-21-08.json', 'rb') as f:
    for sheet in ijson.items(f, 'spreadsheet.sheets.item', use_float=True):
        ...  # в памяти один лист за раз
```

Кириллицу из такого разбора в консоль не печатать: консоль Windows работает в
`cp1251`/`cp866`, и `print()` роняет скрипт с `UnicodeEncodeError: charmap`.
Результат пишется в файл в UTF-8 и читается оттуда.
