Чтение книги: `services/monitoring.ts` — 11 видимых листов параллельно, кэш на
процесс с TTL, отказ листа не валит цикл (`failed` поимённо). Деньги — рубли
(книги ГРБС — тысячи), единица объявлена в `source.moneyUnit`.

**Несоответствие №1 (P0, главное).** Живой роут `/api/monitoring/match` отдаёт
`{summary, matched, bookOnly, monitoringOnly, ambiguous, listCells, internal}`
(routes/monitoring.ts:304-316). Но `normalizeMatch` в contract.ts:858 ждёт
форму `{coveragePct, outcomes, rows, internalDiff}` — ни одного из этих полей в
живом ответе нет, все три списка выходят пустыми, и функция возвращает `null`
(contract.ts:889). Следствие: `matchByCode` на странице (Monitoring.tsx:146-150)
всегда пуст, и полоса «Сверка со строкой книги управления» в карточке КАЖДОЙ
процедуры (ProcedureCard.tsx:269-298) всегда пишет «пары нет либо сверка не
подключена» — при живом и работающем роуте, который панель аналитики
(MatchPanel) читает успешно. Это тот же класс бага «маппер не понимает живую
форму сервера», который 20.08 уже чинили для свода и справочника
(contract.ts:600-613, 737-761 — комментарии об этом прямо в коде). Канон
п.101а требует «маппинг с книгами ГРБС ПО КАЖДОЙ СТРОКЕ» — до строки маппинг
сейчас не доезжает. Лечение: либо научить `normalizeMatch` живой форме
(из `matched[]` строится `MatchRow` по коду: bookDept/bookRow из
`bookRow.book`/`rowKey`, planRub/factRub из `nmck.bookRub`/`fact.bookRub`,
вердикты из `agrees`), либо кормить карточку из уже работающего
`normalizeMatchView`.

**Несоответствие №2 (P1).** `sheetsRead` сервера уже содержит СВОДНЫЙ, «25-26»
и «Перечень ГРБС» (`MONITORING_DATA_SHEETS` = 8 листов управлений + эти три,
core/monitoring/procedures.ts:71-75). `readCount` добавляет к нему ещё раз
+1 за каждый непустой раздел ответа — те же листы считаются дважды. При полном
чтении случайно выходит 14 («11 + 3» — как будто предки прочитаны), а в
промежуточных состояниях число не значит заявленного: лист «25-26» прочитан,
но пуст → «13 из 14», хотя листов прочитано 11 из 11. Сервер честно шлёт
`sheetsExpected` (routes/monitoring.ts:142) — веб его игнорирует. Лечение:
считать «прочитано X из 11 листов с данными; 3 листа-предка — только форма».

**Несоответствие №3 (P0 по п.127).** При выбранном управлении строки реестра в
полосе срезаны, а счётчик сигналов — нет: он считает `data.signals` целиком,
тогда как ниже `SignalCards` показывает срезанные `scopedSignals`
(Monitoring.tsx:111-114, 382). Читатель УКСиМП видит «сигналов: 12», листает
вниз — карточек три. Ровно то, на что жаловался владелец («чужое лезет в
фильтр»). Лечение: полосе отдавать `scopedSignals` + фразу «ещё N — уровня
всей книги, видны в срезе „все управления"».

**Несоответствие №4 (P1).** Листов-предков в ядре ТРИ: «Отчет по процедурам
Свод», «СВОД», «ГРБС» (core, тест directory.test.ts:79-81); в веб-константе
`ANCESTOR_SHEET_NAMES` — ДВА (contract.ts:948, «ГРБС» потерян). Полоса пишет
«3 листа скрыты» только благодаря `+1` в формуле, а режим «Листы-предки»
показывает имена двух. Сервер шлёт `ancestors.sheets` в ответе
(routes/monitoring.ts:213-216) — веб игнорирует и держит свою копию. Лечение:
читать предков из ответа, константу оставить запасной.

### 1.4. Панель разрезов и крошки — карта до предела (прямой запрос владельца)

Состояние разрезов: `SliceState` (slices.ts:53-72). Применение: `applySlices`
(slices.ts:191-214) — все условия соединяются «И», то есть разрезы
**комбинируются свободно**, это уже работает. Списки значений собираются из
живых строк с частотами (`tally`, SliceBar.tsx:44-53) — вес выбора виден до
нажатия. Крошки: `describeSlices` (slices.ts:234-254) + снятие по одной
(`clearSlice`) и «снять все» — SliceBar.tsx:222-247, видны и при сложенной
панели, с «показано X из Y».

Что есть (10 органов, SliceBar.tsx:145-219):

| Способ | select | `method` | с расшифровкой и частотой; порядок METHOD_ORDER |

| Месяц | select | `periodMonth` | — |

Чего НЕТ против запроса владельца (стадия/способ/год/заказчик/диапазон
НМЦК/снижение %/только-с-опечатками, чипы, сохранение, связь с глобальным
фильтром):

1. **Год ПЕРИОДА без органа управления (P0).** `SliceState.periodYear`
   существует, `applySlices` его честно применяет (slices.ts:203), крошка для
   него написана (slices.ts:239) — но селекта в панели НЕТ. Следствие: «1
   квартал» отбирает Q1-2025 и Q1-2026 разом (книга переходящая), и разделить
   их можно только годом процедуры из кода — а это ДРУГОЙ год (год объявления,
   не год даты). Мёртвое состояние + дыра ровно в запрошенном «фильтре по
   году». Лечение: селект «Год (по дате)» рядом с кварталом, значения из
   `dateYear` живых строк.
2. **Разреза «снижение %» нет (P0 по запросу).** Ни поля в `SliceState`, ни
   контрола. При этом гистограмма снижения УЖЕ умеет отдавать клик по корзине
   (`onPickBucket`, DiscountHistogram.tsx:154-156; проп `onPickDiscountBucket`
   AnalyticsSection.tsx:55), но страница его НЕ передаёт (Monitoring.tsx:358) —
   провал «корзина → реестр» спроектирован и не подключён. Лечение: поле
   `discountBucket` в SliceState с теми же ключами корзин, что у ядра
   (`zero`, `0-5`, …, `50+`), предикат по `reductionPct`, крошка, и проброс
   `onPickDiscountBucket={(k) => setSlices({...slices, discountBucket: k})}`.
3. **Диапазон НМЦК только корзинами.** Пять корзин хороши для разговора, но
   вопрос «что у нас от 5 до 8 млн» требует свободного диапазона. Усиление:
   два поля «от/до, руб.» как альтернатива корзине (одно поле состояния
   `nmckFrom`/`nmckTo`, крошка «НМЦК: 5–8 млн»).
4. **«Только с опечатками кода» растворено в «только с дефектами».**
   `defectsOnly` собирает ВСЕ дефекты (даты, ручная экономия, контроль…).
   Отдельного разреза «код с опечаткой / без кода» нет, хотя п.125 сделал
   различение этих двух состояний каноном, а `CodeCell` их уже различает
   (RegistryTable.tsx:179-200). Усиление: селект «Код: любой / с опечаткой /
   не читается» либо чек рядом с defectsOnly.
5. **Сохранение состояния (P0 по запросу).** `modeId`, `slices`, `sortKey`,
   `sortDir` — обычные `useState` (Monitoring.tsx:80-84): уход на другую
   вкладку и возврат сбрасывают всё. Переживают перезагрузку только гармошки
   дат/бюджетов (localStorage, RegistryTable.tsx:59-77). Ссылку «смотри, вот
   разрез УО за 2 квартал по ЭА» послать коллеге нельзя. Лечение: сериализовать
   срез в URL search-параметры (react-router уже в проекте) — это даёт и
   переживание перезагрузки, и глубокие ссылки; localStorage — запасной для
   сортировки.
6. **Связь с глобальным фильтром управлений** — РАБОТАЕТ по п.127: срез шапки
   сужает реестр (`scopeProcedures`) и сигналы (`scopeSignals`,
   dept-scope.ts:19-58), списки панели строятся из уже срезанных строк
   (SliceBar получает `modeRows`), скоуп назван словами (Monitoring.tsx:192-200).
   НО: режим «только ГРБС / с подведомственными» (`deptOnlyMode`) вкладка
   игнорирует, а новый селектор `org-scope.ts` (в движении, приказ владельца
   20.08) к ней не подключён. В мониторинге «заказчик» — это и есть
   учреждение-подвед, а справочник «Перечень ГРБС» даёт связь
   учреждение → ГРБС-владелец: сырьё для разбивки `withSubs` есть. Усиление
   (P1): при одном выбранном ГРБС с подведами группировать реестр по
   заказчикам этого ГРБС (`useOrgScope` + `usedInBook`/`grbs` справочника),
   в режиме «только ГРБС» — честная фраза «подведы скрыты режимом».
7. **Чипы активных фильтров** — есть и работают (крошки с крестиками, «снять
   все», «показано X из Y»). Дополнить чипом основания периода (см. выше) и
   чипом глобального управления (сейчас периметр шапки назван только в
   заголовке портрета — в ряду крошек его нет, а именно туда смотрит рука).
