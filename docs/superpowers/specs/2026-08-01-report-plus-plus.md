# Отчёт++ — утверждённый бриф переверстки (01.08.2026)

**Статус:** бриф подтверждён пользователем (три ответа, 01.08). Уточняет и частично заменяет разделы спеки «Отчёт 2.0» (2026-07-13); при расхождении побеждает этот файл.

## Чего хочет пользователь (расшифровка, без потерь)

Страница «Отчёт» и обе выгрузки — это основной и дополнительный отчёты **«версии ++»**: всё, что есть в ручных документах, есть и здесь, но полнее, универсальнее, с раскрытием на месте. Любым элементом пользуется «полный нуб» без обучения. Методология — не спрятанная страница, а **встроенная база знаний у каждого показателя**. Эти принципы касаются всего продукта, не одной страницы.

## Решения брифа (01.08)

1. **Сразу скролл-документ.** Страница перестраивается по скелету эталона за один заход: шапка со срезом → блок «ПО КОНКУРЕНТНЫМ ПРОЦЕДУРАМ» → блок «ЕДИНСТВЕННЫЙ ПОСТАВЩИК» → восемь секций ГРБС → липкое оглавление. Не поэтапно.

2. **БЗ по наведению — системный механизм.** Наведение мыши на показатель открывает кусок базы знаний: полный, дотошный, для нубов, дружелюбный. Источник — готовые 837 строк `METRIC_KB` + словарь продукта. Состав куска: что это простыми словами → как считается (формула словами) → откуда взято (источник/ячейка) → на что влияет. Механизм один на весь продукт (компонент-контракт), не самодельные подсказки по страницам.

3. **Доказательство по клику — без переходов в Реестр.** Клик по числу раскрывает путь «фраза → формула → строки-атомы → ячейка листа» **прямо на странице** (инлайн/оверлей доказательства): полные списки видны здесь же. Ссылок «→ Реестр» не делать: Реестр в текущем виде «странно сходится» и дублируется с сигналами/рекомендациями/замечаниями.

4. **Судьба Реестра (зафиксировано, реализация позже).** Вместо Реестра — «отображение данных с возможностью редактирования, аналогичное Excel/Google Sheets, но с нашими фишками» (мастер-план В6). Всю навигацию перелопатить под четыре раздела спеки; это делается ПОСЛЕ выведения ядра/бэка/API на 100/100 (разбивка god-файлов В4) — миграции данных на новый UI идут от чистого ядра.

5. **Организация работы: короткие субагенты (<15 минут)** на изолированные куски с жёсткими границами файлов; шаг = коммит. Никаких часовых волн.

## Гарантия «++» (приёмка)

Чек-лист: каждое утверждение обоих ручных отчётов присутствует на странице; каждое число раскрывается до ячейки без ухода со страницы; каждый показатель объясняется по наведению; ни одного внутреннего ключа в текстах; списки («в работе», «осталось отыграть») показываются целиком на странице.


## Корректировка 01.08 (в ответ на ревью пользователя)

**Ошибка первой итерации:** тело документа отрендерено плоскими абзацами тех же
строк, что уходят в .docx, — «состав = выгрузка» соблюдён, а форма деградировала
до сплошного текста. Это НЕ «++».

**Правильное прочтение «++»:** состав эталона полностью + ВСЕ технологии продукта
в каждой секции + идеальный дизайн. Конкретно, по секциям документа:
- шапка: KPI-ряд плиток (KpiTile) с дельтами к прошлому снимку и происхождением;
- claim-строки: фраза эталона, числа — интерактивные (KbHover по наведению,
  доказательство по клику), НЕ сплошные <p>;
- список исполнения по ГРБС: строки с барами процентов и переходом к секции;
- бюджетные тройки: структурная мини-разметка с цветами ФБ/КБ/МБ (DESIGN.md),
  не скобки в тексте;
- сверка со СВОДом с адресами ячеек (DiffText + ссылки в лист) — в каждой
  секции ГРБС; сигналы — бейджами; недельные дельты — в шапке секций;
- честные плашки и режим эфир/архив сохраняются как есть.

**Гарантия «страница = выгрузка» меняет механизм:** не общий рендер, а регресс
состава — тест сверяет НАБОР УТВЕРЖДЕНИЙ страницы с mainReportBlocks (тексты
claim-строк формируются теми же фразовыми хелперами text-blocks, экспортными).
Форма свободна, состав закреплён.

**Порядок:** (1) KPI-ряд в шапку документа; (2) переверстка блока КП в
структурную секцию; (3) блок ЕП; (4) секции ГРБС со сверкой/сигналами/дельтами;
(5) доп. отчёт секцией; (6) доказательство по клику; (7) снос Report.tsx.


## Формула «++» (канон, слова пользователя 01.08)

«++» значит ТО ЖЕ, но ЛУЧШЕ и БОЛЬШЕ по всем возможным критериям.
- «То же»: полный состав и порядок ручного отчёта — читатель бумаги узнаёт
  документ мгновенно, ни одно утверждение не потеряно (страж — регресс состава).
- «Лучше»: каждое измерение усилено — читаемость (структура вместо сплошного
  текста), объяснимость (БЗ у каждого показателя), проверяемость (провенанс до
  ячейки), скорость (оглавление, якоря), честность (плашки, происхождение).
- «Больше»: то, чего бумага не может, — дельты к прошлой неделе, сверка с
  официалом на месте, сигналы, раскрытие полных списков, режим эфир/архив.


## Правило «топ-N раскрывается» (канон, 01.08)

Везде, где отчёт показывает срез выборки (топ-3 сигналов секции ГРБС, крупные
ЭА, «в работе», перечни незаключённых), UI обязан давать разворот В ПОЛНУЮ
выборку с полной фильтрацией — инлайн, на этой же странице, без навигации.
Механизм один — компонент-контракт `ExpandableRows`: свёрнуто N строк и
честная подпись «показать все M», развёрнуто — полный список с поиском и
фильтрами по колонкам выборки. Самодельные «показать ещё» по страницам
запрещены. Правило распространяется на весь продукт.


## Редизайн v3 (требования пользователя, 01.08 вечер)

1. **БЗ у КАЖДОГО числа и показателя** — не только у hero-процентов. Любое
   видимое число несёт наведение с объяснением; ключи метрик проставляются
   при рендере каждого показателя, METRIC_KB наполняется до полноты.
2. **Не калька бумаги.** 100 % охвата содержимого ОБОИХ отчётов — обязателен,
   но подача — настоящий продуктовый интерфейс: переизобретённые элементы,
   эффективное пространство, интуитивность «для нуба», креатив, seamless.
   Текущая версия честно признана хуже старой страницы по подаче: старая
   была лоскутной, новая — сырой калькой. Обе не годятся как финал.
3. **Визуальное всегда дублируется текстом** (бары — с числами, цвета — с
   подписями): требование доступности и печати (внесено и в DESIGN.md).
4. **Провенанс правок** — «кто что поменял с даты последнего среза», адрес
   ЧЕЛОВЕЧЕСКИЙ: лист · ячейка · название атрибута · было → стало · когда ·
   кто. Бэкенд готов: /api/changes (вкладки _ChangeLog, обе схемы, кэш 5 мин).
   UI — частью нового дизайна, не заплаткой сбоку.
5. **Целостность модуля.** Весь код отчёта (страница + выгрузки) — единая
   архитектура под итоговый результат. После редизайна обязательные проходы:
   /simplify и /code-review по всему модулю.

**Порядок следующего захода:** (1) дизайн-концепция страницы (impeccable
shape: 2–3 непохожих направления, выбор пользователя); (2) реализация
целостного модуля по выбранному направлению; (3) simplify + code-review;
(4) снос старого Report.tsx.
