# Рабочий харнесс AEMR — как принимается любая работа

> Канон п.113 (директива владельца 18.08.2026): «продумывай заранее — и что
> делаешь, и харнесс в подробностях, заранее понимая, что делаешь и что хочешь;
> строй систему, а не плюй в колодец».
>
> Документ обязателен к применению до начала любой волны, задачи или правки.
> Он не про вежливость процесса — он про то, чтобы не делать дважды и не
> оставлять после себя лоскутов.

## 0. Чем вызван

Разбор моих собственных промахов 18.08, каждый — следствие отсутствия харнесса:

| Промах | Что произошло | Чего не хватило |
|---|---|---|
| Самодельный спелчекер | Написал частотный подбор опечаток, потом пошёл искать Hunspell и морфологию | Шага «проверить готовое» ДО начала |
| Вкладка мониторинга | Вывел плоский реестр вместо ста процентов книги | Шага «инвентаризовать источник целиком» ДО проектирования |
| Сигнал «не обеспечено финансированием» | Ловил по производной колонке, обвинял здоровые строки | Шага «сверить канон данных с кодом» после записи канона |
| Метрики-сироты | 23 показателя без родословной дожили до экрана | Правила «метрика без источника не выходит на экран» |
| Управляющие символы в файле | Правка через скрипт записала настоящие backspace вместо escape | Проверки результата правки, а не только тестов |

Общее: работа начиналась с действия, а не с постановки.

## 1. Пять ворот. Работа не начинается, пока не пройдены все

### Ворота 1. Постановка (что и зачем)

Заполняется до первой строки кода:

- **Задача одной фразой** — что изменится для человека, который откроет продукт.
- **Кто читатель** — исполнитель книги, начальник управления, владелец продукта, команда мониторинга. У каждого свой язык и свой уровень подробностей.
- **Источник обязанности** (канон п.104) — из чего следует, что это надо: лист свода, еженедельный отчёт, дополнительный отчёт, книга мониторинга, норма закона, прямое решение владельца с номером пункта канона. **Работа без источника не начинается.**
- **Чего НЕ делаем** — граница задачи, явно.

### Ворота 2. Готовое (канон п.112)

- Что уже есть **в нашем коде**: поиск по репозиторию, реестр модулей, карта метрик. Половина «новых» задач оказывается доделкой существующего.
- Что есть **снаружи**: документация библиотеки через Context7, открытые решения на GitHub, практика в обсуждениях. Проверяются лицензия, вес, живость, поддержка кириллицы.
- **Решение**: берём готовое либо пишем своё — и во втором случае причина пишется в шапке модуля («готовое не подошло, потому что…»).

### Ворота 3. Данные (сто процентов источника)

- Источник **инвентаризуется целиком**, а не выборочно: все листы, все колонки, все формулы, условное форматирование, справочники, защиты, заметки, скрытое.
- Замер делается **на живых данных**, а не на воображаемых: сколько строк подпадает, какие крайние случаи есть, где грязь.
- **Ложные срабатывания ищутся заранее**: прогон по корпусу до того, как правило попало в продукт.

### Ворота 4. Приёмка (чем докажем)

- **Проверяемый признак готовности** — не «сделано», а «на живых данных N находок, из них ложных 0; тесты X зелёные; на экране видно то-то».
- **Страж** — тест, который не даст классу ошибки вернуться. Канон-решение без стража считается незакреплённым.
- **Тексты для человека**: механизм, адрес, действие (п.53), по-русски, без английских слов, без обвинений.
- **Обе темы, узкий экран, пустые состояния** — для всего, что видно на экране.

### Ворота 5. Швы (канон п.108, п.109)

Раздел готов, только когда сшит с продуктом:

- общие фильтры (периметр, год, период) — своих не заводим;
- сквозная навигация — из числа в источник и обратно;
- единый поток замечаний — не отдельный список, а маркировка там, где сущность уже показана;
- общие числа — карта происхождения, единицы, момент чтения;
- владение источником видно (чьи данные, кем ведутся).

## 2. Карточка волны (заполняется до запуска)

```
ВОЛНА: <имя>
Источник обязанности: <канон п.N | лист | отчёт | закон>
Задача: <одна фраза>
Читатель: <кто и что делает после>
Не делаем: <границы>
Готовое: <что взяли снаружи и из своего кода; чего нет и почему>
Данные: <какой источник, инвентаризован ли целиком, замер на живых>
Приёмка: <числа, тесты, стражи, что видно на экране>
Швы: <фильтры, навигация, замечания, числа, владение>
Зоны файлов: <что правим; что НЕ трогаем — занято соседями>
Риски и откат: <что может сломаться, как вернуть>
```

Волна без заполненной карточки не запускается. Карточка живёт в сценарии волны — не в голове.

## 3. Разделение зон между параллельными волнами

- Каждая волна получает **список файлов своей зоны** и **список запретных**.
- Пересечение зон — только через новый файл с чётким контрактом, не через правку общего.
- Общие точки (баррели, словари, реестры) правит **одна** волна за раз; остальные читают.
- При обнаружении, что нужный файл занят: не править, а вернуть в отчёт «требует координации» с точной формулировкой изменения.

## 4. Проверка результата (не только тестами)

- После правки скриптом — **читать файл глазами** (сегодняшний случай с управляющими символами тесты пропустили бы).
- После правила — **прогон по живому корпусу** и разбор первых двадцати находок вручную.
- После экрана — **обе темы, узкий экран, пустое состояние**.
- После числа — **сверка с источником** (лист, отчёт, книга мониторинга).

## 5. Что считается «системой», а не лоскутом

| Лоскут | Система |
|---|---|
| Новый список на новой вкладке | Маркировка в существующем месте + один дом сущности |
| Метрика, посчитанная «потому что можем» | Метрика с источником, единицей, моментом чтения и провенансом |
| Правило без замера | Правило с числом находок и нулём ложных на корпусе |
| Документ в markdown вместо результата | Файл, с которым человек работает: таблица, документ, экран |
| Канон-решение в реестре | Канон-решение + страж в коде + ревизия старого кода на соответствие |

## 6. Ритм

1. **Постановка** (ворота 1–3) — до запуска, письменно.
2. **Волна** — параллельные потоки в своих зонах.
3. **Гейт** — проверка типов и тесты всех пакетов.
4. **Замер** — прогон по живым данным, числа.
5. **Показ владельцу** — что изменилось, с числами и адресами.
6. **Выкат** — после зелёного гейта и показа.
7. **Запись в канон** — решение, страж, ревизия старого кода.

## 7. Правило «не плевать в колодец»

Каждая волна обязана оставить после себя **лучше, чем было, в трёх смыслах**:

- **Данные**: меньше грязи, больше сверок, честнее пустоты.
- **Код**: меньше домов у одного понятия, больше стражей, меньше мёртвого.
- **Понимание**: канон пополнен, карта происхождения пополнена, документ обновлён.

Если волна улучшила одно и ухудшила другое (добавила экран, но развела сущность по трём местам) — она не принята.
