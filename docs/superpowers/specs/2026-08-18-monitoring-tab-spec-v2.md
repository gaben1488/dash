# Мониторинг: спека вкладки на сто процентов книги

Владелец сказал про первую версию вкладки прямо: «тупо реестр закинул как
говно, мол жрите». Претензия верна по существу. Из четырнадцати листов книги
в продукт попали восемь, и те — плоской таблицей: колонка «Победитель»
показана как строка текста, хотя внутри неё живут и наименование поставщика,
и ИНН, и исход процедуры; колонка «Проверка данных» показана как слово
«верно», хотя это готовый сигнал; лист «25-26» с родословной процедур,
свод, справочник учреждений и три листа-предка не показаны вовсе. Ничего
из того, что книга умеет, вкладка не усилила, а часть того, что книга умеет,
потеряла.

Эта спека описывает вкладку, в которой есть всё, что есть в книге, плюс то,
чего книга не умеет: воронка стадий, распределение снижения, портрет
поставщиков и их концентрация, сроки этапов, сезонность, родословная
переобъявлений, построчная сверка с книгами ГРБС и собственный класс
сигналов. Все числа ниже посчитаны по полному дампу и воспроизводимы.

### 1.1. Восемь листов управлений — рабочая форма

Форма у всех восьми листов одна и та же до пикселя: шапка занимает две строки
(одиннадцать объединений `A1:A2`…`H1:H2`, `O1:O2`, `P1:P2`), данные идут с
третьей строки. Тонкость, которую первая версия вкладки прочитала неверно:
подпись «Экономия, руб.» стоит в ячейке `L1` и служит визуальной шапкой всей
группы `J:N`, а не именем колонки L. Настоящие имена читаются во второй
строке.

| Кол. | Имя (строка 1 / строка 2) | Тип | Формула / правило |
|---|---|---|---|
| A | № п/п | число, ручное | нет; сквозной нумерации нет (в УО 1…27 идёт дважды — два годовых блока) |
| B | Заказчик | свободный текст | нет; 71 написание на 374 строки, со справочником совпадают 4 |
| C | Наименование объекта закупки | текст | нет; код процедуры приклеен к началу предмета |
| D | Начальная (максимальная) цена, руб. | число | нет; местами текст (неразрывные пробелы, точка вместо запятой) |
| E | Дата поступления заявки в УО | дата | нет |
| F | Дата публикации | дата | нет |
| G | Дата окончания подачи заявок | дата | нет |
| H | Дата проведения торгов/переторжки | дата | нет |
| I | Цена аукциона, руб. | число | нет; 0 — торги без результата, пусто — итога ещё нет |
| J | Экономия · ВСЕГО | число | `=ОКРУГЛ(D−I;3)` — 348 формул на восьми листах, 25 ячеек забиты руками |
| K | Экономия · Проверка данных: сумма ВСЕГО и МБ+КБ+ФБ | текст | `=ЕСЛИ(СУММ(L:N)=J;"верно";"ошибка")` — 374 формулы |
| L | Экономия · МБ | число | нет |
| M | Экономия · КБ | число | нет |
| N | Экономия · ФБ | число | нет |
| O | Победитель | текст | нет; внутри ячейки — наименование, перевод строки, «ИНН …» |
| P | Комментарий | текст | нет; заполнена шесть раз на всю книгу |

Три вещи здесь принципиальны для продукта. Первая: **разбивка МБ/КБ/ФБ —
это разбивка экономии, а не НМЦК**. Контроль сравнивает `L+M+N` с `J`, то есть
проверяет, что сэкономленные деньги расписаны по бюджетам. Вторая: **колонка
«Победитель» — составная**. В 340 ячейках имя и ИНН разделены переводом
строки `\n`, в семи — парой `\r\n` (вставка из другого источника); в одной
ячейке ИНН повторён дважды. Третья: **в той же колонке живут исходы**: «Не
состоялся (0 заявок)» встречается 21 раз, «Размещение повторное (не прошёл
контроль в УФК)» — один раз, и есть строки, где ИНН просто забыли.

Условное форматирование на каждом листе — ровно два правила, оба на колонку K:
текст равен «верно» → фон `#38761D`, белый шрифт; текст равен «ошибка» → фон
`#990000`, белый шрифт. Диапазоны правил обрезаны по числу заполненных строк
(`K3:K44` в УЭР, `K3:K27` в УКСиМП и УАГиЗО, `K3:K34` в УИО и УДТХиРКИ,
`K3:K108` в УД, `K3:K6` в УФБП, `K3:K110` в УО), поэтому каждая новая строка
требует ручного растягивания. У листа УО есть третье правило — градиент на
одной ячейке `O109`, остаток былого итога.

Проверок ввода в книге нет ни одной. Защищённых диапазонов нет ни одного.
Заметок нет ни одной. Скрытых строк на листах управлений нет. Автофильтр
стоит на `A1:P2` у шести листов, у УД на `A1:P108`, у УО на `A1:P104`.

### 1.2. Лист «СВОДНЫЙ» — итог, который занижен

Свод — таблица девять на восемь: строка 1 занята объединённым заголовком
«Общая информация по проведённым ЭА в рамках реализации МП (без текущей
деятельности)», строки 2–3 держат двухэтажную шапку, строки 4–11 — восемь
управлений, строка 12 — «Итого:». В ячейке `C14` живёт пояснение автора книги:
«Ячейка считает количество непустых строк (не путать с ненулевыми) в столбце
"Цена аукциона, руб."».

Формулы одинаковы по смыслу: `C = СЧЁТЕСЛИ('лист'!I3:I1000;"<>"&"")`,
остальные — `СУММ` по колонкам D, I, J, L, M, N соответствующего листа.
Границы диапазонов разъехались лесенкой (`J3:J1001`, `J3:J1002`, … `J3:J1007`)
— след протяжки формулы вниз; сегодня на итог не влияет, при дозаполнении
листов начнёт.

Итог свода: 372 процедуры, НМЦК 1 257 371 242,29, цена аукциона
1 082 073 223,20, экономия ВСЕГО 116 830 490,23, из неё МБ 62 832 012,17,
КБ 21 593 656,75, ФБ 23 403 238,58.

Здесь два расхождения, которые продукт обязан показать, а не сгладить.
Первое: **свод недосчитывает 73 970 897,35 рублей НМЦК**. Ячейка
`5. УДТХиРКИ!D34` (процедура ЭА291-26) хранится текстом, `СУММ` её не видит.
Наш парсер видит, поэтому продуктовая сумма НМЦК — 1 331 342 139,64, а разница
между ней и цифрой свода в точности равна этой одной ячейке плюс 25 333,28 по
строке `6. УД!D91`, у которой нет цены. Второе: **экономия не сходится с
разбивкой по бюджетам**. `F12` = 116 830 490,23, а `G12+H12+I12` =
107 828 907,50; разрыв 9 001 582,73 рубля не показан на своде никак, потому
что контрольной колонки на своде нет. По управлениям он собирается из УД
(4 115 635,90), УФБП (21 638,94) и УО (4 864 307,89).

Ещё одна мелочь с последствиями: **на своде управления названы третьим
способом** — «УЭР АЕМР», «УАГЗО АЕМР», «УДТХ АЕМР». Имя листа («4. УАГиЗО»),
имя на своде («УАГЗО АЕМР») и канонический ид продукта («УАГЗО») — три разных
написания одного управления, и связывать их надо явной таблицей, а не
подстрокой.

### 1.4. Справочник «Перечень ГРБС» и его скрытый близнец «ГРБС»

Семьдесят пять строк, четыре колонки: `A` номер, `B` ГРБС-владелец,
`C` «Наименованиеучрежения» (опечатка в шапке), `D` «Сокращеное наименование
учреждения» (вторая опечатка). Распределение по управлениям: УО 43,
УКСиМП 22, по два у УАГиЗО, УД, УЭР и УДТХ, по одному у УИО и УФБП.

Справочник наполовину не работает. У **35 строк из 75** (адреса 9–43) колонка
сокращённого наименования дословно повторяет полное: «муниципальное бюджетное
дошкольное образовательное учреждение „Детский сад № 11 „Умка“» вместо
«МБДОУ „Детский сад № 11 „Умка“». В перечне правок к книге этот дефект назван
на одиннадцати адресах — строгое сравнение строк даёт тридцать пять. Ещё у
четырёх строк пусто полное наименование.

Лист «ГРБС» (скрытый) — побайтовая копия «Перечня ГРБС», включая обе опечатки
в шапке. Два источника одного справочника разойдутся при первой же правке
одного из них.

Практический вывод для продукта: **справочник сегодня почти не связан с
книгой**. Из 71 написания заказчика на листах управлений точное совпадение со
справочником (по полному или сокращённому имени) находят четыре. «УД АЕМР»
(52 строки), «УИО АЕМР» (31), «УДТХиРКИ» (27), «МКУ ЕРУС» (22) — это сами
управления и казённые учреждения, которых в справочнике нет; «МБОУ ЕСШ №1
им. М.В. Ломоносова» и «МБОУ „ЕСШ №1 ИМЕНИ М.В.ЛОМОНОСОВА“» — одна школа,
записанная двумя способами; «Совместный аукцион ШКОЛЫ», «Совместные ШКОЛЫ»,
«Совместный аукцион Д.САДЫ+ШКОЛЫ» — вообще не учреждение, а признак
совместной закупки, попавший в колонку заказчика.

### 1.5. Три скрытых листа-предка

«Отчет по процедурам Свод» и «СВОД» пусты: в обоих только шапка из семнадцати
колонок и ноль строк данных. Шапка при этом богаче нынешней рабочей формы, и
именно поэтому листы нельзя выбрасывать не глядя — это память о полях,
которых продукту сегодня не хватает:

`№ п/п` · `Наименование муниципальной программы` · `Общий объём ассигнований,
с учётом тек. деятельности (М.б., К.б., Ф.б.)` · `Остаток не принятых
(свободных) бюджетных обязательств` · `Заказчик` · `Наименование объекта
закупки` · `Начальная (максимальная) цена` · `Дата поступления заявки в УО` ·
`Дата публикации` · **`Статус`** · `Дата окончания подачи заявок` ·
**`Дата окончания срока рассмотрения заявок`** · `Дата проведения
торгов/переторжки` · **`Кол-во заявок от поставщиков`** · `Цена аукциона` ·
`Экономия` · `Победитель`.

Три поля выделены не случайно. «Статус» — то, что сегодня растворено в
колонке A листа «25-26». «Дата окончания срока рассмотрения заявок» — этап,

## §2. Что показываем: перенос формы книги

Правило переноса одно: **у каждого листа книги есть свой режим на вкладке**,
и в этом режиме лист узнаётся глазами. Читатель, открывший вкладку, должен
сказать «это мой лист УО», а не «это какая-то таблица про закупки».

### 2.1. Режим «Лист управления»

Восемь листов — восемь вкладок второго уровня плюс режим «все восемь сразу».
Таблица повторяет книгу колонка в колонку и в том же порядке, с двухэтажной
шапкой: над `J…N` стоит объединённая подпись «Экономия, руб.», под ней —
«ВСЕГО», «Проверка», «МБ», «КБ», «ФБ». Это не украшение: без надшапки читатель
не поймёт, что МБ/КБ/ФБ относятся к экономии, а не к НМЦК, — ровно та ошибка,
которую сделала первая версия вкладки.

Колонки, которые продукт показывает иначе, чем книга, и почему:

**Колонка C** разбирается на код процедуры и предмет. Код — моноширинный
бейдж со способом определения поставщика («ЭА» — электронный аукцион,
«ЭАС» — совместный, «ЭЗК» — запрос котировок, «ЭЕП» — единственный
поставщик), предмет — обычным текстом. Код не разобрался — строка остаётся в
реестре, а её адрес уходит в сигнал; молча чинить искажение нельзя.

**Колонка O/K «Победитель»** разбирается на три части: наименование, ИНН
(кликабельный — копируется одним нажатием), исход. Если ИНН нет, а текст
похож на исход («Не состоялся», «Размещение повторное»), продукт показывает
его как исход, а не как поставщика, — но не переписывает: исходный текст
доступен по наведению. Интерпретации текста как источника статуса нет
(п.27): стадия по-прежнему считается по числам.

**Колонка K «Проверка данных»** превращается из слова в значок с объяснением.
«Верно» — тихая зелёная точка, «ошибка» — красная точка с подсказкой:
«экономия 441,00 руб. не расписана по бюджетам: МБ+КБ+ФБ = 0». Красное красим
только там, где книга сама краснеет: продукт не изобретает новых поводов
для тревоги в этой колонке.

**Колонка A «№ п/п»** показывается вместе с номером строки листа — двойной
адрес «строка 34 · № 32», как уже принято на других вкладках. В УО, где
нумерация 1…27 идёт дважды, без номера строки ссылка неоднозначна.

Под таблицей — итоговая строка листа: количество, НМЦК, цена, экономия,
разбивка по бюджетам. Ровно те шесть чисел, которые лист отдаёт своду, и
рядом — то же число, как его видит свод. Расходятся — показываем оба и
объясняем причину.

### 2.2. Режим «Сводный»

Свод книги воспроизводится один в один: восемь строк управлений и «Итого»,
колонки «Кол-во», «НМЦК», «Цена аукциона», «Экономия ВСЕГО / МБ / КБ / ФБ».
И три вещи, которых на своде книги нет.

Во-первых, **колонка контроля**, которой книге не хватает: «ВСЕГО = МБ+КБ+ФБ»
по каждой строке и по итогу. Сегодня она сразу покажет три красных строки —
УД, УФБП, УО — и разрыв 9 001 582,73 рубля по итогу.

Во-вторых, **две колонки вместо одной там, где свод и лист расходятся**:
«как считает книга» и «как считает продукт». По УДТХиРКИ это 229 452 023,50
против 303 422 920,85, и подпись объясняет разницу одной фразой: сумма
процедуры ЭА291-26 записана в книге текстом, и формула `СУММ` её не видит.
Это и есть ответ на вопрос «почему у вас другие цифры» — заданный заранее.

В-третьих, **счётчик процедур честный**: свод считает непустые ячейки цены
(372), продукт считает строки (374) и рядом объясняет разницу — две строки
цены не имеют вовсе.

### 2.3. Режим «Переходящий реестр 25-26»

Лист «25-26» получает собственный режим, потому что несёт то, чего нет на
листах управлений: победителя и ИНН по процедурам, которых на листах ещё нет,
и родословную. Форма — та же таблица, но с двумя добавленными колонками
слева от предмета: «Судьба» (бывшая колонка A, разобранная на словарь) и
«Связь» — стрелка на процедуру-предшественницу или преемницу.

Родословная показывается двумя способами. В таблице — стрелка со ссылкой:
нажатие на «ЭА52-26 → ЭА91-26» открывает обе строки рядом. В карточке
процедуры — цепочка целиком: ЭА52-26 (отменена) → ЭА91-26 (после доработки) →
ЭА119-26 (после доработки), с датами и НМЦК каждого захода. Это отвечает на
вопрос, который сегодня не задаётся, потому что данных для него не видно:
сколько времени и денег стоит один круг переобъявления.

Скрытые в книге 201 строка **показываются**, но помечаются: «скрыта в книге».
Прятать данные, которые участвуют в расчётах, продукт не должен; молча
показывать то, что человек спрятал, — тоже. Переключатель «показывать
скрытые» стоит рядом, по умолчанию включён.

Строки 376–392, выпавшие из автофильтра книги, отмечаются подписью «вне
области фильтра книги»: в самой книге эти семнадцать процедур человек при
работе с фильтром не увидит.

### 2.4. Режим «Справочник учреждений»

Семьдесят пять строк справочника показываются как есть, с колонкой
«ГРБС-владелец», и с двумя добавленными колонками. Первая — «встречается в
книге»: сколько строк реестра ссылается на это учреждение (точным
совпадением либо нормализованным). Вторая — «сокращение»: там, где сокращённое
наименование дословно повторяет полное, стоит честная пометка «сокращения
нет» вместо длинного текста, притворяющегося коротким.

Отдельным блоком под справочником — **список написаний заказчика, которых в
справочнике нет**: 67 из 71, отсортированные по частоте. Это рабочий
инструмент: по нему отдел за один заход приведёт написания к одному виду, а
продукт получит возможность группировать закупки по заказчику.

### 2.5. Режим «Листы-предки»

Скромный, но обязательный блок: два пустых листа с их семнадцатью колонками
и подписью, каких полей не хватает нынешней форме — статуса, даты окончания
рассмотрения заявок, количества заявок от поставщиков, муниципальной
программы, объёма ассигнований и остатка непринятых обязательств. Это не
данные, это память о форме; она нужна при разговоре с владельцем о том, что
вернуть в книгу.

### 2.6. «Смотреть по-разному»: восемь разрезов

Канон п.101а требует не «переключатель листов», а возможность смотреть на
один и тот же реестр разными глазами. Разрезы применяются к любому режиму и
комбинируются:

**По управлению** — восемь листов плюс «все»; помнит, что одна и та же
процедура-совместная закупка живёт на нескольких листах, и не двоит деньги
в режиме «все» (совместные помечаются, доли складываются с оговоркой).

**По стадии** — заявка · опубликована · торги прошли · договор заключён ·
без результата. Стадия считается по числам и датам, не по тексту.

**По способу определения поставщика** — ЭА (269 процедур на листах
управлений), ЭЕП (40), ЭЗК (33), ЭАС (28). Разрез отвечает на вопрос
начальства «сколько у нас конкурентных процедур»: снижение по ЭА и по ЕП —
разные явления, складывать их в один средний процент бессмысленно.

**По кварталу и месяцу** — по дате публикации либо по дате торгов, на выбор.
Обе даты содержательны, и подмена одной другой меняет картину.

**По заказчику** — с группировкой по нормализованному имени и честной
пометкой, что нормализация — наша, а не книги.

**По победителю** — по ИНН, а не по написанию наименования: 191 уникальный
ИНН на 347 побед.

**По размеру НМЦК** — пять корзин: до 100 тыс. (90 процедур), 100–600 тыс.
(122), 0,6–3 млн (66), 3–20 млн (86), свыше 20 млн (10). Разрез нужен потому,
что снижение на мелких и крупных закупках ведёт себя по-разному, и общий
средний процент их смешивает.

**По году процедуры** — по суффиксу кода: 2026 год — 305 процедур,
2025 — 67. Книга переходящая, и без этого разреза «итог года» невозможен.

## §3. Собственная аналитика: чего книга не умеет

Всё в этом разделе книга не считает и посчитать не может. Все числа — по
дампу на 18.08.2026, восемь листов управлений (374 строки), если не сказано
иное.

### 3.1. Воронка стадий с конверсией

Пять ступеней: заявка поступила → опубликована → торги состоялись → есть цена
победителя → экономия расписана по бюджетам. Заполненность колонок книги на
сегодня: дата заявки 371, дата публикации 369, дата окончания подачи 358,
дата торгов 367, цена 372, победитель 374 из 374.

Стадия по числовым предикатам: договор заключён (цена > 0 и ИНН победителя
разобран) — 347, торги прошли без результата или итог не внесён — 26,
процедура только объявлена — 1. По листу «25-26» та же воронка выглядит
иначе: 337 · 40 · 14, и это правильная разница, а не ошибка: переходящий
реестр ведёт процедуры раньше, чем они попадают на лист управления.

Конверсия показывается между ступенями, а не только итогом: «из 374 заявок до
цены победителя дошли 347 — 92,8 %; сорвались либо ждут 27». Ступень, на
которой процедура стоит дольше медианы, подсвечивается.

### 3.2. Распределение снижения на торгах — фундамент живого коэффициента

Это главная аналитика вкладки, потому что из неё родится ответ на вопрос,
который начальство задаёт постоянно: «а сколько мы обычно экономим на торгах».
Ответов оказывается три, и они отвечают на разные вопросы. Показывать надо
все три и подписывать, чем они отличаются.

| Коэффициент | Значение | На какой вопрос отвечает |
|---|---|---|
| Портфельный: (Σ НМЦК − Σ цена) ÷ Σ НМЦК по состоявшимся | **9,74 %** | на сколько подешевел весь портфель денег |
| Среднее построчных процентов по всем состоявшимся | **15,84 %** (медиана 0,50 %) | как ведёт себя типичная процедура, включая те, где снижения не было |
| Среднее по тем, где снижение вообще было | **29,10 %** (медиана 26,34 %; квартили 5,70 и 45,68) | насколько падает цена, когда торги реально идут |

Разброс между 9,74 и 29,10 объясняется одним фактом, который книга не
показывает: **из 351 состоявшейся процедуры у 160 цена в точности равна НМЦК**
— это 45,6 %. Почти половина торгов проходит без единого шага снижения.
Медиана по всем состоявшимся (0,50 %) именно поэтому почти нулевая.

Гистограмма — семь корзин по проценту снижения:

| Снижение | Процедур |
|---|---|
| ровно 0 % | 160 |
| 0–1 % | 19 |
| 1–5 % | 27 |
| 5–10 % | 15 |
| 10–25 % | 31 |
| 25–50 % | 57 |
| свыше 50 % | 42 |

Форма распределения двугорбая: огромный столб на нуле и второй горб в зоне
25–50 %. Это не шум, это два разных мира — процедуры с одним участником и
процедуры с реальной конкуренцией. Гистограмма делается кликабельной: нажатие
на корзину отбирает её строки в таблице.

### 3.7. Сравнение управлений

Кроме таблицы из §1.1, вкладка даёт сравнение по нормированным величинам,
иначе УО с 108 процедурами всегда «лучший», а УФБП с четырьмя — всегда «худший».
Сопоставляются: процент экономии (от 1,15 % у УИО до 31,50 % у УАГиЗО),
доля процедур с реальным снижением, доля несостоявшихся, медианный срок
«заявка → торги», доля строк со статусом «ошибка», доля строк, где экономия
не расписана по бюджетам.

Крайности объясняются, а не выставляются оценкой. УИО с 1,15 % ведёт
приобретение квартир, где снижения нет по природе предмета. УАГиЗО с 31,50 %
ведёт мелкие услуги проектирования, где падение цены вдвое — обычное дело.
Тон — объяснение механизма (п.104), не упрёк.

**Нулевая цена при заполненных датах торгов** — 21 строка, см. §3.6.

**Дубли кода процедуры внутри одной книги.** На листах управлений один и тот
же код встречается дважды: ЭА363-25, ЭА166-26, ЭА241-26 (по два раза),

## §4. Сверка с книгами ГРБС — по каждой строке

Канон п.101а требует маппинга по каждой строке, а не сводного процента.
Механика связки уже есть в ядре (`packages/core/src/pipeline/monitoring-match.ts`,
305 строк, покрыт тестами) и сегодня не вызывается ниоткуда. Задача этой
волны — довести её до экрана.

### 4.1. Ключ и единицы

Ключ — канонический код процедуры. В книге мониторинга он приклеен к началу
колонки C; в книгах ГРБС живёт в колонке AG. Обе стороны нормализуются одним
парсером `extractProcedureRefs` из `@aemr/shared` — второго парсера быть не
должно.

Единицы: книги ГРБС хранят тысячи рублей, мониторинг — рубли. Множитель один
и живёт в `THOUSANDS_TO_RUB`. Порог согласия сумм — 1 %: K книги хранится с
точностью до 0,01 тыс. (десяти рублей), поэтому честное «то же самое число»
после перевода расходится на копейки, а лимит против НМЦК — на проценты.

### 4.2. Что именно сверяем

Три сверки на строку:

**НМЦК ↔ план.** `K` книги × 1000 против колонки D мониторинга. Это проверка
канона п.102: исполнители начали писать в плановые колонки НМЦК из заявок
вместо лимитов бюджетных обязательств. Где сходится — практика «пишут НМЦК»
подтверждена данными; где не сходится — либо старая семантика лимита (УДТХ
прямо говорит, что расписывает лимиты), либо третья семантика УКСиМП, где из
плана задним числом вычитают изъятую экономию.

**Цена победителя ↔ факт.** `Y` книги × 1000 против колонки I мониторинга.
Расхождение здесь означает либо незавершённый контракт, либо ошибку в одной
из книг.

**Даты.** Дата торгов мониторинга против даты заключения договора книги.
Договор раньше торгов — невозможен; разрыв больше месяца — повод посмотреть
(четыре такие пары уже найдены: `6. УД!H19`, `H22`, `8. УО!H35`,
`5. УДТХиРКИ!H8`).

### 4.3. Классы исходов

Словарь закрытый — свободного текста в исходах нет.

| Исход | Смысл | Что делать читателю |
|---|---|---|
| `matched` | один код — одна строка книги — одна процедура; суммы сверены | ничего, если суммы согласны |
| `code-in-book-not-in-monitoring` | в книге ГРБС код есть, в мониторинге такой процедуры нет | процедура не заведена в мониторинг либо код искажён с одной стороны |
| `monitoring-without-book-row` | процедура есть, строки плана нет | закупка идёт вне плана либо номер не проставлен в книге |
| `ambiguous` · разные книги | один код в нескольких книгах ГРБС | норма для совместной закупки (ЭАС): каждое управление ведёт долю |
| `ambiguous` · одна книга | один код дважды в одной книге | аномалия заполнения, сигналить |
| `listCell` | ячейка AG со списком кодов, одна плановая строка на несколько процедур | парная сверка сумм невозможна, но коды закрыты от класса «без строки книги» |

Покрытие связки на дату замера — 87,4 % строк находят пару. Каждая
исправленная опечатка в коде добавляет к этому конкретную процедуру с
конкретными деньгами.

## §5. Сигналы мониторинга: свои, из дефектов книги

Каждый сигнал оформляется карточкой диагноста по п.53: **механизм** (почему
так вышло), **адрес** (лист, строка, ячейка), **действие** (что сделать).
Тон — объяснение, не упрёк (п.104). Сигналы этой вкладки живут в своём
пространстве имён `monitoring_*` и не смешиваются с сигналами книг ГРБС.

**Сумма записана текстом.** Механизм: значение вставлено из Word или площадки
с неразрывным пробелом либо точкой вместо запятой; на экране выглядит числом,
формулой `СУММ` не считается, поэтому свод занижен. Адрес: `5. УДТХиРКИ!D34`
и `25-26!D357` (73 970 897,35 — одна ячейка на семьдесят четыре миллиона),
`25-26!D242`, `25-26!I307`, плюс 43 ячейки с неразрывными пробелами и девять
ячеек `25-26!D14`–`D22`. Действие: перезаписать числом; после этого итог свода
вырастет — предупредить получателей отчёта. Критичность: высшая.

**Пробел вместо числа.** Механизм: ячейка выглядит пустой, но хранит один
пробел; попадая в разбивку МБ/КБ/ФБ, ломает контроль. Адрес: десять ячеек,
среди них `5. УДТХиРКИ!M33`, `N33`, `25-26!M39`, `J213`, `M276`. Действие:
очистить либо поставить ноль.

**Код процедуры искажён.** Механизм: код набирается руками в начале текста
предмета, и опечатка рвёт связь с книгами ГРБС. Пять паттернов, все
подтверждены встречной строкой в книге ГРБС: потеряна буква (`А427-25` вместо
`ЭА427-25`), лишний дефис (`ЭЗК-120-26`), год из трёх цифр (`ЭА146-226`),
неверный год (`ЭА04-25` при процедуре 2026 года), перепутанный префикс
(`ЭКЗ301-26`, `ЭЗЗК01-26`, `ЭК03-26` — во всех трёх имелось в виду `ЭЗК`).
Плюс склейка кода с предметом без пробела и двойные пробелы после кода.
Действие: адрес и предлагаемое написание; исправление — в книге, руками
владельца, продукт не чинит молча.

**Экономия внесена вручную.** Механизм: формула `=ОКРУГЛ(D−I;3)` считает
экономию даже когда цена аукциона равна нулю, поэтому сотрудник забивает ноль
руками; связь с исходными ячейками рвётся, и при изменении НМЦК экономия не
пересчитается. Адрес: 25 ячеек на листах управлений (`1. УЭР!J43`, `J44`,
`3. УИО!J3`, `J32`, `8. УО!J100` и другие) и 164 на листе «25-26». Действие:
показать как «внесено вручную», не как ошибку; предложение по книге —
защищённая формула, которая молчит при незаполненной цене.

**Контроль книги показывает «ошибка».** Механизм: экономия не расписана по
бюджетам, `МБ+КБ+ФБ ≠ ВСЕГО`. Адрес: 29 строк — УО 19, УД 8, УФБП 2.
Действие: заполнить разбивку; данные знает исполнитель, машинно не
восстанавливаются. Это единственный сигнал, который книга поднимает сама, —
продукт его лишь переносит и суммирует до свода.

**Экономия свода не сходится с разбивкой.** Механизм: контроля на своде нет
вовсе, поэтому разрыв невидим. Адрес: `СВОДНЫЙ!F12` против `G12+H12+I12`,
разрыв 9 001 582,73 рубля. Действие: добавить контрольную колонку на своде
книги; на вкладке она уже есть.

**Дата записана текстом или невозможна.** Механизм: опечатка в наборе даты
(`23.062026`, `15.0.12026`, `03.06.25026`, `11.08.0206`) превращает дату в
текст; строка выпадает из сортировки, отбора по периоду и расчёта сроков
молча. Адрес: двенадцать ячеек, из них подтверждены `4. УАГиЗО!G20`–`G22`,
`6. УД!G26`, `G100`, `25-26!G63`–`G65`, `25-26!F388`. Отдельно — двенадцать
процедур с отрицательной длительностью этапа. Действие: перезаписать датой.

**Пропущенный этап.** Механизм: процедура прошла торги, но не имеет даты
публикации либо окончания подачи — путь неполон. Адрес: двенадцать строк, где
дата торгов есть, а даты окончания подачи заявок нет, и одна, где нет даты
публикации; всего по книге не заполнены 16 дат окончания подачи и 5 дат
публикации. Действие: дозаполнить.

**Ложно-успокаивающая строка.** Механизм: цена и экономия пусты, контроль
сравнивает ноль с нулём и показывает зелёное «верно» — незавершённая
процедура выглядит проверенной. Адрес: `6. УД!I91`, `J91`, `K91` при
`D91` = 25 333,28 и пустой дате публикации. Действие: заполнить цену либо
пометить строку незавершённой.

**Расхождение с книгой ГРБС** и четыре остальных сигнала маппинга — см. §4.5.

**Заказчик не найден в справочнике.** Механизм: колонка заказчика —
свободный текст, проверки ввода нет; 67 написаний из 71 в справочнике не
находятся. Действие: список написаний с частотой, чтобы отдел свёл их к
одному виду. Критичность низкая, но без этого разрез «по заказчику» неполон.

**Процедура сорвалась, преемница не найдена.** Механизм: цена ноль либо
статус «отменена», а ссылки на новую процедуру в колонке A листа «25-26» нет.
Действие: посмотреть, чем кончилось.

## §6. Макет экрана

### 6.1. Порядок блоков сверху вниз

**Шапка вкладки.** Название — «Мониторинг · Реестр процедур определения
поставщика» (п.101а, дословно). Под ним — плашка периметра: книга-источник,
момент чтения («данные книги на 18.08.2026, 14:05»), единица денег («рубли;
книги управлений ведутся в тысячах»), оговорка, что глобальные фильтры шапки
приложения к этой книге не применяются. Кнопка обновления справа. Плашка
периода (`PeriodBadge`) стоит **у каждого блока чисел ниже**, не только в
шапке — период у разных блоков разный (реестр — на момент чтения, сезонность
— по дате публикации, сверка — по датам обеих книг).

**Полоса состояния книги.** Одна строка: сколько листов прочитано из
четырнадцати, сколько строк, сколько сигналов по классам. Лист не прочитан —
называется поимённо, и счётчики честно объявляются неполными. Это не
«ошибка», это состояние источника.

**Шесть чисел портрета.** Процедур в реестре · НМЦК · цена контрактов ·
экономия на торгах · процент снижения (портфельный, с раскрытием до трёх
коэффициентов из §3.2) · процедур без результата. Каждое — с подсказкой
`KBTooltip`, объясняющей формулу и подводные камни. Пустых нулей нет: нет
данных — так и написано (п.36).

**Воронка стадий.** Горизонтальная, пять ступеней с конверсией между ними.
Клик по ступени отбирает её в таблице ниже.

**Панель разрезов.** Восемь переключателей из §2.6 плюс поиск по коду,
предмету, заказчику и ИНН победителя. Выбранные разрезы показываются
хлебными крошками с крестиками — как на других вкладках.

**Режимы листов.** Ряд вкладок второго уровня: «Все управления» · восемь
листов · «Сводный» · «25-26» · «Справочник» · «Листы-предки». Выбранный режим
меняет таблицу ниже, разрезы сохраняются.

**Таблица реестра.** Форма листа книги с двухэтажной шапкой (§2.1).
Виртуализация от 200 строк. Строка раскрывается в карточку.

**Карточка процедуры** (раскрытие строки, не модальное окно). Слева — путь:
пять дат с интервалами в днях и подсветкой этапа, выбившегося из медианы.
В центре — деньги: НМЦК, цена, снижение в рублях и процентах, разбивка
экономии по бюджетам с контролем. Справа — победитель: наименование, ИНН,
исход. Ниже — три полосы: родословная (цепочка переобъявлений с листа
«25-26»), сверка с книгой ГРБС (план, факт, вердикт по каждой из трёх
сверок), сигналы этой строки карточками диагноста.

**Аналитика** — четыре графика, каждый со своей плашкой периода:
гистограмма снижения (кликабельная), столбики сезонности по месяцам,
«ящик с усами» по срокам этапов, сравнение управлений по нормированным
величинам. Ниже — два блока-списка: топ поставщиков (переключатель
«по деньгам / по числу побед») с полосой концентрации, и повторяющиеся пары
«поставщик — заказчик».

**Сверка с книгами ГРБС** — таблица классов исходов со счётчиками и
раскрытием в список адресов; отдельно — внутренняя сверка «лист ↔ 25-26» с
шестью расхождениями сумм.

**Сигналы** — карточки диагноста, сгруппированные по критичности; в каждой
механизм, адреса (сворачиваемый список), действие.

**Что осталось за кадром** — короткий честный блок, §7.

### 6.2. Цвет, тон, пустоты

Фон кремовый и спокойный, цвет несут только данные. Зелёное и красное
употребляются ровно там, где краснеет и зеленеет сама книга (контроль
`K`), и на светофоре сигналов. Графики — echarts, как на соседних вкладках,
цвета из `lib/chart-colors` (категориальная палитра для управлений и
поставщиков, закреплённая тройка ФБ/КБ/МБ для бюджетов — их нельзя путать),
тултипы через `getTooltipStyle`. Тёмная тема читается: проверяется на всех
графиках и на таблице.

Честные пустоты вместо нулей: «книга не прочитана», «в книге нет процедур
под выбранные разрезы» и «фильтры всё срезали» — три разных экрана с разными
словами и разными кнопками. Ноль в цене аукциона — не пустота, а содержание
(«торги без результата»), и его нельзя показывать прочерком.

Ни одного упрёка в подписях. «Экономия внесена вручную — формула на этой
строке разорвана, при изменении НМЦК число не пересчитается» — так. «Ошибка
заполнения» — нет.

### 6.3. Мобильный вид

Таблица реестра на узком экране превращается в список карточек: код и
способ бейджем, предмет двумя строками с многоточием, НМЦК и цена в столбик,
стадия значком. Раскрытие карточки — тот же состав, но вертикально:
путь → деньги → победитель → родословная → сверка → сигналы.

Панель разрезов сворачивается в один выпадающий список с числом выбранных
фильтров на кнопке. Ряд режимов листов — горизонтальная прокрутка с
липким первым элементом.

Из четырёх графиков на узком экране остаются два: гистограмма снижения и
сезонность (оба хорошо читаются в высоту 220 пикселей). «Ящик с усами» и
сравнение управлений сворачиваются в раскрывающийся блок «Ещё графики» —
они требуют ширины, и растянутые на 375 пикселей врут глазу. Таблицы сверки
и справочника получают горизонтальную прокрутку внутри своего контейнера;
корпус страницы горизонтально не едет никогда.

Шесть чисел портрета выстраиваются в сетку два на три. Плашка периметра
складывается в две строки. Проверяется тестом ширины, как принято на
остальных вкладках.

## §7. Что остаётся за кадром и почему

**Количество заявок от поставщиков.** Единственная величина, по которой
конкуренцию можно измерить прямо, а не выводить из текста. В нынешней форме
книги её нет — она осталась в шапке скрытого листа-предка. Пока её нет,
конкуренция оценивается косвенно: по факту снижения и по тексту «Не
состоялся (0 заявок)». Это оценка, и подписывать её надо как оценку.

**Дата окончания срока рассмотрения заявок.** Тот же случай: этап есть в
жизни, поля в книге нет. Воронка из-за этого имеет пять ступеней вместо
шести, и разрыв между окончанием подачи и торгами включает в себя
рассмотрение, которое не видно отдельно.

**Статус процедуры как поле.** Сегодня он растворён в колонке номера листа
«25-26» и существует только для 53 строк из 391. Продукт разберёт эти 53,
но выдавать разбор за полную картину статусов нельзя.

**Муниципальная программа и объём ассигнований.** Есть в шапке листов-предков,
нет в рабочей форме. Без них вкладка не может сказать, к какой программе
относится процедура, — а это ровно тот разрез, которого ждёт начальство.
Связь можно тянуть через книги ГРБС по коду процедуры, но только для тех
87,4 %, что нашли пару.

**Единица закупки в лоте.** Дробный номер `ЭАС205/1-26` встречается в книге
ровно один раз. Парсер его понимает, но строить на одном случае разрез
«по лотам» нельзя.

**Выбор правой стороны при расхождении.** Продукт называет расхождение и его
размер — и не выбирает, какая книга права. Это решение человека: и по
шести расхождениям «лист ↔ 25-26», и по семантике плановых колонок книг ГРБС
(п.102: три разные семантики K в восьми книгах), и по совместной закупке
ЭАС258-26, где одно управление показало сумму всей закупки, а пять — свои доли.

**Правка книги.** Вкладка ничего в книге не меняет. Список из сорока правок
согласуется отдельно (`2026-08-18-monitoring-edit-proposal.md`), а продукт
живёт с книгой как она есть: занижение свода на 73,97 млн и завышение на
34,64 млн из-за пяти задвоенных строк он показывает, а не исправляет.

**Скрытые листы-предки.** Показываются как форма, но не как данные — данных
там ноль.

## §8. План реализации на три параллельных агента

Зона волны: `packages/core/src/monitoring/*`,
`packages/core/src/pipeline/monitoring-match.ts`,
`packages/server/src/{services,routes}/monitoring.ts`,
`packages/web/src/pages/Monitoring.tsx`,
`packages/web/src/components/monitoring/*` (новая),
`packages/web/src/lib/monitoring/*` (новая).

### Агент А — ядро и сервер

Читает всю книгу, а не восемь листов: в `MONITORING_DEPT_SHEETS` добавляются
`СВОДНЫЙ`, `25-26`, `Перечень ГРБС`; сервис `services/monitoring.ts` читает их
той же трубой с тем же поведением при отказе листа.

Новые модули ядра: `monitoring/svod.ts` (разбор свода, контроль
`ВСЕГО = МБ+КБ+ФБ` по строкам и итогу, сопоставление «как считает книга ↔ как
считает продукт»); `monitoring/journal.ts` (лист «25-26»: разбор колонки A на
словарь судьбы и граф родословной `code → code`, флаг скрытой строки, флаг
«вне области фильтра»); `monitoring/directory.ts` (справочник, нормализация
имени заказчика, класс «сокращения нет», список написаний вне справочника);
`monitoring/winner.ts` (разбор ячейки победителя на имя, ИНН, исход — с
поддержкой `\n` и `\r\n` и склеенных повторов); `monitoring/analytics.ts`
(воронка с конверсией, три коэффициента снижения, гистограмма по семи
корзинам, топ поставщиков и концентрация по деньгам и по числу, пары
«поставщик — заказчик», сроки этапов с квартилями, сезонность по месяцам и
кварталам, корзины НМЦК, сравнение управлений); `monitoring/signals.ts`
(двенадцать классов сигналов из §5, каждый — с адресами).

Расширяет `procedures.ts`: стадия получает пятую ступень, добавляются поля
разобранного победителя, разбивка экономии МБ/КБ/ФБ, флаг «экономия внесена
вручную», год процедуры из кода, способ определения поставщика из префикса.

Подключает `pipeline/monitoring-match.ts` к живым данным: строки книг ГРБС
собираются существующим ингестом, процедуры — из мониторинга, результат
матчинга и пять сигналов маппинга уезжают в ответ.

Роуты: `GET /api/monitoring` расширяется (`svod`, `journal`, `directory`,
`analytics`, `signals` в дополнение к `procedures`); `GET /api/monitoring/match`
отдаёт результат сверки с книгами ГРБС и внутренней сверки «лист ↔ 25-26».
Оба под тем же rate-limit и с теми же честными отказами; `source.moneyUnit`
остаётся `руб`, `source.readAt` — обязателен. Тесты: `inject`-тесты обоих
роутов, юнит-тесты каждого нового модуля ядра на фикстурах из дампа.

### Агент Б — экран-реестр
