# Карта код-механизмов и навигации dash — 2026-07-13

**Что это.** Полная трассировка «что видит пользователь → какой механизм это производит →
из какого источника». Основание переплавки: ничего не переплавляется, пока его механизм не
зафиксирован здесь. Источники: инвентаризация web/backend (агенты 2026-07-13), QA-проход
(`../qa/2026-07-13-ui-qa-pass.md`), целевые чтения кода. Вердикты «СТАНДАРТ?» — соответствие
рыночной практике BI-продуктов.

**Вердикт: НЕ СТАНДАРТ.** Один продукт — два независимых источника одного ГРБС без сверки
между ними (QA D1: УЭР 35 против 76 строк). Рынок: один канонический слой данных, все
проекции от него; расхождение источников — это сигнал, а не молчание. Целевое: ингест обеих
книг в один слой + явная сверка «сводная ↔ отдельная» как проверка качества.

## 2. Фильтр-движок (`useFilteredData`, 870 строк)

Единственный клиентский агрегатор. Вход: `dashboardData` (весь снапшот-DTO) + 10 осей стора.
Механика по осям — где применяется на самом деле:

| Ось | Кто применяет | Где НЕ применяется (по коду) |
|---|---|---|
| год | сервер (`?year=` → пересчёт снапшота) | Реестр (год не передаётся в /api/rows) |
| период/месяцы | `summaryByPeriod`-пересбор из quarters/months | Сверка, Доверие, Замечания, Журнал |
| ГРБС/подвед | `depts`-фильтр + orgSelf/realSubs split | сигнал-виджет (D10), счётчики Замечаний частично |
| метод КП/ЕП | только topKpis + totals (kp*/ep* поля) | рейтинг, DrillPie, Экономия-числа, Свод-чипы… (D3-D5) |
| активность | fd.issues + topKpis | Экономия-числа, Сверка |
| бюджет | totals + Экономия-разрез | Свод-сетка (D6), Аналитика-графики, Реестр |
| деньги (тыс/млн) | formatMoney везде | — |
| поиск | depts/issues/topKpis | Свод, Сверка, Журнал (свой локальный) |

**Вердикт: НЕ СТАНДАРТ.** Оси применяются лоскутно; контракт «фильтр показан ⇒ применяется»
не выполняется (доказано числами в QA). Рынок: единый селекторный слой (все производные числа
проходят один pipeline фильтров), контракт-тест на каждый экран. Целевое: §8 спеки (канон
фильтров) + отчёт-проекция параметризована фильтр-контекстом.

## 3. Период-модель

`periodMode: 'week' | 'explicit'`; неделя = `focusedWeekStart` (понедельник) → месяцы недели;
explicit = `monthsByYear[year]` (Set месяцев), кварталы = синтаксический сахар над месяцами.
`setYear` синхронизирует activeMonths (починено B-5). WeekRoller ↔ TimeDrum двусторонне.
Квартальная агрегация ядра — по **план-кварталу** строки; факт засчитывается без сравнения
дат (QA D8): «исполнено в срок» не существует.

**Вердикт: модель богатая (лучше рынка по гибкости), но семантика «исполнения периода»
не определена продуктово** — добавить метрики «на дату среза» и «в срок» (эталон отчёта).

## 4. Деньги и величины

Все суммы ядра — тыс. руб (канон источника). UI: `formatMoney` (тыс/млн; 'млрд' объявлен
в типе, в барабане отсутствует). Проценты: смесь долей (0..1) и процентов (0..100) на
границе ядро/UI — исторический источник багов ×100 (см. «КП Q1: исполнение % = 1» на
Сверке-по-метрикам = доля, не отформатирована).

**Вердикт: НЕ СТАНДАРТ** — тип «процент» должен быть один (доля в ядре, форматирование в UI
через единственный форматтер), «1» вместо «100%» на сверке — прямое следствие.

## 5. Сигналы → Замечания → Жизненный цикл

29 строчных сигналов (`signals.ts`) → 17 конвертируются в Замечания (`LEGACY_SIGNAL_TO_CHECK`),
2 считаются и не показываются, 2 badge-only. Замечания перегенерируются каждым снапшотом со
status:'open'; DB-overlay возвращает статусы (B-4). issue_history хранит
reason/justification/responsible/deadline (показывается только в таймлайне одного замечания).
Рекомендации-страница = переупаковка тех же замечаний (D17), движок 13 правил мёртв.

**Вердикт: конверсия сигнал→замечание и overlay — здравые; НЕ СТАНДАРТ:** расщепление
серьёзности одного факта между вкладками (D17), сигналы без дома, отсутствие связи
замечание↔рекомендация↔реакция (ядро спеки §6).

## 6. Сверки (три подсистемы + одна скрытая)

1. «По управлениям» (`/api/reconciliation`, reconcile.ts) — сводная книга vs пересчёт. 8/8.
2. «По метрикам» (deltas в снапшоте) — официальные ячейки vs пересчёт. 528/528.
3. «Помесячно» (`reconcileMonthly`, «СВОД с месяцами»). 918/918.
4. Скрытая: `crossVerifyQuarterly` — ШДЮ vs СВОД, роут-сирота, UI нет.
Плюс псевдо-«сверка» на Экономии: AD-конфликты (210) — замечания к данным, не сверка.
«По подведам» — НЕ сверка, а витрина отдельных книг (D2).

**Вердикт: формульные сверки — сильная сторона (выше рынка); НЕ СТАНДАРТ:** вкладка
«По подведам» внутри экрана «Сверка» показывает другой источник без предупреждения;
категоризация расхождений (наш баг/лист/методология/ввод) отсутствует — §17 спеки.

## 7. Навигационная карта (все переходы)

Глобально: Header (7 секций) · OrgStrip (ГРБС/подведы, «только управление») · TimeDrum+
WeekRoller · барабаны метод/активность/бюджет/деньги · поиск · сброс. URL-sync двусторонний:
`year, period, months, depts, subs, method, activity, budget` (moneyUnit, поиск, qualityTab —
НЕ в URL).

Переходы «в глубину» (все navigateTo-сайты, 16 шт.):
- Пульт: CriticalBanner→Контроль/Замечания · rating-строка→toggle ГРБС, «detail»→Реестр ·
  квартальный бар→Аналитика(+квартал+метод) · exec-бар→toggle ГРБС · DrillPie→درill внутрь ·
  сигнал-карточка→Контроль/Замечания(+категория+поиск).
- Экономия: строка таблицы→Реестр(+ГРБС) · подвед-строка→Реестр(+подвед).
- Аналитика: KPI-карточка→Контроль.
- Контроль/Доверие: компонент→Сверка/Замечания (3 сайта); Сверка: строка→Реестр,
  метрика→лист Google (внешний) · Замечания: замечание→Реестр(строка).
- Свод: «Открыть лист»→Google Sheets (внешний, ячейка).
- Тупики (вход есть, выхода нет): Журнал (события не ведут к строкам/замечаниям),
  Рекомендации (советы не ведут никуда), «По подведам» (строки некликабельны).

**Вердикт: паттерн drill-переходов с предзаполнением фильтров — СТАНДАРТ и сохраняется;
НЕ СТАНДАРТ:** необратимость (нет breadcrumb «вернуться к контексту», browser-back работает
только для осей из URL), тупиковые страницы, legacy-ключи страниц (recon/trust/issues/recs/
journal) в navigateTo при отсутствии страниц.

## 8. Запись (единственные write-пути)

1. Редактор ячеек: PUT/POST rows → запись в ОТДЕЛЬНУЮ книгу ГРБС (та, которую Пульт не
   читает! запись может не влиять на Пульт до расхождения источников) + audit_log
   (old_value=null — провенанс теряется).
2. Статусы/комментарии замечаний → БД (транзакция, B-4).
3. Маппинг-оверрайды → БД (пайплайн их читает при сборке адресов).
4. Settings: spreadsheetId, .env (dev-gated).

**Вердикт: НЕ СТАНДАРТ** — правка пишется в источник, который главные экраны не читают
(следствие D1); отсутствие old_value ломает аудит. Целевое: один канонический источник
чтения+записи, полный провенанс правок.
