### Один рассказ, несколько свидетельств

Карточка изменения содержит книгу/лист/№ п/п, физический адрес на момент
наблюдения, поле, исходные значения, источник и время. Оригиналы остаются
раскрываемыми свидетельствами. Совпадение старого ID недостаточно: разные
значения, авторы, моменты, номера и физические строки не объединяются. Свёртка
заполнения/очистки строки сохраняет каждую ячейку; одинаковый счёт ячеек не
доказывает одинаковое событие. Неизвестное время и повторные изменения одной
ячейки не превращаются в одно действие строки.

Webhook — уведомление перечитать источник, не редактирование сотрудника.
SSE read-diff доказывает наблюдаемое изменение двух чтений; время его публикации
не является временем ввода. Автор старой ячейки даже при совпавшем переходе
не назначается новому наблюдению. Исходный `_ChangeLog` сохраняет собственные
подписи, а недельный diff — контроль и интервал обнаружения без выдуманного
автора. Межисточниковая связь без доказанного события остаётся открытой;
сходство текста и совпадение часов не дают права тихо удалить свидетельство.

### Виды комментариев и работа пользователя

1. **Обсуждение Google:** исходная ветка, все прочитанные сообщения/ответы,
   авторы и времена постов, подтверждённый anchor и состояние ветки. Время
   чтения показывается отдельно. «Отработано» в ответе координатора и закрытие
   ветки Google не означают автоматически принятое решение Dash.
2. **Заметка ячейки:** полный исходный текст, адрес, версии чтения. Встроенная
   история «Было… (дата, имя)» остаётся текстовым утверждением скрипта, а не
   метаданными Google. Её повторы с ChangeLog/снимками не выбрасываются;
   подтверждённые связи должны раскрывать оригинал и основания связи.
3. **Пояснительные графы реестра:** комментарии ГРБС/УЭР/УФ, причины и
   обоснования — значения таблицы; их правки имеют собственные before/after.
   Они не смешиваются с Google-ветками и не доказывают законность автоматически.
4. **Решения Dash и экспертные предложения:** самостоятельная проверяемая
   история решений по строке/ControlCase, с сохранением автора решения и
   read-after-write. Решение не переписывает Google-пояснение и не закрывает
   Google-ветку без отдельного действия.

В компактной панели доступны изменения, обсуждения/заметки и паспорт источника;
полная лента использует тот же отбор книги/вида/автора/поиска и недельное окно,
включая эфир. Исходные сообщения и свидетельства раскрываются из карточки.
Диагностика чтения каналов выводится отдельно: она не занимает лимит обсуждений.
Разная версия legacy-проекции Drive не прячется под прежним полным witness.

## §1. Зачем (цель)

Оператор видит таблицы; руководитель видит дашборд; но **никто не видит, как данные пришли в текущее состояние**. Пользователь уже решил это вручную в Google-таблице — бот-трекер `_ChangeLog` v6 красит изменённые ячейки по типу (🔴дата/🟡число/🟠формула/🔵текст), хранит старое значение в примечании, шлёт сводки кураторам (Соколова — даты немедленно, Филатов — формулы). AEMR должен поднять это в продукт на двух высотах:

- **Руководитель:** «что изменилось с прошлой недели» в метриках (доля ЕП 50.4%→54.1%, экономия 33.5→52.8 млн).
- **Оператор:** «кто, что и когда правил в этой строке/ячейке», цветом по типу — как в его листе.

Инвариант: история = **темпоральная сверка** (было↔стало), брат пространственной сверки (calc↔ШДЮ). Обе отвечают на один вопрос — *можно ли верить числу*.

## §2. Два слоя данных

### Слой 1 — Snapshot-diff (дрейф метрик, руководитель)
**Источник — уже есть:** `snapshots` (точки времени: `id`, `createdAt`, `data`, trust/issue/row counts) + `metric_history` (`snapshotId`, `metricKey`, `numericValue`, `displayValue`, `confidence`). Diff = выбрать две точки → для каждого `metricKey` взять значения и посчитать дельту.
**Модель:** `MetricDelta { metricKey, from:{value,at}, to:{value,at}, deltaAbs, deltaPct, direction:'up'|'down'|'flat', sentiment:'good'|'bad'|'neutral' }`. `sentiment` — по справочнику направлений (рост экономии = good; рост доли ЕП = bad/внимание; рост исполнения = good). Цвет по **sentiment**, не по знаку.
**Сервис (новый):** `snapshotDiff(fromSnapshotId, toSnapshotId, axisFilter?) → MetricDelta[]`. Чистая функция над `metric_history`, тестируемая изолированно.

### Слой 2 — Cell-edit log (провенанс ячеек, оператор)
**Источник:** `audit_log` (есть, ловит правки) + **новая материализация `event_changelog`** из листа `_ChangeLog` трекера. Каждая правка: `{sheet, cellA1, col, row, dept, sub, oldValue, newValue, at, author, kind, priority, status}`. `kind` ∈ {date,number,formula,text} — **те же 4 ловушки трекера** (классификатор переиспользует `classifyChange` логику: дата>формула>число>текст). `priority`/`status` (pending/sent/confirmed) — из трекера + `_Exceptions` (подтверждённые исключения, чтобы не шуметь ложными — урок УИО).
**Сервис (новый):** `cellHistory(filter:{dept?,sub?,kind?,period?,cellRef?}) → CellEdit[]` + `cellHistoryForRow(dept, rowKey) → CellEdit[]` (для инлайн-поповера).

> **Что строить (для агентов):** (1) ingest листа `_ChangeLog` → таблица `event_changelog` (drizzle-схема уже специфицирована в `DATA_MODEL §5`, но не материализована); (2) `snapshotDiff` сервис над `metric_history`; (3) переиспользовать `classifyChange` (4 типа) на сервере.

## §3. Две поверхности (UI)

### Инлайн — Δ-оверлей (везде)
- Глобальный тумблер в шапке: **«изменения с [дата]»** (дефолт: −7 дней). Включён → по приложению зажигаются Δ-маркеры.
- На **метриках** (Пульт/Свод/Экономия): маленький бейдж `▲+3.7пп` цветом sentiment; клик → мини-поповер «было→стало, когда, из какого снимка» (слой 1).
- На **ячейках Реестра/Свода**: точка-Δ цветом `kind` (🔴/🟡/🟠/🔵); клик → поповер истории правок ячейки (старое→новое, когда, кто, тип) — слой 2. **Один в один язык трекера**, оператор уже его знает.
- Компонент-изоляты: `<DeltaBadge metric>` (слой 1), `<CellDeltaDot edit[]>` + `<CellHistoryPopover>` (слой 2). Каждый — одна ответственность, тестируется отдельно.

### Хаб — страница «Доверие» → вкладка «История»
- Слева **таймлайн снимков** (вертикальная ось времени, точки = снимки; выбрать две для сравнения; дефолт сегодня↔неделя-назад).
- Центр — **diff метрик** (слой 1): таблица/водопад дельт по выбранным двум точкам, фильтр по 6 осям, сортировка по |дельте|.
- Низ/право — **лента правок ячеек** (слой 2): хронология, фильтр депт/подвед/тип/период/автор, цвет по типу. Клик по правке → подсветка в Реестре.

## §4. Пересборка IA (что объединить/разъединить)

Сейчас: 7 пунктов; «Контроль» уже хаб (quality/recon/trust/issues/recs/**journal**). Журнал погребён.
**Предложение:** переименовать/осмыслить хаб как **«Доверие»** = `Сверка ШДЮ` (пространственная) + **`История`** (временная, эта фича) + `Trust` + `Проблемы` + `Журнал`(сырой audit). Одна ось «можно ли верить числам и как они менялись».
**Целевая навигация (7, чисто):** Пульт · Свод · Реестр · Экономия · Аналитика · **Доверие** · Система. История — ещё и **сквозная** (Δ-оверлей везде), не только вкладка.
**YAGNI:** не плодим отдельный top-level «История» — она живёт как оверлей + вкладка Доверия. Recs (рекомендации) — кандидат на слияние в Аналитику/Доверие (проверить с агентами, вне этого спека).

## §5. Фазы (анти-слоп: каждый слой вылизываем, не вываливаем)

- **Фаза C (MVP, инлайн слой 1):** `snapshotDiff` сервис + `<DeltaBadge>` на метриках Пульта/Свода + тумблер «изменения с [дата]». Данные есть (snapshots+metric_history) → быстрый видимый эффект, ноль новых таблиц. **Ship первым.**
- **Фаза 2 (инлайн слой 2):** materialize `event_changelog` из `_ChangeLog` + `cellHistory` + `<CellDeltaDot>`/`<CellHistoryPopover>` в Реестре/Своде. Поячеечная история цветом-как-трекер.
- **Фаза 3 (хаб + IA):** вкладка «История» в «Доверие» (таймлайн+diff+лента) + переименование/слияние IA. Полная картина.

## §6. Обработка ошибок и краевые
- Снимков <2 → оверлей скрыт, тумблер disabled с подсказкой «нужно ≥2 снимка».
- `metricKey` есть в одном снимке, нет в другом → дельта = «появилось/исчезло», не NaN.
- Ложные правки (урок УИО): `_Exceptions`/`status:confirmed` фильтруют шум — подтверждённые исключения не маркируются красным.
- Демо-режим: snapshot-diff на демо-снимках (как сосед сделал для СВОД) — реалистичные дельты, не пусто.

## §7. Тестирование
- `snapshotDiff` — юнит: дельты, sentiment, появление/исчезновение метрики, фильтр по осям.
- `classifyChange` (4 типа) — уже есть в трекере; портировать + юнит на сервере.
- `event_changelog` ingest — parity-тест: N строк листа `_ChangeLog` → N типизированных правок, типы совпадают.
- Компоненты — изолированный рендер `<DeltaBadge>`/`<CellHistoryPopover>` на фикстурах.
- Каждая фаза — зелёный tsc+test перед мержем (гейт husky).

## §8. Планка качества (без слопа)
- Язык = трекер пользователя (4 цвета/типа), не дженерик-таблица.
- Δ-маркеры — *тихие* по умолчанию (точка/бейдж), раскрываются по клику; не зашумлять экран.
- Apple-compact: оверлей не ломает 1240×480; история — прогрессивное раскрытие.
- `impeccable-shape`→`impeccable-polish` перед ship каждой фазы; `impeccable-audit` a11y.
