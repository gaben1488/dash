# Контракт данных: dash → 1С и «Смарт-бюджет» (05.08.2026)

**Цель пользователя:** dash становится системой данных, из которой
**нормализованные и верифицированные** сведения о закупках уходят в
существующие процессы — учётный контур 1С и бюджетный «Смарт-бюджет».
Не «ещё одна таблица», а источник, которому те системы могут доверять.

Документ отвечает на три вопроса: что у нас уже есть в качестве актива,
что физически мешает стыковке сегодня, и какой контракт данных закрывает
разрыв. Все числа — из живых книг выгрузки 26.06.2026 (3 691 строка,
8 ГРБС), проверены скриптами разведки 04–05.08.

## §1. Что у dash уже есть — активы для интеграции

| Актив | Состояние | Почему это ценно для 1С / Смарт-бюджета |
|---|---|---|
| **Строка-атом** — 33 колонки канона `DEPT_COLUMNS` | ✅ читается из 8 книг, шапка распознаётся | Единая структура вместо восьми разных листов |
| **Способ определения поставщика** | ✅ нормализован (`classifyMethodGroup`): КП/ЕП, алиасы сведены | В листах «ЭА», «эа», «Ед. поставщик» — снаружи нужен один код |
| **Основание выбора ЕП** | ✅ 30 кластеров, распознаёт 98 % строк (3 022 из 3 081) | Основание ст. 93 — обязательный реквизит учёта |
| **Причина отклонения сроков** | ✅ 25 кластеров, 79 % из 494 строк, у каждого — ответственный | Для бюджетного контура это причина недоисполнения |
| **Ожидаемая дата заключения** | ✅ вынимается из текста (`extractForecastDate`) | Прогноз кассового исполнения — то, чего нет в листах вовсе |
| **Деньги в трёхсрезе ФБ/КБ/МБ** | ✅ план и факт, инвариант `fb+kb+mb=total` | Прямая проекция на источники финансирования |
| **Этапность** (вид деятельности, стадия) | ✅ считается по колонкам F/N/Q | Текущая деятельность vs программные мероприятия |
| **Сверка с официальным листом** | ✅ по каждому ГРБС, с адресами ячеек | Доказательство, что цифра не разошлась с признанным источником |
| **Провенанс до ячейки** | ✅ книга → лист → строка → ячейка у каждого числа | Аудиторский след при переносе в учёт |
| **Журнал правок `_ChangeLog`** | ✅ 37 тыс. записей, кто/когда/было→стало | История изменений, которую внешняя система не восстановит |

## §2. Что мешает стыковке — три разрыва (проверено на данных)

### 2.1. Разрыв идентичности: у строки нет устойчивого ключа

`№ п/п` (колонка A) уникален внутри книги, но **между неделями он не
держится**. Сравнение выгрузок 08.05 и 26.06 по одному и тому же номеру:

| ГРБС | Общих номеров | Предмет совпал | Что это значит |
|---|---:|---:|---|
| УД | 184 | 184 (100 %) | номера стабильны |
| УЭР | 81 | 79 (98 %) | две строки разъехались |
| **УО** | 2 049 | **1 468 (72 %)** | **581 строка сменила предмет при том же номере** |

Строки вставляют в середину, нумерация сдвигается — и «строка № 1165»
на прошлой неделе и на этой это разные закупки. Без устойчивого ключа
внешняя система не сможет обновить запись: она либо задвоит, либо
перезапишет чужое.

### 2.2. Разрыв реквизитов: ключей внешних систем в листах нет

| Реквизит | Есть строк | Из 3 691 | Кому нужен |
|---|---:|---:|---|
| КБК (20 знаков) | 71 | 2 % | Смарт-бюджет — без него не лечь в роспись |
| Реестровый номер контракта ЕИС (19 знаков) | 5 | 0,1 % | 1С — связь с контрактом и платежами |
| ИНН поставщика | 19 | 0,5 % | 1С — контрагент |
| ОКПД2 | нет отдельной колонки | — | классификация предмета закупки |
| Код мероприятия муниципальной программы | текстом в двух колонках | — | Смарт-бюджет — привязка к программе |

Учётный контур опознаёт закупку по реестровому номеру и контрагенту,
бюджетный — по КБК и коду мероприятия. Ни того, ни другого в листах
практически нет: закупка описана словами, а не кодами.

### 2.3. Разрыв качества: свободный текст вместо значений

239 разных формулировок причин отклонения на 494 строки, 250 формулировок
оснований ЕП на 3 081. Словари это чинят на 79–98 %, но остаток —
авторские тексты, которые не сводятся к коду в принципе. Плюс дефекты
заполнения, которые продукт уже видит: 77 строк «техническая ошибка ввода
даты», 11 строк со статусом вместо причины.

**Вывод.** Данные dash пригодны как ИСТОЧНИК СМЫСЛА (что закупается,
каким способом, на какие деньги, почему задерживается), но не как готовый
поток проводок: у них нет ни идентичности, ни кодов внешних систем.
Контракт ниже закрывает разрыв, не требуя переделки книг ГРБС.

## §3. Контракт данных — канонические сущности выгрузки

Пять сущностей, стабильные по составу; каждая несёт провенанс и уровень
доверия. Формат обмена — JSON Lines и CSV (UTF-8, BOM для 1С), один файл
на сущность; поверх — REST-эндпойнт для инкрементальной выборки.

### 3.1. `procurement_item` — плановая позиция закупки (ядро)

| Поле | Тип | Источник | Обязательное |
|---|---|---|---|
| `item_uid` | string | **суррогатный ключ dash** (§4) | да |
| `grbs_id` | string | реестр ГРБС (канон `DEPARTMENT_REGISTRY`) | да |
| `subordinate` | string \| null | колонка C | нет |
| `subject` | string | колонка G, как в листе | да |
| `method_code` | `KP`\|`EP` | нормализация `classifyMethodGroup` | да |
| `method_raw` | string | колонка L дословно | да |
| `ep_reason_cluster` | string \| null | словарь ЕП (30 кластеров) | у ЕП |
| `ep_reason_raw` | string \| null | колонка M дословно | нет |
| `ep_legitimate` | boolean \| null | признак словаря | у ЕП |
| `plan_date`, `plan_quarter`, `plan_year` | date, 1–4, int | колонки N/O/P | да |
| `fact_date` | date \| null | колонка Q, канон `factCountsOn` | нет |
| `plan_fb/kb/mb/total` | number (тыс. руб.) | H/I/J/K | да |
| `fact_fb/kb/mb/total` | number \| null | V/W/X/Y | нет |
| `economy_total`, `economy_approved` | number, boolean | Z–AC, флаг AD | нет |
| `activity_type` | `current`\|`program`\|`unknown` | колонка F | да |
| `stage` | `concluded`\|`in_work`\|`overdue`\|`unfunded` | расчёт этапности | да |
| `deviation_cluster`, `deviation_owner` | string \| null | словарь причин | нет |
| `forecast_date` | date \| null | извлечение из текста | нет |
| `provenance` | object | книга, лист, строка, дата чтения | да |
| `trust_level` | `verified`\|`normalized`\|`raw` | §5 | да |

### 3.2. Остальные четыре сущности

- **`grbs`** — справочник управлений: `grbs_id`, полное и короткое имя,
  подведы. Ключ уже канонический (`DEPARTMENT_REGISTRY`).
- **`reason_dictionary`** — оба словаря как данные: кластер, подпись,
  ответственный, признак легитимности, образцы формулировок. Внешняя
  система получает не только код, но и его смысл.
- **`change_event`** — правка книги: `item_uid`, атрибут, было, стало,
  автор, время. Источник — `_ChangeLog`; это аудиторский след переноса.
- **`weekly_snapshot`** — срез четверга: агрегаты по ГРБС и району с
  адресами ячеек официального листа. Для сверки принимающей стороной.

## §4. Правило идентичности — как получить `item_uid`

Ключ строится dash и живёт в dash; книги ГРБС не меняются.

1. **Естественный ключ-кандидат**: `grbs_id` + `subordinate` +
   нормализованный `subject` + `plan_year`. Совпадение по нему между
   неделями = та же закупка.
2. **Разрешение коллизий**: если в одном ГРБС несколько строк с
   одинаковым предметом и годом (типовые «поставка канцтоваров» × 12),
   в ключ добавляется `plan_quarter`, затем `plan_total`, затем порядок
   появления. Полученный ключ хэшируется — `item_uid` = стабильная
   строка, не зависящая от `№ п/п`.
3. **Журнал соответствия**: dash хранит таблицу `item_uid ↔ (неделя,
   № п/п, строка листа)`. Именно она отвечает на вопрос «эта строка на
   прошлой неделе была той же?» — и она же даёт внешней системе право
   обновлять запись, а не плодить дубли.
4. **Честность при разрыве**: если сопоставить не удалось (предмет
   переписан целиком), позиция уходит как новая, со ссылкой на
   предполагаемого предшественника и пометкой `match: uncertain`.
   Продукт не склеивает вслепую.

## §5. Уровни доверия — что можно отдавать наружу

| Уровень | Что это | Правило выгрузки |
|---|---|---|
| `verified` | Число сошлось с официальным листом СВОД (сверка по ГРБС) либо взято из него | Отдаётся как есть |
| `normalized` | Пересчёт dash по канону движка; распознанный кластер словаря | Отдаётся с указанием правила и провенанса |
| `raw` | Свободный текст, нераспознанная формулировка, дефект заполнения | Отдаётся только как текст, БЕЗ кода — принимающая система не должна принимать решение по нему |

Строка с `trust_level: raw` в бюджетную роспись не идёт: сначала человек
приводит её в порядок в источнике. Это защита принимающей системы от
мусора, а не ограничение выгрузки.

## §6. Что нужно от принимающей стороны (чего у нас нет)

Полная стыковка требует встречного шага — того, что dash получить
неоткуда:

1. **КБК и код мероприятия программы** на позицию — из Смарт-бюджета или
   от ГРБС при заполнении. Без них связь с росписью строится вручную.
2. **Реестровый номер контракта ЕИС и ИНН поставщика** — из ЕИС-выгрузки
   либо из 1С по факту заключения. Тогда закупка склеивается с платежами.
3. **Согласованный справочник предметов** (ОКПД2 или внутренний) — иначе
   «поставка бумаги» у восьми ГРБС останется восемью разными строками.

**Порядок, который это закрывает** (без переделки книг): dash отдаёт
позиции с `item_uid`; 1С и Смарт-бюджет возвращают свои коды по этому
ключу; dash хранит соответствие и с этого момента отдаёт данные уже
обогащёнными. Иными словами, ключ — наш, коды — их, связь — журнал.

## §7. Этапы

| Этап | Содержание | Готовность |
|---|---|---|
| 1 | Суррогатный ключ `item_uid` + журнал соответствия недель | не начато |
| 2 | Выгрузка `procurement_item` и словарей (JSONL/CSV) + эндпойнт | не начато |
| 3 | Приём встречных кодов (КБК, ЕИС, ИНН) и их хранение | не начато |
| 4 | Двусторонняя сверка: расхождение сумм dash ↔ 1С как сигнал | не начато |
| 5 | Отказ от ручных книг: ввод в dash, выгрузка в оба контура | цель |

Этап 1 — самостоятельная ценность и без интеграции: устойчивый ключ
превращает недельные снимки в историю позиции («эта закупка ездит по
кварталам третий раз»), чего сегодня продукт сказать не может.

## §8. Чего этот документ НЕ утверждает

Я не видел ни одного интерфейса 1С и Смарт-бюджета этого района: какие
именно объекты там заводятся, какие поля обязательны, есть ли API или
обмен идёт файлами. Всё выше описывает нашу сторону контракта — что мы
можем отдать и на каких условиях. Формат приёма нужно согласовывать с
владельцами тех систем; после этого §3 уточняется под их поля, а §6
превращается в конкретный список.
