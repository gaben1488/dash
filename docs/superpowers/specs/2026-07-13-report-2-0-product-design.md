# Отчёт 2.0 — продуктовый дизайн dash

**Дата:** 2026-07-13 · **Статус:** согласован по секциям с пользователем (4 секции, все approved)
**Основа:** инвентаризация реального кода (3 агента: web UI, backend/core, ground-truth отчётов),
`docs/PLAN.md` §0-1 (контрольный список 21), REPORT_STRUCTURE (ДНК эталонного отчёта).

---

## 1. Цель

dash — живой еженедельный «Отчёт по закупкам», а не BI-обёртка над таблицами. Первый экран
читается как документ, который сейчас пишут руками: те же три блока (конкурентные процедуры →
единственный поставщик → блок по каждому из 8 ГРБС), в том же порядке, с теми же утверждениями.
Отличие от бумаги: каждое число кликабельно до строки-атома и исходной ячейки, каждая
рекомендация несёт статус реакции ГРБС, каждый вывод подпёрт аудит-индикатором.

**Критерий готовности** — контрольный список из 21 строки в `docs/PLAN.md` §1:
колонка «Показано» должна стать 21/21 (замер 2026-07-10: данные 7/21 полных, показано 0/21).

Строка-атом остаётся законом: `ГРБС × подвед × метод × активность × бюджет × период`.

## 2. Решения, принятые пользователем (2026-07-13)

1. **Отчёт как ось** — IA повторяет скелет эталонного отчёта, BI-разрезы — второй слой.
2. **Переплавка** — старые 7 страниц растворяются в новой IA; никаких «старых» и «новых» разделов рядом.
3. **Человеческий контекст: чтение + ввод в dash** — реакции на рекомендации и оговорки вводятся
   в интерфейсе и хранятся в БД dash (первые данные, где dash — источник истины).
4. **Аудит-слой встроен в отчёт** — доказательная подложка утверждений, не отдельная страница-свалка.
5. **Дизайн с ЕИС, реализация фазами** — модель данных учитывает ЕИС-слой (стадии, победитель+ИНН)
   с первого дня; реализация — поздняя фаза (сначала ручной импорт xlsx, потом автоматизация).

Плюс два жёстких требования пользователя:

- **Язык продукта.** Ни один внутренний ключ или артефакт (`UNMAPPED`, `uo`, `_org_itself`,
  `exec_count_pct`, латиница-иды) не появляется в UI. Только обывательский русский из словаря
  продукта (§6.3). Закрепляется тестом.
- **Frontend-качество.** Каждая UI-задача проходит цепочку skills:
  `impeccable-shape` (до кода) → `frontend-design`/`emil-design-eng` (реализация) →
  `impeccable-audit` → `impeccable-polish` + `humanizer` по всем текстам.

## 3. Пользователи

- **УЭР / ЦЭР** (полный доступ): читают отчёт, разбирают сигналы, вводят реакции по итогам
  совещаний, правят строки.
- **ГРБС-вьюер** (решение принято ранее, реализация — фаза 7): видит свою секцию отчёта
  (у каждой секции ГРБС свой URL — задел под RBAC).
- **Начальство**: читает отчёт как документ; для них язык продукта и честные плашки важнее всего.

## 4. Информационная архитектура — 4 раздела

| Раздел | Что это | Куда переплавляются старые страницы |
|---|---|---|
| **Отчёт** (главная) | скролл-документ: блок КП → блок ЕП → 8 секций ГРБС (свёрнуты; свой URL у каждой) | Пульт (hero-KPI → шапка), Свод (единая сетка → таблица блока КП), Экономия (→ подсекция КП + карточки ГРБС), Рекомендации (→ секции ГРБС со статусами) |
| **Реестр** | строки-атомы: просмотр, сигналы, редактор, экспорт | Реестр текущий + честные фильтры (год и бюджет сейчас игнорируются — дефект) |
| **Лаборатория** | песочница аналитика: Benford, Z-выбросы, прогноз, scatter, сезонность, дробление, композитные баллы | Аналитика + весь непоказанный аудит-слой (dataset-signals пишется в каждый снапшот и не читается ни одним роутом; scorecard-стек висит на orphan-эндпойнтах) |
| **Данные** | сверка, доверие, журнал, замечания-lifecycle, источники, маппинг | Контроль (5 вкладок) + Система |

### 4.1 Страница «Отчёт» — поведение

- Липкое оглавление по скелету эталона (КП: план года / кварталы / заключено / крупные ЭА /
  исполнение по ГРБС / осталось / в работе / расчётная экономия; ЕП: план-факт / причины по ГРБС /
  обоснованные vs к централизации; далее 8 ГРБС).
- **Claim-строки**: утверждение = простая русская фраза с подчёркнутыми числами. Клик по числу —
  оверлей «доказательство»: строки-атомы, провенанс ячейки («Откуда число: лист СВОД, ячейка Q14 ·
  открыть в таблице»), формула пересчёта.
- Ссылки «→ строки» ведут в Реестр с уже применённым фильтром.
- Секция ГРБС: КП/ЕП-цифры, двойное исполнение (% к кварталу И к году рядом), экономия,
  «осталось отыграть» списком, рекомендации со статусом реакции, оговорки ГРБС из колонки AE.
- **Честные плашки** вместо пустоты: «в работе по стадиям — нет данных источника (появится с
  ЕИС-слоем)»; «комментарии ГРБС заполнены на 5% — контекст неполон» (реальная неравномерность:
  УО 100%, УКСиМП 99%, УД 71%, УФБП 63% — УЭР 5%, УДТХ 8%).
- Всё уважает глобальные фильтры; дефолт = текущий год, неделя снапшота.
- Отчёт за прошлую неделю: проекция над историческим снапшотом (снапшоты уже хранятся в БД).

## 5. Поток данных

```
Источники: Google Sheets (СВОД + 8 ГРБС)  +  [фаза 6] ЕИС-выгрузки (OrderSearch/ContractSearch)
   ↓
Конвейер (ядро, чистые функции): ингест (без тихих потерь) → расчёт → сверка → доверие →
   сигналы (29) → аудит-слой (Benford, дробление, сезонность, баллы) → снапшот
   ↓
Проекции (новый слой):
   • Отчёт-проекция: снапшот → упорядоченные ReportClaim по скелету эталона
   • Рекомендации + реакции (БД dash)
   • Словарь продукта (ключ → человеческая фраза)
   ↓
UI: Отчёт · Реестр · Лаборатория · Данные
```

Архитектурная валидация (проведена адверсариально против CQRS/hexagonal): проекция =
материализованное чтение над снапшотом, зависимости только внутрь ядра, тестируется без
сервера. Принято с четырьмя поправками — §6.2.

## 6. Модель данных

### 6.1 Новые сущности

- **ReportClaim** — утверждение отчёта: `sectionId` (позиция в скелете), текст-шаблон (русский),
  числа со ссылками на источник (метрика → ячейка ИЛИ фильтр строк), статус данных:
  `посчитано | источника нет | данные неполны (X%)`. Чистая проекция, в БД не хранится.
- **Recommendation** — порождается 13 правилами `recommendations.ts` (сейчас мёртвый модуль,
  0 импортёров) + централизацией + дроблением. Стабильный естественный ключ (§6.2.1).
- **RecommendationReaction** (БД): `recommendationKey`, статус `принята | не принята | частично`,
  `justification` (текст ГРБСа), `author`, `createdAt`. Задел уже есть: `issue_history` хранит
  reason/justification/responsible/deadline.
- **RowCaveat** (БД): оговорка к строке, введённая в dash (дополняет AE из таблиц, не заменяет).
- **WeeklyConclusion** (БД): вывод недели (человеческий текст к отчёту), автор + дата.
- **StageInfo** [фаза 6]: стадия закупки из ЕИС (извещение / подача заявок / рассмотрение /
  заключение / не состоялся).
- **Supplier** [фаза 6]: победитель + ИНН → концентрация поставщиков, single-bid.

### 6.2 Четыре поправки по швам (иначе — баги)

1. **Идентичность рекомендации.** Ключ = (правило, ГРБС, нормализованный отпечаток предметов
   закупок). НИКОГДА — индексы строк (сдвиг строк в таблице не должен отрывать реакцию).
   Прецедент: статусы замечаний уже переживают перегенерацию через overlay по стабильному id.
2. **Жизненный цикл реакции.** Рекомендация исчезла в новом снапшоте → пара архивируется со
   статусом «выполнена/неактуальна», остаётся видимой в истории секции ГРБС. Ничего не удаляется
   и не виснет.
3. **Проекция параметризована фильтрами.** `buildReport(snapshot, filterCtx, reactions)` — не
   глобальный синглтон. Иначе повторим главный анти-паттерн текущего UI (фильтр показан, но
   не применяется).
4. **Временна́я честность.** Исторический отчёт показывает реакции по состоянию на дату снапшота
   (`createdAt ≤` даты снапшота), не сегодняшние.

### 6.3 Словарь продукта

Единый реестр «внутренний ключ → человеческая фраза» в `@aemr/shared`. Единственный легальный
путь текста в UI. Примеры: `UNMAPPED` → «причина не распознана», `_org_itself` → «само
управление», `exec_count_pct` → «исполнение по количеству». Закрепляется тестом: ни один сырой
ключ не отрисовывается (проверка рендера страниц на паттерны ключей).

### 6.4 ЕИС-стыковка [фаза 6]

Точного ключа (ИКЗ) в таблицах ГРБС нет → модуль сопоставления «строка ↔ ЕИС-запись» по
наименованию + сумме с показателем уверенности и честным списком несопоставленного. Ручной
прецедент существует: лист «Сверка 5 источников» в ПЛАН-РЕЕСТРЕ (115×28, наименования по
УЭР/ПГ/ЕИС рядом).

### 6.5 БД

SQLite остаётся; новые таблицы (`recommendation_reactions`, `row_caveats`, `weekly_conclusions`)
проектируются сразу совместимыми с PostgreSQL (ADR-0001 отложен). Паттерн един: снапшот —
источник фактов, БД — источник жизненного цикла (уже так работают статусы замечаний).

## 7. Аудит-подложка

Индикаторы живут у утверждений, не на отдельной странице:

- дробление — чип в секции ГРБС рядом с рекомендацией «объединить» (клик — строки-доказательства);
- Benford / Z-выбросы — в Лаборатории + бейдж «данные аномальны» у затронутого ГРБС;
- балл дисциплины — в карточке ГРБС словами: «дисциплина 83 из 100: минус 12 за просрочки,
  минус 5 за пустые обоснования»;
- доля «причина не распознана» в ЕП — метрика качества данных в блоке ЕП.

Показываем только то, что доказуемо до строки.

## 8. Канон фильтров

Шесть осей (год, период, метод, активность, бюджет, ГРБС/подвед) + денежная единица работают на
**каждом** экране либо честно объявлены неприменимыми («Журнал не фильтруется по бюджету — это
события, а не деньги»). Контракт-тест на каждый экран: фильтр показан ⇒ фильтр применяется.

Известные дефекты (из инвентаризации, чинятся фазой 0): Реестр игнорирует год и бюджет;
Аналитика игнорирует бюджет; Экономия использует метод только в лейбле; `changeWindow` мёртв.

## 9. Ревизия ядра (сквозной трек, требование пользователя)

Каждый модуль конвейера проходит доказательную ревизию:

- **математика** — формула сверяется руками на реальных выгрузках (64 файла, метод отработан),
  фиксируется тестом с рукосчитанными числами;
- **продуктовая логика** — каждая метрика отвечает на вопрос из контрольного списка 21;
  лишнее удаляется (ponytail);
- **законодательная сверка** — пороги 44-ФЗ (ст.93 ЕП, ст.37 антидемпинг, дробление,
  ст.25 совместные закупки) сверяются с актуальной редакцией (свежий поиск + канон legal-refs);
  каждое правило получает ссылку на статью в коде и в подсказке UI;
- **known-баги** — реестр CONFIRMED дочищается (остался B-8: счётчик дропнутых строк + сигнал
  unknown-листа; фиксы задрафчены и верифицированы).

Выход: для каждого модуля вердикт «доказан» с тестом-свидетельством.

## 10. Методы и тестирование

**Парадигмы:** DDD (контексты: Ингест / Расчёт / Отчёт-проекция / Реакции / Словарь; инварианты
домена — закон, менять только через ADR), TDD (красный тест раньше фикса, дисциплина отработана),
CDD-характеризация (числа старых страниц пиннятся до переплавки — новая страница обязана
показывать те же числа или расхождение объяснено), ponytail (удалять раньше, чем добавлять;
мёртвые компоненты, changeWindow, orphan-роуты — под нож или в дело).

**Тестовая пирамида:**
1. ядро — юнит с рукосчитанными фикстурами;
2. отчёт-проекция — снапшот-фикстура → структура отчёта побайтно;
3. контракт фильтров — на каждый экран;
4. словарь — «сырой ключ не дошёл до глаз»;
5. браузерные (playwright) — путь «утверждение → доказательство → реестр» и ввод реакции;
6. характеризация — переплавка без потерь чисел.

Гейт неизменен: `pnpm typecheck` (4 пакета) + `pnpm lint` (0 ошибок) + `pnpm -r test` на каждый
коммит; lint обязателен для move-only (урок G-3).

## 11. Фазировка

| Фаза | Что | Видимый результат |
|---|---|---|
| 0 | Дочистка CONFIRMED (B-8) + канон фильтров на текущих страницах + **перепись остатка сверки** (§17 шаг 1-2: полный список расхождений с категориями) | фильтры перестают врать; письменный ответ «почему расхождения» |
| 1 | Словарь продукта + отчёт-проекция (ядро) + тесты + **реверс-инжиниринг эталона** (§14: пара docx+xlsx одной недели) | claims собираются из снапшота и сверены с реальным отчётом |
| 2 | Страница «Отчёт»: блоки КП/ЕП + 8 секций ГРБС (skills-цепочка UI; блоки закрывают дефициты §15) | живой Отчёт 2.0 на главной |
| 3 | Рекомендации (оживить 13 правил) + реакции (БД, ввод, история) | цикл рекомендация→реакция замкнут |
| 4 | Переплавка: Реестр → Лаборатория → Данные (каждый блок — до 100/100 по §15) | старые 7 страниц растворены |
| 5 | Ревизия ядра (§9) + **ревизия сигналов** (§16) + **сверка-ноль** (§17 шаги 3-4) — параллельно 2-4 | вердикты «доказан»; сигналы измерены; ноль необъяснённых расхождений |
| 6 | ЕИС-слой: импорт xlsx → сопоставление → стадии + поставщики | строки 8/16/20 списка закрыты |
| 7 | RBAC (multi-user: УЭР/ЦЭР полный, ГРБС-вьюер свой срез) + прод (TLS, мониторинг) — когда VPS оплачен | наружу |

Прогресс меряется списком 21: после ф.3 «Показано» ≈ 14/21, после ф.6 — 21/21.

**Протокол «без регресса» (обязателен каждой задаче плана):** до правки — характеризационный
тест пиннит текущие числа/поведение блока; после — те же числа либо задокументированное
объяснение расхождения; гейт (typecheck+lint+тесты) зелёный; для UI — impeccable-audit
без P0/P1. Ничего не описанное в плане не делается: план — исчерпывающий контракт работ,
каждая задача перечисляет файлы, шаги, тесты и команды.

## 12. Вне скоупа этого дизайна

- Генератор .docx (PLAN.md §0: отчёты команда пишет сама; dash даёт картину и доказательства).
- PostgreSQL-миграция (ADR-0001 отложен; новые таблицы проектируются совместимыми).
- Автоматический ЕИС-API (фаза 6 начинается с ручного импорта xlsx).
- Совместные закупки как модель эффекта (строка 20) — внутри фазы 6, после поставщиков.

## 13. Карта сохранности: каждый существующий блок → новый адрес

Принцип: переплавка ≠ выбрасывание. Язык интеракций, спроектированный с пользователем
(TimeDrum + WeekRoller, OrgStrip, барабаны фильтров, drill-оверлеи, expandable-карточки,
sparklines в рейтинге), — сохраняется как система; меняется структура страниц, не паттерны.

| Hero-KPI ×4 + expand (Пульт) | шапка Отчёта (те же метрики, те же панели раскрытия) |
| RatingTableV2 (assertion, sparklines, подведы) | блок КП «исполнение по ГРБС» — компонент переезжает |
| План/Факт по кварталам (стек КП+ЕП + линия) | блок КП «по кварталам» |

## 16. Ревизия сигналов: нужность и корректность по факту (требование пользователя)

Правило: сигнал существует, только если он (а) ловит **реальную** оказию данных или
организационный момент закупок, (б) измерен на реальном корпусе (64 файла, 3261 строка

Процедура (фаза 5, для каждого из 29 строчных + всех датасетных):
1. Прогон на реальном корпусе → частота срабатывания, примеры строк.

3. Вердикт: оставить / перекалибровать порог / удалить (ADR).
4. Каждому выжившему: человеческое название из словаря, объяснение в БЗ, дом в UI.

## 17. Сверка-ноль (требование пользователя: «сверка не должна показывать расхождений»)

**Почему расхождения были всегда — честный ответ на сегодня.** Часть корней уже найдена и
устранена в прошлых волнах: знак amount_dev (факт−план), база «все годы vs один год»,
нормализация ключей латиница↔кириллица, AD-гейт экономии. Крупнейший известный остаток —
помесячная сверка ШДЮ: 596 расхождений диагностированы как **дефекты формул легаси-листа**
(движок канон; таксономия корней есть в `SHDYU_RECON_ROOT_CAUSES`). Полного пофактного
разбора **текущего** остатка расхождений нет — это и есть первый деливерабл этого трека.

Программа:
1. **Перепись остатка**: прогнать все три сверки (единая сетка, по ГРБС, помесячная) на живых
   данных → полный список расхождений с числами.
2. **Каждому расхождению — категория**: наш баг движка / дефект формулы листа / методологическое
   различие (окно периода, гейт) / ошибка ввода данных ГРБС.
3. **Наши баги** — чинятся (TDD). **Дефекты листа** — сверка показывает «лист ошибается, вот
   доказательство» (это продуктовая фича: сверка = аудит листа, а не наш позор; красный бейдж
   заменяется на «расхождение объяснено: формула листа»). **Методология** — выравнивается или
   документируется у бейджа. **Ввод** — становится замечанием ГРБСу.
4. **DoD: ноль необъяснённых расхождений.** Каждый бейдж сверки либо зелёный, либо несёт
   категорию и доказательство. Письменный разбор «почему расхождения были всегда» — отдельный
   документ по итогам переписи (ответ на вопрос пользователя, который так и не был дан).

## 18. Терминология организаций: ГРБС / ПБС / аппарат (канон, требование пользователя)

Основание — БК РФ (ст.6, 158-162): **ГРБС** (управление) распределяет лимиты между
подведомственными **ПБС** — получателями бюджетных средств (бюджетные/автономные/казённые
учреждения: школы, сады, ДК…). Ключевой факт: орган может быть **одновременно ГРБС и ПБС** —
это и есть наш `_org_itself`: УО как орган — ГРБС для сети, и сам заказчик собственных закупок.

Канон словаря (заменяет «само управление», «УО (само)», `_org_itself` в UI):
- `_org_itself` → **«Аппарат УО»** (закупки самого управления); в списках — «Аппарат»;
- подведы → **«подведомственные учреждения»** (в БЗ-подсказке: «получатели бюджетных
  средств, ПБС — школы, сады, учреждения культуры…»);
- итог ГРБС → **«сеть УО: аппарат + 47 учреждений»**.

**Правило сравнимости.** УО (сеть ~47 заказчиков) и УИО (только аппарат) в одном рейтинге без
пометки — категориальная ошибка. Каждый рейтинг/сравнение ГРБС несёт состав («аппарат + N
учреждений» / «только аппарат») и режим: «сеть к сети» (по умолчанию, с пометкой состава) или
«аппарат к аппарату» (честное сравнение органов).

**Смежные исправления (полевые наблюдения 2026-07-13, живой UI):**
- «Совместные закупки» живут в данных УО как псевдо-организация в колонке C (165 млн лимита!)
  и сейчас показываются как обычный «подвед» — становятся первоклассной сущностью (совместный
  аукцион N учреждений), не строкой списка ПБС;
- регекс-эвристика самоссылок в OrgStrip (`^администрир|^опека$|^управлен`) даёт противоречия
  («Опека» — то аппарат, то отдельная организация) — заменяется реестром: реальные 77 подведов
  из еженедельного xlsx (лист «ГРБС») + явный признак «аппарат», никаких регексов по именам.

## 19. UX-ресерч: карта всех нажатий (100% охват, требование пользователя)

До переплавки — обязательный деливерабл «**Карта интеракций**»: по живому dev-серверу
(агент-ресерчер с браузером) фиксируется каждый экран × каждый кликабельный элемент × куда
ведёт × что меняет (фильтры/стор/URL) × скриншот. Каждая интеракция получает вердикт:
сохранить как есть / переплавить (куда) / убить (почему). Роль продуктового дизайнера
выполняет цепочка `impeccable-critique` (эвристическая оценка каждого экрана) →

drill-оверлеи — как в §13). Ничего не переплавляется, пока его текущее поведение не
зафиксировано в карте — это и есть механическая гарантия «без регресса и галлюцинаций».
