## 3. Технические уточнения (проверить в коде)

### 3.1 Считается ли сумма по ФБ/КБ/МБ раздельно
Основной отчёт даёт план и факт в разбивке H/I/J и L/M/N. Проверить, что `buildReport`/
проекции dash умеют суммировать деньги в разрезе трёх бюджетов (не только фильтровать).
Если нет — добавить бюджет-осью в проекцию (колонки, а не только фильтр).

### 3.2 Мультиквартальный роллап
`quarterExecution(rows, {quarter})` даёт один квартал. Для «за полугодие» и «Q1+Q2+Q3»
нужна обёртка `periodExecution(rows, {quarters: [1,2,3], year})` = Σ план / Σ факт по
кварталам. Тривиально поверх 1.3, тем же каноническим путём.

## 4. Модуль совмещения / ЕП→ЭА / ОКВЭД — статус выясняется инвентаризацией

Пользователь спрашивал про «модуль предложений по совмещению названий закупок, знающий
ОКВЭД». Допотчёт показывает, что аналитик делает это ВРУЧНУЮ (143 рекомендации, из них
про совмещение разрозненных процедур в единую + замену ЕП→ЭА). Идёт read-only
инвентаризация кода (`recommendations*.ts`, similarity/ОКПД2/ОКВЭД/КТРУ/дробление) —
её результат определит: есть заготовка/заглушка или писать с нуля. Дизайн-решение по
модулю — ПОСЛЕ инвентаризации (не проектировать вслепую). Предварительная форма модуля:
вход — строки плана-реестра (предмет G, сумма K, тип процедуры, ГРБС, бюджет); выход —
кластеры «похожие по номенклатуре, разные строки → кандидат на объединение в ЭА» +
«ЕП выше порога + категория, целесообразная для ЭА → кандидат на замену». Классификатор
категории: если в данных есть ОКПД2/КТРУ — по коду; если нет — по нормализованному
названию (лемматизация + похожесть). Точный механизм — отдельная спека после §4-инвентаря.

## 5. Стратегия надёжной верифицируемой генерации (ключевое требование пользователя)

Принцип: **отчёт = ЧИСЛА (автогенерация, доказуемая) + КОНТЕКСТ (человеческий, захваченный,
НЕ выдуманный).** dash не галлюцинирует нарратив причин — он хранит то, что человек внёс.

### 5.1 Три инварианта кросс-фута (уже проверены на допотчёте — сходятся ТОЧНО)
Проверено вручную по таблице допотчёта:
- **бюджет**: МБ + КБ + ФБ = ВСЕГО (38 587 039,30 + 15 925 072,01 + 3 231 598,58 = 57 743 709,89 ✓);
- **период**: Q1 + Q2 = полугодие (35 696 061,92 + 22 047 647,97 = 57 743 709,89 ✓);
- **агрегация**: Σ по 8 ГРБС = Итого (сумма = 57 743 709,89 ✓; кол-во ЭА 36+25+31+24+25+77+4+71 = 293 ✓).
Эти три семейства тождеств — **обязательные property-тесты** генератора отчёта: любая
проекция обязана их удовлетворять, иначе числа не сходятся по построению.

### 5.2 Три уровня доказательности каждой цифры
1. **Drill-down**: каждое число раскрывается в строки-источники (клик → строки плана-реестра,
   давшие сумму). Нет «магических» чисел без обоснования.
2. **Сверка с официалом**: числа проекции сверяются с ячейками СВОДа (механизм reconcile
   уже сходится 528/528) — второй независимый источник подтверждает.
3. **Кросс-фут-инварианты** (§5.1) — внутренняя согласованность.
Число проходит все три → verified. Не проходит хоть один → помечено «требует проверки»,
не показывается как факт.

### 5.3 Граница авто/человек
- **Авто (генерируется, верифицируется)**: все суммы, кол-ва, проценты исполнения, экономия,
  кандидаты ЕП→ЭА (по порогам), детект сдвига квартала (по истории снапшотов).
- **Человек (захватывается в БД dash, НЕ генерируется)**: причина простоя процедуры («продлён
  срок из-за изменений в документации»), исход рекомендации (принято/отложено/нецелесообразно),
  протокольные формулировки, решения ВКС. Это реакции — вводятся людьми, отображаются как есть.
- **Запрет**: dash НИКОГДА не сочиняет причину/контекст. Пустой контекст = «не заполнено»,
  не выдуманный текст. Иначе теряется доверие (главная ценность продукта — заменить ручной
  отчёт, оставшись точным и честным).

## 6. Куда встраивается в фазы мастер-плана

- Δ1, Δ7, 3.1–3.2 → **фаза 1.4** (buildReport-проекция): добавить бюджет-ось-колонками +
  мультиквартальный роллап + вид «экономия × ГРБС × бюджет × период».
- Δ2, Δ3, Δ8 → **фаза реакций** (БД реакций ГРБС): жизненный цикл рекомендаций + нарратив
  причин + атрибуция экономии рекомендациям.
- Δ4, Δ5 → **фаза сигналов/аномалий**: детект сдвига план-квартала (snapshot-diff) +
  «внесено под факт в окне дат» с суммой МБ.
- Δ6, §4 → **отдельная спека модуля совмещения/ЕП→ЭА** после инвентаризации кода.
- §5 → **сквозной инвариант генератора отчёта**: property-тесты кросс-фута обязательны
  с первой строки buildReport.
