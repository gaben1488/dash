**Рабочая редакция:** `AOPS-2026-10-22.1` · **база источников:** `gaben1488/dash@9d0cedaee51483bc0430200354ba6820a7681295` · **владелец изменений:** основной интегратор проекта.  
**Статус:** предложение правил и результат первой исследовательской итерации, **не** утверждённая миграция скриптов, не изменение production и не замена принятых ADR.

## Назначение и граница

Это маленький *операционный индекс*, не очередной новый «канон продукта». Его назначение — привести к одному проверяемому способу выполнения **изменений в коде, восьми план-реестрах, реестре процедур, справочниках, SQLite, отчётном генераторе, Apps Script и VPS**, когда задачи распределяют между Claude и OpenAI.

- **Постоянные правила** уже остаются в корневых `AGENTS.md`, `CLAUDE.md` и `docs/AGENTS.md`; этот пакет **не копирует** их целиком.
- **Предметные решения** остаются в соответствующих `docs/decisions/*` и подтверждённых контрактах, а первичка — в своих источниках; этот пакет их не перезаписывает.
- **Одна работа = одна задача GitHub + одна ветка/PR + один ответственный интегратор.** Изолированные агенты получают конкретные непересекающиеся зоны файлов; результаты и точные SHA сохраняются до завершения сессии.
- **Производственные источники не редактируются этим пакетом.** До любых будущих write-операций обязательна отдельная проверка согласованного плана, доступа, ревизии и отката.
- **GitHub фиксирует решения, код и след изменений; Drive хранит неизменённые исходники и собранные отчёты; SQLite, защищённые исходные книги и frozen snapshots остаются доказательными источниками своих контуров.** Drive-архив не становится второй рабочей правдой.

## Метод полного чтения 250 `.md`

Чтение контролируется `READING_LEDGER.csv`, а не заявлением «всё знаю». На снимке 22.10.2026 все **250 полных текстов** получены, декодированы и просканированы (10 514 007 байт, 4 662 Markdown-заголовка); SHA-256 каждого сохранён в реестре. Это **100% целостности и первичной индексации, не 100% углублённой семантической экспертизы**. Отдельно проработана предметная методология/ключевые разделы **33** документов; **217** остаются на содержательную повторную экспертизу и проверку связи с кодом. Не называть их прочитанными экспертно заранее.

Пять очередей не требуют загрузки всех 10,5 МБ в память каждого агента:

| Очередь | Файлов | Задача чтения | Результат одной записи |
|---|---:|---|---|
| 00. Методология, ошибки, ответственность | 13 | История неудач, способ координации, что было принято/опровергнуто; **начата первой** | Правило либо отказ от ненужного ритуала, точный источник |
| 01. Действующие контракты и поздние решения | 28 | ADR, эксплуатация, безопасность, исходные поля, события, source IDs | Предметный контракт с версией и статусом: proposed/accepted/verified/unknown |
| 02. Аудиты и QA | 100 | Факты и методы проверки, ложноположительные, дата и основание | Идентичность класса дефекта + тест/сценарий + что уже исправлено |
| 03. Спецификации/исследования | 69 | Не реализованные предложения и их условия, архитектурные альтернативы | Привязка к действующему контракту либо пометка «не внедрено» |
| 04. Планы, архив, учебные и агентные документы | 40 | Невостребованные находки, явно отменённые/превзойдённые планы | Архивная ссылка/открытый блокер; без возврата старого поведения |

Правила прохода каждого файла:
1. Сначала **точная версия** (`path`, blob/`SHA-256`, дата и заголовок); при смене SHA предыдущий смысловой вердикт становится `needs_revalidation`.
2. Прочитать текст целиком по разделам (для длинных файлов — последовательными порциями), выделить только требования/решения/свидетельства, которые меняют техническое действие. Сохранить адрес раздела или цитату длиной до одного предложения; не копировать переписку в новый канон.
3. Присвоить статус **наблюдение / принятое решение / реализовано в коде / сверено на источнике / историческая гипотеза / отменено**. Статус файла не равен статусу всех утверждений внутри: поздние исправления могут отменять его первую половину.
4. Сопоставить с более поздним документом, текущим кодом или владельцем исходного решения. **При конфликте не выбирать по дате автоматически**: написать обе позиции, область применения, требуемый тест и безопасное действие до прояснения.
5. Результат: **изменение существующего конкретного контракта**, один новый отрицательный тест или осознанное `no_action`; никакого второго каталога задач по тем же фактам.
6. После проверки сохранить в строке реестра `read_state=reviewed_core` только если содержательный анализ действительно состоялся; `indexed_fulltext` иначе. После проверки актуальным кодом можно отдельно поставить `source_verified` через новое поле/приложение.

Процесс продолжается следующими итерациями без повторного создания основного архива. Отсутствующие `scratchpad/*`, локальные выгрузки, внешние vault `NOW.md` не выдумывать. В крупных документах отличать записанное наблюдение на историческую дату от результатов живого теста на текущем снимке.

## Что действительно заслуживает автоматизации

Не новый «мозг» для агентов, а пять небольших гарантий:

1. **Версионная граница:** агент перед выполнением сверяет `repo SHA`, PR-head и исходный `spreadsheetId`/sheetId/схему; при несовпадении останавливает запись.
2. **Пакет изменения:** одна заявка GitHub содержит владельца, атомарную зону правки, план/превью, контрольный снимок, негативный тест, согласование, путь отката и прямых потребителей.
3. **Уже существующие следы:** события, `source-integrity` и публикации не дублируются; новые инструменты читают их результаты и показывают *последнюю попытку* отдельно от *последней подтверждённой проверки*.
4. **Сквозная приёмка:** числа и поля план-реестров, процедур, генератора Word, Dash и архивной недели проверяются на одном доказательном срезе, если изменение затрагивает этот тракт.
5. **Передача между агентами:** каждый агент отдаёт не резюме вкуса, а ID задачи, точный SHA, изменённые файлы, пройденные/непройденные проверки, необработанные данные, опасные зависимости и следующий безопасный шаг.

Правила исполнения — в `CHANGE_PROTOCOL.md`. Машинная проверка формы и контрольных хешей — в `tools/verify_agent_ops.py`; она **не** авторизует операции и пока **не подключена к production**. Автоматическое исполнение внешних `write`-запросов без отдельного разрешённого изменения запрещено.

## Лестница дальнейшего совершенствования (без расползания пакета)

**Сразу:** закончить содержательную волну 01, уточнить действительный статус source-integrity в CI/VPS, исключить старые прямые обращения к `Settings` из всех актуальных генераторов, сверить worker #93 и форму release evidence.  
**Далее:** объединить дедупликацию наблюдений с реальными идентификаторами, собрать consumer matrix на схемы и формулы, ввести идемпотентный учёт смены версии для всех записывающих скриптов.  
**Затем:** прикрепить машинный validator к уже имеющемуся CI (`.github/ci/`), не создавая параллельный GitHub Workflow; протестировать конфликтующие PR и rollback, не меняя текущий production по одному успешному тесту.

Вопросы юриспруденции, предложения по облику, прогнозы и исторические непроверенные баги остаются на своих страницах документации и не засоряют протокол изменений. Этот пакет не присваивает себе статус источника истины для предметных данных или решений владельца.

## Подтверждённые внешние ориентиры методологии

- Claude Code: [Memory и AGENTS.md/CLAUDE.md](https://code.claude.com/docs/en/memory), [subagents](https://code.claude.com/docs/en/sub-agents), [hooks](https://code.claude.com/docs/en/hooks). Claude при наличии корневого `CLAUDE.md` **по умолчанию не читает** соседний `AGENTS.md` автоматически: оба правила требуется явно связать или настроить загрузку. Хук не заменяет валидацию в независимых CLI и CI.
- OpenAI: [Iterating Development Workflows](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex) и [Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra): читать **релевантные** документы, не подключать весь исторический корпус к каждому шагу; по умолчанию меньше файлов и правил.
- GitHub: [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). На исследованном GitHub main помечена `protected:false`: правило «только PR» пока **организационное**, а не технически гарантированное; настройку защиты менять отдельно с разрешения владельца.
