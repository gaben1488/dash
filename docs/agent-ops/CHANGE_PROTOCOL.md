# Протокол изменения источников и передачи задач между агентами

**Версия:** `AOPS-2026-10-22.1`. Этот документ дополняет `AGENTS.md`, `CLAUDE.md`, решения в `docs/decisions/` и `docs/superpowers/specs/2026-08-22-mandate.md`, а не заменяет их. Для действий над реальными источниками нужен отдельный утверждённый план.

## 1. Один интегратор, один предметный контракт, много помощников

Агенты Claude/OpenAI имеют равную исследовательскую ценность, но **не равные полномочия на запись**. Один интегратор владеет задачей, разрешением на изменение, очередью PR и контрольными снимками; остальные получают либо **read-only исследование**, либо **независимые файлы в своей ветке**. Не использовать общее dirty-дерево, stash или рабочий файл у нескольких агентов одновременно. GitHub Issue/PR — единый адрес задания и результата. Частный транскрипт, чат и autosaved memory не являются принятой работой.

**Выбирай самого дешёвого исполнителя:** одна локальная проверка или grep вместо субагента; параллельный агент оправдан только независимой зоной и сформулированным выходом. Каждый помощник перед завершением записывает находки в свой файл/комментарий PR, не ожидая конца всей цепочки. Интегратор отвечает за принятие или мотивированный отказ от каждой находки, чтобы не повторился августовский урожай потерь.

## 2. Оси состояния — не единый флажок «готово»

| Измерение | Различаемые стадии | Что служит доказательством |
|---|---|---|
| Документы/решение | `proposed`, `accepted`, `superseded`, `unknown` | автор и дата решения, scope, точный исходник/ADR |
| Код | `not_started`, `branch`, `tests_exact_head`, `merged` | PR URL, head SHA, список проверок, merge SHA |
| Данные | `not_checked`, `snapshot_captured`, `same_snapshot_verified`, `blocked` | полные идентификаторы источников/ревизии и воспроизводимая сверка |
| Выпуск | `not_deployed`, `deployed`, `readback_verified`, `rolled_back` | release SHA, timestamp, API/worker/файлы, факт отката |
| Приёмка | `pending`, `accepted`, `rejected` | документированная приёмка того, что увидел владелец/ответственный |

**Инвариант:** `merged` без `deployed` и `readback_verified` не превращать в «исполнено на production». `readback_verified` не гарантирует предметную правильность без независимой сверки. Неприменимую ось помечать `N/A` с причиной, а не `PASS`.

## 3. Два типа операций

**А. Код / документация — по PR:** Issue → выявить актуальные задания и перекрывающиеся PR → фиксированный исходный commit → characterisation/отрицательный тест → change diff → lint/typecheck/tests + специальный гейт → независимый review → разрешённый merge → проверка `deploy_scope` → фактический deploy/readback при затрагивании runtime. Изменение `docs/`, корневых `AGENTS.md`/`CLAUDE.md` сейчас распознаётся `.github/ci/deploy_scope.py` как не-runtime, но это проверять на exact-head; изменение неизвестного пути считается runtime. **Не менять main напрямую, не обходить хуки `--no-verify`.**

**Б. Действующие Google Sheets/Apps Script/SQLite — отдельная транзакция:**

1. Снять идентификаторы (fileId/spreadsheetId + sheetId, диапазон, рабочие заголовки/ширину, source-schema SHA или etag/revision), зафиксировать исходный набор строк, формулы, валидации, граф внешних потребителей, часовой пояс. **Имя вкладки не идентификатор**.
2. Сгенерировать *read-only* diff `before → proposed` + негативный сценарий «что не трогаем». Обнаружить разнородные исторические схемы, старые имена и автоматические зависимости (bound Apps Script/triggers, клиентский код, отчётный Python, SVOD mirrors). Не подменять пустой ответ Google уверенным «нет зависимостей».
3. Получить конкретное разрешение на данный diff; сохранить независимый неизменяемый снимок / резервную копию и описать откат. Для удаления или смены схемы нужен возврат из копии без догадок.
4. Перед записью повторно сравнить прочитанный revision/hash с планом: drift ⇒ **abort**, новый diff и согласование. Ограничить batch ровно адресами плана, запретить автоматическую запись в формульные и архивные поля, сохранить историю и пользовательские комментарии.
5. После записи readback того же диапазона и потребителей на одном срезе; проверить число исходных строк, суммы K/Y/AC, формулы N/Q→O/P/R/S, нативные validations, старые/новые имена и состояние `_ChangeLog`; отдельный тест Apps Script delivery/queue, не только наличие листа.
6. Если какое-либо доказательство отсутствует, отметить `blocked`; предыдущий рабочий выпуск и историю сохранить. Не повторять попытку бесконечно; не считать аварийную пустоту нулём. Для source integrity показывать две временные оси: *latest attempted check* и *last confirmed result*.

**Критический реальный пример:** `docs/TECHNICAL_SHEETS_COMPATIBILITY_2026-10-10.md` (заключительный раздел 11.10) удостоверяет физическое удаление `Settings`, `Контроль`, `_Справочник` в восьми книгах, с сохранением `СИСТЕМА`, `_Настройки`, `_ChangeLog`. При этом `scripts/etalon-sync/canon.cjs:239` на текущем Git-срезе всё ещё генерирует ссылку на `Settings!$B$6`, а `apply.cjs` обращается к `Settings!B3`. **Запрет запуска `etalon-sync/apply.cjs` по старому контракту на production-книгах** до read-only сверки всех волн и адаптации ссылок на единственную опору. Не восстанавливать старые листы автоматически ради совместимости.

## 4. Машинный пакет передачи (один на изменение)

Передавать в PR/Issue структурированную карточку с полями:

```json
{
  "change_id": "issue-123",
  "repo_sha": "<40-символьный SHA исходного commit>",
  "owner": "роль/аккаунт интегратора",
  "agent": "Claude или OpenAI — исполнитель",
  "kind": "code",
  "stage": "branch",
  "scope": ["packages/server/src/services/название.ts"],
  "reason": "Какой класс дефекта и из какого требования",
  "diff_ref": "ссылка на PR, commit или зафиксированное сравнение",
  "tests": { "command": "команда", "result": "passed | failed | not_run" },
  "evidence": {},
  "remaining_risks": ["Незакрытая зависимость"],
  "next_action": "Один конкретный безопасный шаг"
}
```

Это шаблон: placeholder `<...>` нельзя передавать как факт. `kind = docs | code | source_write | production_release`. `stage = proposal | branch | ci_verified | source_verified | deployed | accepted | blocked`. У `source_write` пакет дополнительно содержит **source_guard**: `source_id`, `source_revision`, `snapshot_before`, `approved_plan`, `rollback_ref`, `consumer_matrix`. У релиза — `release_evidence`: точные build/deploy SHA, CI, backup, readback и rollback. У `accepted` обязателен `acceptance_ref` настоящей приёмки, не подпись самого агента. Инструмент ниже структурно проверяет пакет, но ссылки и сами факты дополнительно проверяет интегратор.

**Пример вызова:** `python docs/agent-ops/tools/verify_agent_ops.py handoff путь/к/пакету.json`.

Формирование промежуточного результата допустимо на стадии `blocked`: сохранённые наблюдения и next_action ценнее незавершённого несохранённого исследования. Новую задачу не открывать, если она уже является пунктом существующего Issue/PR; зарегистрировать зависимость на текущем ID.

## 5. Протокол чтения документов для порученного агента

Перед назначением темы интегратор выбирает файлы из `READING_LEDGER.csv` по волне/смыслу, а не выдаёт агенту весь архив. Исполнитель не переписывает прочитанный документ в новую заметку: фиксирует **факт/вердикт + физический источник/раздел + статус источника + конкурирующую более позднюю трактовку + затрагиваемый код + проверку**. Если актуальный смысл нельзя установить без закрытого Google-источника, статус `NEEDS_SOURCE_READBACK`, не «готово». После содержательного прохода меняется конкретная запись `read_state`, без инвалидации SHA.

Интегратор сравнивает пересекающиеся выводы двух агентов: при конфликте нужны 1) обе точные версии источника, 2) одна проверка, способная различить гипотезы, 3) безопасное действие до проверки. **Более новый текст не заменяет историю решения; он обозначает новый срез и причины изменения**.

## 6. Эксплуатационная проверка и принципы отказа

- Хранилище истории — единственное: SQLite/source-history/авторитетный `_ChangeLog` остаются на своих местах; новый файл не дублирует события строк закупок. Любая попытка доставки и подтверждённый вердикт должны переживать рестарт; `persisted:false` нельзя выдавать за успешную проверку.
- Недельный снимок четверга `Asia/Kamchatka` не подменять ближайшим; версию правил и источников хранить с выпуском. Пятничный Word не меняет первичку задним числом.
- Не путать историческую рекомендацию, текущую идентичность, результат торгов и исполнение договора/оплату. Сомнение выражать `unknown` и объяснением, а не успешным статусом.
- Наблюдение о структурной целостности формул — не доказательство арифметики; совпадение зеркал — не доказательство итогов; зелёный CI — не выпуск; приложение `СИСТЕМА` — не наблюдение доставки уведомлений.
- Сбой сохранения, изменение исходной ревизии, пропавший обязательный источник, повреждённая история и неопределённый доступ останавливают соответствующее действие. Отказ логировать с причиной и ссылкой на последнюю подтверждённую версию. Чтение текущего Dash может продолжаться с явной оговоркой.
- Доказательство «принято» должно отвечать на 5 вопросов: что реально изменено, на какой версии, чем проверено, какой пользовательский эффект, какой обратимый путь.

## 7. Минимальный путь внедрения

**Сейчас — только документы + локальный validator и тесты.** Никаких данных пользователя и секретов в Git. Это можно включить отдельным docs-only draft PR без изменения CI/деплоя.  
**Следующее независимое изменение после ревью:** привязать validator к действующему CI через существующий `.github/ci` и добавить отрицательный тест на неполный пакет, не добавлять ещё один workflow.  
**Отдельное изменение по источникам:** устранить текущие прямые обращения к удалённому `Settings` в `etalon-sync`, восстановить тесты изменения/отката и получить разрешение на реальную миграцию.  
**Отдельная эксплуатация:** проверить GitHub protection/review правила, фактические Apps Script и два цикла отчётного worker на действующем томе. Документационный PR их не решает.
