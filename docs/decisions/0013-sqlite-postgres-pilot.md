# ADR-0013 — C08.14: SQLite WAL и PostgreSQL для Dash

**Решение от 22.10.2026:** сохранить SQLite WAL как каноническую рабочую БД Dash; миграцию на PostgreSQL **не начинать**. Это решение о сохранении проверенной архитектуры при текущей нагрузке, а не утверждение о технической непригодности PostgreSQL. Повторное рассмотрение возможно лишь по результатам парного реального replay, проверенного backup/restore и положительного измеримого эффекта.

**Контур:** современная интеграция PR #79. Старый main, реальная Google-таблица, рабочие БД, weekly/Word archive, report-worker и VPS этим изменением не модифицируются. Ни один synthetic PASS не означает production-приёмку.

## Текущее состояние и основания

Приложение использует better-sqlite3 + drizzle-orm/better-sqlite3 (packages/server/src/db/connection.ts), WAL, busy_timeout=5000, synchronous=NORMAL, foreign_keys=ON. Это один writer с несколькими readers; сохранены большие JSON snapshots, журнал замечаний и решений, webhook queue, источники Google, отдельный Word/report-worker. PostgreSQL мог бы дать выигрыш при нескольких активных писателях, но это пока непроверенная гипотеза и сама по себе не обосновывает перенос всех схем/данных.

В docs/PLAN.md присутствуют read-only измерения на копии рабочей SQLite БД объёмом около 478 MB с 17 снимками: после адресного индекса тяжелый metadata/retention selector уменьшился примерно с 3,1 секунды до 4 мс. Эти измерения относятся к конкретному SQL и копии, не к общему p95 всего Dash. Исторические timeout могут включать Google, JSON, расчёты, Word, API и диск; смена БД без профиля причины не оправдана. Производственного PostgreSQL-профиля в доступных доказательствах нет.

## Реализованный изолированный пилот

- scripts/db-pilot/compare.py: одинаковый детерминированный JSON payload для SQLite и PostgreSQL, 17 снимков, 3 000 замечаний и очередь по умолчанию. Замеряются четыре действительно используемых класса SQL: latest snapshot head; issues pagination; выбранная полная JSON detail; pending webhook queue. Синхронная серия фиксирует p50/p95/max; многопоточная — 8 читателей плюс 1 writer, p95, ошибки и фактическое wall time. Дополнительно байты диска и peak RSS клиента.
- SQLite WAL: база создаётся только в TemporaryDirectory, PRAGMA соответствует текущему подключению Dash. Выполняется online sqlite3.Connection.backup, в новой базе построчно вычисляется SHA-256 всех таблиц; содержание сравнивается с источником, не только количество строк.
- PostgreSQL 16: подключение разрешено только к одноразовой отдельной DB с точным именем bench_c08_14. Таблицы создаются в случайной схеме bench_c08_14_*. Выполняется отдельный pg_dump (custom), CREATE DATABASE bench_c08_14_restore_*, pg_restore, повторное полное хеширование и удаление временной БД/схемы. Ни SSH, ни производственные учетные записи или источники не используются. При несовпадении restore/данных проверка FAIL.
- scripts/db-pilot/decision.py: проверяет эквивалентность полного начального fingerprint, seed и параметров, независимое восстановление каждой БД, отсутствие ошибок конкуренции. При несовпадении отвергает сравнение. Результат всегда production_approved=false, migration_approved=false.
- .github/workflows/db-engine-pilot.yml: PR/ручной запуск в одноразовом GitHub-hosted окружении с Postgres service и отдельным артефактом агрегированных JSON. В этой workflow нет deploy, подключения VPS и переноса бизнес-данных.
- scripts/db-pilot/test_pilot.py: локальные negative-тесты отказа подключения к чужой DB, неподтверждённого restore, расхождения параметров, устойчивости SHA и полноты локального цикла SQLite.

## Граница доказательств

Синтетическая нагрузка — не реальный PostgreSQL-пилот на рабочем содержимом. Python sqlite3 и psycopg не являются драйверами Node сервиса (better-sqlite3); у SQLite в отчёте учитываются db/WAL/shm, у PostgreSQL — отношение и индексы, а pg_dump custom и SQLite online backup имеют разную степень сжатия. Клиентский peak RSS исключает память процесса PostgreSQL. CPU, диски и RTT GitHub runner не равны VPS. Эти факты явно указываются в артефакте, абсолютные синтетические значения нельзя выдавать за ожидаемую задержку production.

Полноценная предметная приёмка C08.14 требует:

1. **Exact-head парный CI:** одинаковые seed/числа/хэши, 0 concurrency errors, обе восстановленные базы сравнимы, сохраняются измерения p50/p95/RSS/disk. Если run skipped/failed — не считать пройденным.
2. **Реальная изолированная копия:** с санкционированного постоянного тома снять согласованную online SQLite+WAL копию; без изменения живых данных повторить выборки current/history/journal/queue/issue decisions при 1/4/8/16 readers + writer, cold/warm, p50/p95/p99, IO и memory. Аналогичный обезличенный вход развернуть в PG и проверить одинаковые read/write ответы. Реальное чтение должно быть привязано к snapshot и полному version manifest; никаких скрытых переключений источников.
3. **Безопасность и стоимость:** проверить восстановление целостности, replay решений/UID и трёх Word, работу двух последовательных worker cycles, совместимый image+data rollback и время/память/место резервирования. Сравнить ежедневную эксплуатационную цену дополнительного сервиса, мониторинга, апгрейдов, репликации и бэкапов.
4. **Критерий пересмотра:** преимущество PostgreSQL должно подтверждаться на узком реальном проблемном запросе/конкуренции писателей, быть существенным для установленного SLO и превосходить стоимость миграции и восстановления; иначе SQLite остаётся решением. Новое измерение при росте числа писателей/объёма или SLO — легитимный триггер, не бесконечный аудит.

Зависимости из реестра: C08.15, C08.16, R07.01. Никакой перенос на PostgreSQL, второй бизнес-реестр, новый worker или production-выпуск не входит в этот PR.

**Статус фиксации:** программа измерений и негативные проверки готовы. Результаты парного CI и реального read-only replay должны добавляться как датированные доказательства по exact SHA, а не приписываться без запуска. До этого задачa не объявляется полностью принятой в эксплуатации.
