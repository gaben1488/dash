# ADR-014 — C08.02: границы расчётного контекста и взаимосвязей Dash

Статус: **рабочий контракт для PR #140, не эксплуатационная приёмка**.
Основание: выбранная задача 13/20, `docs/PLAN.md`, существующие `CalculationContext`,
`getSnapshot`, `withPersistedDecisions` и независимый frozen-публикатор 3 Word.
База: современная интеграционная линия #79, не устаревшая `main`.

## Что именно является одним результатом

- **Capture:** фактически полученные строки, формулы, версия/время источника,
  схема и сопоставление листов. Недоступный, устаревший и реально пустой источник
  — разные состояния; `null` нельзя превращать в наблюдаемый `0`.
- **Calculation:** неизменяемый `CalculationContext` v1: fingerprints исходных
  значений/профилей; версия реализации и правил; frozen-пороги с редакцией;
  фактический `asOf` и расчётный день Камчатки; годовой scope. Его `id`
  относится к *базовому* расчёту, а не к логину пользователя или UI-фильтру.
- **Readiness:** источник и контекст проверяются **оба**. Только совместимый
  снимок того же source-generation и product-day разрешён как `ready`.
  При расхождении старое значение может быть показано только с явным
  `refreshing`/`stale`, с исходным временем и без ложной оценки полноты.
- **Projection:** решение человека и выбранный фильтр накладываются на
  захваченный результат отдельно. `decisionView.revision` — производное
  состояние запроса; изменение решения не переписывает исходный snapshot.
  `decisions: not-applied` и `access: full-dataset` обозначают только
  стадию базового расчёта, **не доказывают авторизацию конечного ответа**.
- **Publication:** опубликованный Word/исторический снимок связан с собственным
  frozen input, правилами и release ID; следующий live snapshot не меняет его
  задним числом. Паритет Python/TS нельзя приписывать одному только `id`.

## Матрица инвалидации

| Изменилось | Обязательно проверить/пересчитать | НЕ делать автоматически |
|---|---|---|
| Значение/формула, версия листа, схема, source binding | affected capture; source receipt; базовый расчёт и зависимые показатели | сбрасывать все листы и историю без evidence |
| Код расчёта, редакция правила, нормализация, словарь порогов | базовый расчёт; проверку семантики, edition и времени правила | приравнивать неизвестную норму закона к проверенной |
| Расчётный день Камчатки (UTC+12), Q/N и календарные условия | применимость календарных выводов и вычислений; текущий ready-кэш | переписывать историческую дату, публиковать Word без нового выпуска |
| Год, период, activity/method/budget/org, источник | точность выбранного scope и проекции; version-bound API/ссылку | отдавать соседний год или личный фильтр из общего кэша |
| Решение по сигналу, статус, комментарий | `decisionView`, Trust/сигналы нужного запроса | мутировать sealed raw/ID контекста, удалять старое решение |
| Роль/права, сессия | доступ к конкретной проекции до ответа | считать `full-dataset` доказательством полномочий пользователя |
| Новый live вход при открытом архиве | только живую проекцию/последующий выпуск | подменять исторические числа текущими |
| Сбой Google, SQLite, worker или неполный контекст | explicit stale/refreshing/503 + существующую coalesced очередь | `ready`, `0`, массовый retry или новый worker из UI |

Смена суток в текущем ограниченном исправлении инвалидирует базовый
календарно-зависимый ready-кэш *консервативно*. Это безопаснее ложной
актуальности, но **не доказывает** минимальный набор зависимых вычислений.
Следующее уточнение R05.04 должно переиспользовать неизменные sealed
исходные значения без лишнего обращения к Google, с доказательством
совместимости формул, source receipt и правил. Не вносить псевдокэш,
пока такого доказательства нет.

## Конкретный сквозной разрыв, исправленный в PR #140

В `routes/analytics.ts` четыре маршрута (`compliance`, `anticorruption`,
`scorecard`, `anomalies`) прежде совмещали `snapshot.recalcResults`
и изменяемый `getDeptSheetValues()`. При смене одного источника это две
независимые ревизии. Теперь эти маршруты берут строковую базу только из
`snapshot.rowsByDept`, захваченную самим расчётным снимком. Физическая
нумерация остаётся +3 строки шапки; известная пустая книга = `[]`, а
отсутствие захвата возвращает явный отказ, не «нулевую аналитику».
Новых чтений Google и пересчётов такой переход **не добавляет**.

`ep-reasons`, `subjects` и `centralization` пока работают со своим
live-кэшем, без `recalcResults` смешанной версии; нужно отдельно
проверить их readAt/scope и связь с другими карточками. Нельзя объявить
полный паритет всех аналитических маршрутов по четырём исправлениям.

## Границы потребителей, которые должны пройти совместную приёмку

| Потребитель | Проверяемый инвариант | Состояние |
|---|---|---|
| `snapshot.ts` → `dashboard.ts`, `metrics.ts`, `analytics.ts` | один контекст на выбранный snapshot; неполный input не становится числом | адресный C08.02 guard в PR #140; **не общий PASS** |
| Экраны Dash и разрезы ГРБС/года/организации | повтор клика/фильтра не смешивает `snapshotId` и значения; понятный stale | нужна матрица API + browser |
| `issue-decisions.ts` → Dashboard, Trust, Report | изменение статуса видно в живой проекции без переписывания архива | существующий overlay; нужна сквозная приёмка |
| Единый расчёт TS ↔ Python report engine | одинаковые frozen строки/единицы/методика/asOf; отдельно проверить 3 Word | отдельные source-parity и Word gates, не доказаны этим PR |
| Сохранённые снимки/история/релиз/worker | архив воспроизводим; отказ не удаляет prior release; image+data rollback | #93/#119, production **BLOCKED** |

## Минимальный допуск для C08.02

1. Тесты на real `CalculationContext`: same-day reuse, UTC 11:59:59→12:00:00
   как границу Камчатки, rule/source/threshold/scope/clock/decision/access
   mismatch, битую/отсутствующую запись и неизменяемый исторический replay.
2. Cache/read-model: `ready` лишь при совпадении generation + контекста,
   stale/retry bounded, concurrent GET не порождают два чтения, старый SQLite
   результат не выдаёт успешный Trust при недоступной первичке.
3. Контекст и decision overlay проходят API на одном реальном frozen
   источнике; для каждого изменения проверяется верная причина недоступности.
4. Та же выборка проверена в карточке, таблице, графике и всех 3 Word;
   точный release/source и допустимость контекстов наблюдаются независимо.
5. Exact-head lint, TS, tests, build, source integrity, worker continuity,
   backup+isolated restore и live authenticated desktop/mobile/API/Word readback
   по #93/#119. Skipped/недоступный этап не равен `PASS`.

Не расширять этот PR заменой всех кэшей, новой БД, фоновыми poller'ами,
дополнительными идентификаторами в пользовательских таблицах или
автоматическим переходом на новый релиз.
