# ADR-001: Проверенный выпуск отчёта как неизменяемый комплект

Статус: принято для реализации; производственное включение требует сквозной приёмки.
Дата: 2026-09-30.

## Контекст

Задача владельца — автоматический выпуск основного документа, дополнения и
согласованного среза дашборда. Существующий Python-генератор v1.4 формирует
ReportModel и документы; TypeScript `/api/report` показывает оперативные данные.
Переписывание расчётов при переносе потеряет уже проверенные предметные правила.
Проверенный выпуск должен переживать сбой, повтор запуска и изменение источников.

## Решение

Сохранить исходники Python-генератора в `packages/report-engine`. Перенос не
включает реальные выгрузки, реестр рекомендаций, SQLite или готовые документы.
Эти входы и результаты хранятся в закрытом постоянном каталоге сервера.

Публикация принимает комплект, проверяет разрешение предметных проверок,
независимый аудит, контрольные суммы документов, точное совпадение проекции
дашборда с ReportModel и барьер версий источников перед выпуском. Документы
содержат манифесты с хешем модели и собственным хешем файла.

Комплект копируется в закрытый временный каталог на том же файловом разделе,
проверяется, синхронизируется и переименовывается. Лишь затем транзакция SQLite
делает его видимым. Сбой до транзакции оставляет невидимый каталог, пригодный
для проверки и повторного завершения. Уникальный хеш модели предотвращает
дубли. Предыдущий проверенный выпуск остаётся доступным с исходной датой.

Оперативный API не называется опубликованным отчётом. Представление выпуска
читает сохранённую модель без повторного расчёта показателей. Существующие
предметные блокировки v1.4 не снимаются инфраструктурой публикации.

## Альтернативы

Переписать расчёты на TypeScript — отклонено: неоправданная повторная реализация.
Заменять документы по одному — отклонено: пользователь может получить смесь выпусков.
Считать успешный DOCX разрешением публикации — отклонено: вёрстка не подтверждает данные.

## Последствия

Нужен Python 3.11+ и python-docx в среде генерации. Рабочая среда публикации —
Linux с локальным постоянным томом; сетевой файловый раздел не поддерживается.
Резервное копирование должно включать каталог комплектов и SQLite согласованно.
Нельзя отмечать продукт готовым до рабочего расписания, подключения закрытых
входов и положительной приёмки реального выпуска.

## Доступ и расписание

Fastify вызывает установленный CLI через execFile без оболочки. Чтение выпуска
остаётся в Python: проверка SQLite и контрольных сумм не дублируется в TypeScript.
Адрес документа содержит release_id, поэтому два последовательных скачивания
не переключаются на разные выпуски при фоновой публикации. Выдаются только
два документа и сохранённая проекция дашборда; исходные снимки не раздаются.

Периодический worker работает в том же образе, отдельным процессом Docker Compose,
использует существующие переменные сервисного аккаунта и постоянный том. Профиль
reports включается после размещения закрытых входов и сквозной приёмки. Ошибка
одного запуска сохраняется в status.json и не прекращает следующие попытки.
Управляемый интервал отсчитывается после завершения попытки; на старте процесс
выполняет попытку сразу. Остановка прерывает ожидание, текущая попытка ограничена
таймаутами сетевых запросов; атомарность комплекта защищена публикационным шлюзом.

## Дополнение 11.10.2026: объём хранения и резервирование

Владелец разрешил сокращать старую историю ради устойчивой эксплуатации.
Это не разрешает удалять её до проверки восстановления. Новые машинные
JSON записываются компактно и потоком; значения и семантические хеши не
меняются. Уже опубликованные файлы этой правкой не переписываются.

Допускается дополнительный формат полной резервной копии: закрытый gzip/tar
с точным файловым манифестом, владельцами, режимами, SQLite/WAL и документами.
Исходный формат 1 остаётся совместимым. Формат 2 проверяется полным
восстановлением в отдельном каталоге, всеми файловыми хешами, SQLite integrity
и структурой DOCX; один хеш архива не является проверкой восстановления.
Запись архива ограничена свободным местом с резервом, источник сравнивается
до и после копирования. Оба писателя остановлены вызывающим оператором.

Изолированное восстановление может выполняться на другой машине с достаточным
местом. Перед выпуском требуется заново сравнить остановленный источник с
проверенным манифестом. Действующий локальный release gate пока не поддерживает
удалённое свидетельство: до реализации и проверки всей цепочки сжатая копия
сама по себе его не открывает. Архивы и манифесты не публикуются в GitHub;
передача только по приватному защищённому каналу.


## Уточнение владельца 12.10.2026: недельная история и отдельная скорость UI

Старые частые снимки владельцу не нужны; целевая история — недельные срезы.
Текущая рабочая версия и предыдущая для отката являются ограниченными
операционными исключениями. Последнее указание разрешает удалять избыточные
исторические комплекты; требование полной проверенной копии перед deployment
сохраняется. Удаление не должно оставлять запись каталога, указывающую на
отсутствующий комплект, или потерять данные для восстановления идентичности.
Сначала проверяются недельные источники, каталог и сохранённые сигнатуры;
исходные книги, RAW, ledger и экспертные решения не относятся к мусору.

Штатное удержание полных transient attempts сокращается с 12 до 2; текущая
попытка и защищённые недельные источники сохраняются прежним алгоритмом.
Выполненная разовая live-очистка не равна внедрению новой штатной политики.

Оптимизация времени загрузки страниц, таблиц и API ведётся отдельно от
минимизации диска: она требует собственных baseline, нагрузочных замеров и
проверки времени ответа/рендера. Уменьшение объёма хранения её не закрывает.


Перед удалением sealed исторических доноров требуется доказать, что
identity.sqlite хранит все производные plan/entity signatures для их snapshot
IDs. Read-only census12.10 выявил8126 NULLзначений. Для восстановления
переиспользуется строгий IdentityStore.backfill_plan_signatures: полное покрытие
locator, исходный fingerprint и UID должны совпасть; обновляются только NULL
метаданные. Frozenresults и экспертные решения не переписываются. Explicit
список targets расширяет существующий recovery, не меняя обычный latest/chain
режим. Missingdonor остаётся блокером; нужен и счётчик unrecovered=0, и повторный
NULLcoverage=0. До liveизменения identity — privatebackup и scratchrestore.


## Пересмотр 12.10.2026: общий вход Dash/Word и минимальное хранение

Статус этого раздела: проект перехода, реализация и live-миграция не выполнены.
Последнее требование владельца: одна система данных для Dash и отчётов;
сохранять изменения вместо полных копий при обновлении. Недельная история
остаётся обязательной, но недельный срез не обязан быть отдельной полной копией.
Этот раздел меняет целевой способ хранения ADR-001/ADR-010; прежние форматы
остаются читаемыми до проверенной миграции. Сама проверенность выпуска сохраняется.

### Подтверждённая причина объёма

На a456ae46 read-only rehearsal38167757661: published=18 177 708 KiB.
Последний release: 298 213 451 байт; snapshot_bundle=128 471 852 байта;
identity.sqlite=7 430 144 байта; main/management DOCX=107 508/64 891 байт.
Два документа вместе составляют около 0,058% этого выпуска. Это не замер
третьего DOCX и не полная разбивка остальных файлов.

Dash `snapshot.ts:saveSnapshot` записывает полный PipelineSnapshot JSON,
metric_history и procurement_rows в одной транзакции. Python `runtime.run_once`
сам читает Google; `raw_pipeline.build_from_capture` сохраняет исходный bundle,
ReportModel и производные JSON; `PublicationStore.publish` копирует candidate
целиком. Поэтому согласованная report/dashboard projection внутри Python-выпуска
ещё не означает общего source revision со всеми оперативными экранами Dash.
IdentityStore.backup_snapshot уже ограничивает identity proof одним snapshot:
повторно исправлять его как «копию всей продольной базы» неправильно.

### Выбранный подход и альтернативы

Цель — общий журнал версий источников плюс дедупликация неизменившихся данных,
проверяемые изменения и ограниченные контрольные точки восстановления.

* Только сжать и проредить нынешние комплекты — полезный первый этап, но
  сохраняет два чтения источников и повторные representations.
* Общая версионированная первичка с изменениями и лёгкими ссылками выпусков —
  целевой подход; совместимые readers позволяют переносить потребителей поэтапно.
* Полный business event sourcing, новая NoSQL-система или отдельная streaming
  платформа — не обоснованы текущими замерами. Внешнее изменение ячейки является
  наблюдаемым изменением, а не доказанным заключением/оплатой/отменой закупки.

SQLite/PostgreSQL — отдельное решение C08. Перенос в PostgreSQL сам по себе
не прекращает копирование JSON и не создаёт постоянную историю: MVCC старые
версии очищаются. Новый storage contract не зависит от конкретного SQL engine;
миграция выбирается после замеров конкуренции writers, запросов и восстановления.

### Контракт общего входа

Один координатор приобретает полный зарегистрированный набор источников.
Переиспользуются существующие source-refresh, Drive revisions и report capture
barrier; неполное чтение не продвигает текущую подтверждённую версию. Источник
не обещает глобальную транзакцию Google: версии обязательных книг проверяются
до/после acquisition, затем перед продвижением версии. Formula/raw/display
values, headers/schema fingerprint, sheetId/fileId, ledger и review revisions
сохраняются раздельно и связываются манифестом, а не выводятся из одинакового имени.

`source_revision` — внутренняя версия наблюдаемого состояния; существующие
snapshot_id/release_id сохраняются через соответствие. Новых колонок или ID
в рабочих Google-книгах нет. Вектор source versions, cutoff, полнота чтения,
применённая схема и исходные checksums входят в commit версии.

Dash, история, контроль и Python report-engine читают один sealed source revision.
Разные периоды/фильтры разрешены и названы явно; они не создают новую первичку.
Live head и ранее проверенный report release могут отличаться, если новые данные
ещё не прошли проверки. UI показывает обе версии и причину отставания; тихая
подмена версии документа свежими данными недопустима. Расчётные модели сохраняют
свою предметную семантику до доказанной parity, а не механически заменяют Python
TypeScript-формулами или наоборот.

### Что хранить

1. Текущее индексированное состояние для быстрых запросов.
2. Неизменившиеся исходные значения/фрагменты — один раз по checksum. Новая версия
   содержит ссылки на прежние фрагменты и только реально изменившиеся значения.
3. Изменения с parent revision, before/after checksum, типизированными значениями,
   источником/координатами, временем наблюдения и автором только при доказательстве.
   `0`, отсутствие, пустая строка и false не склеиваются. Формула и её вычисленное
   значение — отдельные факты. No-op обновляет freshness, но не дублирует payload.
4. Недельные маркеры по Камчатке — ссылки на завершённую версию. Для ограниченного
   времени восстановления сохраняются периодические checkpoints; частота и
   предел цепочки выбираются замером, а не бесконечной цепочкой от первого дня.
5. Ledger, решения человека, наблюдения идентичности и доказательства этих решений.
   Доказательство конкретного решения не удерживает весь снимок, если выделенный
   минимальный proof полностью сохраняет его контекст и неоднозначность.
6. Выпуск — ссылки на source revision, модель/правила/renderer, выбранный период,
   frozen review evidence и проверки. Построенная модель хранится один раз;
   dashboard/diagnostic projections выводятся из неё либо имеют ограниченный cache.
   Исходные bundles и копии identity DB не вложены заново в каждый выпуск.
7. Уточнение владельца 12.10.2026: Word скачивается кнопкой в браузере,
   постоянный архив всех DOCX на VPS не нужен. Целевой путь — генерация по запросу
   из выбранной подтверждённой версии/недельного среза и короткий автоматически
   очищаемый cache. Повторные запросы одного контекста используют одну задачу;
   HTTP202 означает ожидание, скачивание разрешено после терминальной проверки.
   Дата, год, квартал и версия источника фиксируются до генерации. Истёкший cache
   не делает сохраняемый источник повреждённым и не подменяет его свежим Google.
   Byte-identical DOCX не обещается без проверки renderer/шаблонов/ZIP metadata.
   Старые download routes сохраняются совместимыми; до подключения on-demand
   reader нельзя просто удалить файлы, которые текущий каталог считает доступными.
   При намеренно удалённой ежедневной первичке UI честно сообщает невозможность
   повторной генерации. Это уточнение заменяет постоянное хранение всех выданных
   документов; текущая одноразовая compaction временно сохраняет дешёвые artifacts.

Сдвиг/удаление строк, изменение номера и смена схемы не решаются fuzzy matching.
Хранение восстанавливает точную матрицу книги; спорная бизнес-идентичность остаётся
отдельным экспертным решением. Если структурная patch не доказана, сохраняется
новая версия соответствующего листа/фрагмента, а не ошибочный компактный diff.
Переименование не создаёт новое юридическое лицо; schema aliases сохраняют историю.

### Атомарность и очистка

Изменённые immutable фрагменты записываются и проверяются до commit metadata.
Транзакция фиксирует parent, изменения, root checksum и head; повтор одной версии
идемпотентен. Незавершённые записи невидимы. Parent mismatch/изменение источника
блокирует продвижение, прежняя подтверждённая версия остаётся читаемой.

GC удаляет только объекты, недостижимые от live/rollback head, недельных маркеров,
выданных releases, сохраняемых source revisions и экспертных proofs. Checkpoints
не удаляются при живых dependent deltas. Сначала строится и проверяется замена
цепочки, затем атомарно меняются ссылки, затем удаляются недостижимые bytes.
Старые ненужные daily releases допускаются к retirement по указанию владельца;
каталог и файлы сокращаются согласованно. Retirement атомарно снимает именно
разрешённые strong roots. Сохраняемый воспроизводимый выпуск удерживает нужную
версию источника; документ из сознательно удалённой истории хранит свой файл,
checksum и сведения о происхождении, но не обещает повторный расчёт и не удерживает
автоматически весь старый граф. Reader явно сообщает отсутствие исходной истории.
Минимальные экспертные proofs остаются strong roots; их объём и достаточность
проверяются отдельно, включая контекст неоднозначных строк. Резервирование retained state и
проверенное восстановление остаются условием deployment.

### Исполнительные этапы и приёмка

A. Завершить уже подготовленную разовую cleanup: восстановить derived signatures,
удалить лишние daily catalog entries/bundles, подтвердить retained weekly/current
readback. Это не ждать полной архитектурной миграции.
B. Ввести общий immutable source contract и reader для старого bundle/новой версии;
перенести первичку на изменения/checkpoints без изменения расчётов. Выполнять
shadow comparison, а не второй постоянный сбор всех источников.
C. Подключить Dash и Word к одному source revision и on-demand скачиванию с коротким cache; уменьшить публикацию до ссылок,
одной frozen модели и документов. Отключить повторное source acquisition только
после проверки полного source coverage всех потребителей.
D. Перенести provenance/identity/решения на минимальные proofs, включить GC и
проверить фактическую экономию. SQLite/PostgreSQL C08 решается независимо.

Приёмка: точная реконструкция всех сохраняемых недель и свежего состояния;
159 исторических recommendation chains без потери/подмены; исторические схемы
18/19/32/34, формы/значения, отрицания/даты/суммы; insertion/deletion/renumbering,
частичное чтение, retry/crash, неверный parent, повреждённый chunk/delta/checkpoint,
GC с concurrent reader и dangling dependency; readback Dash/Word на одной версии.
Замерять logical/physical bytes, bytes per unchanged refresh/per changed cell,
reconstruction time, latest query latency и восстановление backup. Синтетический
процент экономии не выдаётся за production результат или закрытие скорости UI.

### Проверенные внешние сведения

изменений, но сами не решают предметный provenance и общий source contract

и код проекта не передавались.

### R09: один владелец maintenance lock при выпуске

Раздельный backup job завершает healthy resume исходного API и освобождает
свой guardian. Перезапуск API сам меняет watermarks/parsedAt в SQLite даже
при прежнем fingerprint; прошлую полную копию нельзя назвать текущей.
Release job получает собственный EX fd9 и проверяет исходный runtime из
приватного runtime.json. До остановки API count-only проход существующего
gzip producer (level 1, тот же codec capture) проверяет свободное место для новой сжатой копии и одного
полного scratch restore, учитывая реальные файловые системы. Прежняя копия
отдельно полностью восстанавливается как история, без заявления source-match.

Затем владелец EX останавливает этот же здоровый API и создаёт новый полный
приватный compressed checkpoint без подмены старого. При общем файловом
разделе ограничитель архива резервирует объём полного scratch плюс запас.
Source-match до и после полного scratch restore проверяет новую копию целиком,
включая SQLite, WAL, Word, историю и технические timestamps; исключений нет.
Оценка ёмкости перед остановкой не является снимком: рост или нехватка места
при capture/restore отклоняет выпуск и возвращает исходный API здоровым до
изменения runtime. Нехватка, уже выявленная preflight, не останавливает API.

Rollback point сохраняет код и фактические image digests, прочитанные до
остановки. Приватный receipt связывает release SHA, fresh manifest SHA,
runtime, предыдущий restore и текущий restore/source-match. До замены
контейнера любая ошибка возвращает именно исходный API с проверкой health,
без запуска worker. Поздняя ошибка worker не запускает глобальный restore
или старый API. Передача чужого fd9, остановка внешнего guardian ради gate
и обход lock флагом окружения исключены. Активность и установленный код/unit/policy guard проверяются до остановки.
Внешние дочерние процессы не наследуют maintenance fd9; проверка SIGKILL
показывает освобождение lock и восстановление API существующим guard.
Живые свободное место, guard и операционная приёмка VPS отдельно проверяются; синтетика их не подменяет.

Уточнение 12.10.2026: наблюдаемые 12 113 375 232B в приватном backup-разделе
не допускают полный локальный scratch прежних 22 048 941 998B. Отказ
preflight обязан происходить до API stop. Full-worker-backup уже использует
независимый временный runner restore; текущий release ещё не переиспользует
его. Предлагаемая граница — свежий checkpoint → независимый restore →
digest/session/SHA-bound proof → match-source у исходного EX владельца,
без освобождения lock и без выдачи старой копии за текущую. Это предложение,
не реализованный внешний допуск. Reports-only restore и runtime rollback
не объявляются полным in-place возвратом всех БД; совместимость прежнего
образа после candidate bootstrap/migrations требует отдельного smoke.

job ID, точная область/свежесть/формулы, этап, attempt, владелец/lease и
конечный результат. API быстро возвращает ID и читает готовые проекции;
не выполняет CPU/массовую запись внутри HTTP-потока. Существующий исполнитель
может вызывать канонический TS-расчёт дочерним процессом. SQLite/WAL сохраняется
на первом этапе; один писатель, ограниченные ресурсы и короткие транзакции
не подменяются обещанием параллельных writers.

Присоединение допускается только при покрытии всех требований новой команды;
иначе сохраняется один обоснованный следующий проход. Перезапуск не теряет
принятую команду. Поздний старый владелец не продвигает указатель результата:
проверка полномочия и готовности, pointer и событие выполняются атомарно.
Принятая версия данных, состояние новой попытки и готовность трёх документов
имеют разные состояния и указатели. Долгий render не удерживает право принять
новый пригодный набор данных и имеет свой ресурсный бюджет.

Общий вход фиксирует sources/ranges/values/formulas, фактически наблюдённые
revisions, начало/конец каждого чтения и полноту. Снимок одной области не
дочитывает изменяемые глобальные кэши посередине расчёта. Отдельны идентичности
контента/наблюдения/нормализованного набора/расчёта/артефакта/публикации.
Календарное правило может требовать нового расчёта при прежнем содержимом;
новый шаблон — нового документа. Контракт предметной модели определяет gates,
а не номер Word-renderer. Независимый oracle сохраняется.

Неполная попытка сохраняется для диагностики, но не вытесняет полный принятый
официальный результат той же области. Stale пригоден для чтения с возрастом;
он не доказывает успех новой команды. Node–Python передают ограниченный receipt
с ID/состоянием/ссылками; фактический итог подтверждается из сохранённой операции,
включая исход «уже выполняется» и ошибку канала после состоявшегося коммита.
Произвольные private assurance/исходные данные не печатаются в stdout/API.

История подключается адресно по закреплённым источникам и пригодному индексу.
Выбранное доказательство проверяется строго; посторонний повреждённый manifest
не должен маскировать целевой архив, но его дефект остаётся в integrity-деле.
У проверки формулы появляется затронутая область/следствие по доказанному
графу зависимостей. Пока независимость ошибки не установлена, строгий запрет
не ослабляется; старый архивный #REF не «лечится» переписыванием.

Снятие forced polling допустимо только вместе с проверенным version/catch-up
путём restart/gap/reconnect/retry. JSON/SSE/download используют один договор
авторизации. Guard сохраняет ограниченную причину каждой отказавшей пробы и
различает startup/liveness/readiness/freshness; изменение таймаута не заменяет
устранение блокировки. Обслуживание/backup/retention — отдельные ограниченные
операции под прежним maintenance admission.

Три конечных перехода из отчёта уточняют существующие задачи: устойчивое чтение
и сохраняемая команда; общий вход/расчёт/раздельное принятие данных и документов;
адресная история/каталог/восстановление с измеренной стоимостью. Это не три
уже принятых выпуска и не скрытая замена объявленной десятки. Перед каждым
кодовым участком — точный состав, negative test, совместимость и условие
переключения; состав следующей десятки объявляется до начала реализации.

Текущийb24 выносит только чистый runPipeline/attachUnifiedGrid в один thread.
Массовая SQLite-запись остаётся у API, очередь материализации не durable,
общего захвата TS/Python и всех перечисленных состояний ещё нет. Этот
ограниченный шаг не объявляется исполнением первого целевого перехода.
Приёмка нового контура требует чтения Dash/Word под нагрузкой, двух автономных
циклов, transient source failure, restart API/worker, SSE gap, позднего старого
job, отказа stdout после коммита и постороннего повреждённого архива.
Существующие полные restore/rollback gates действуют, пока не доказан
замещающий checkpoint; стоимость backup сама по себе не разрешает их убрать.

### 20.10.2026 — адаптивное чтение по событиям

Основание: вложение владельца `6252c4e4`, существующие D01 и сохраняемый контур
выше. Статус: целевой договор; разделение запроса формул и принудительного
чтения реализовано в кандидате, диапазонное приобретение ещё не переключено.

Последнее принятое состояние листа — база применения частичных чтений.
Идентификатор книги/листа, версия профиля, расположение строк и покрытие
values/formulas относятся к этой базе. Адрес строки — координата наблюдения,
а не постоянная идентичность закупки. Новый UUID в пользовательских строках
не вводится ради удобства читателя.

Событие добавляет грязные диапазоны в существующее задание книги. Пересекающиеся
строки объединяются; известные зависимости профиля расширяют область до
контрольных итогов/формульных колонок. Новые события во время чтения остаются
следующему проходу. Отдельная очередь и второй планировщик не создаются.
Параметры объединения 2 секунды и максимального ожидания 10 секунд из вложения
остаются гипотезой до замера задержек и квот.

Обычная правка с подтверждённым положением строки допускает перечитывание всей
строки в пределах схемы и её зависимостей. Сортировка, вставка/удаление строк,
неизвестная формула, изменение профиля либо неподтверждённая координата требуют
полного рабочего диапазона листа. Неизвестный лист расширяет цель до книги.
Drive-событие без объясняющего диапазона не даёт права угадать изменённую строку.
Совпавшая версия допускает пропуск только при полном подходящем кэше и отсутствии
обязательной сверки; запрос формул сам по себе не означает полный обход.

Журнал используется для адресации перечитывания, значения «стало» из старой
записи не накладываются на актуальное состояние. Курсор разрешён только после
проверки writer: неизменяемое дописывание, поколение журнала, последовательность
и явная регистрация собственных API-записей. Непрерывность записанных событий
не доказывает охват всех правок. До проверки действующих триггеров существующий
`_ChangeLog` не объявляется полным журналом и не заменяет сверку.

Читатель переиспользует Google API adapter/retry и пакетное чтение диапазонов.
Сокращённые ответы Google с отсутствующими хвостовыми пустотами восстанавливаются
по запрошенной геометрии: очищенная ячейка не сохраняет старое значение.
Значения и формулы обязаны относиться к явно названной области и окну чтения;
версии до/после обнаруживают дрейф, но не дают транзакции между книгами.
Новый целый набор проверяется до короткой транзакции принятия: данные, курсор
и исход задания фиксируются вместе. Ошибка чтения/записи не продвигает курсор.
SSE сообщает изменение принятого содержимого, а не каждую попытку чтения.

Первая приёмка — сравнение частичного и полного чтения устойчивой версии:
вставка диапазона, очистка последней строки, формула/её зависимость, сортировка,
удаление, повтор/запаздывание события, конкурентная правка, смена поколения,
перезапуск и отказ сохранения. Измеряются байты ответа, запросы, задержка и
расхождение результатов. Пока покрытие не доказано, официальный результат
основывается на полном чтении. Независимая сверка остаётся и после переключения;
её период ограничивает время обнаружения незамеченной правки.
Четверговый контроль в 18:00 — отдельное полное чтение с реальным окном захвата,
не восстановление четверга из пятничного состояния.
