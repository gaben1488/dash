# ADR-010 — канонический недельный архив входов отчёта

Статус: кандидат; требует обычного CI и производственной read-only приёмки.

## Проблема

Серверный `DataSnapshot` и его `weeklyTableContext` сохраняют полезную историю
оперативной страницы, но это не полный вход Python-генератора. В частности,
оперативная модель мониторинга не заменяет зарегистрированные источники
`Рабочий реестр процедур` и `Процедуры в работе`, закрытый накопительный реестр
рекомендаций, пакет оригиналов истории и состояние постоянных идентичностей.

Поэтому старый снимок страницы нельзя объявлять воспроизводимым отчётом и нельзя
дополнять его сегодняшними процедурами или рекомендациями. Замена идентификатора
одной книги мониторинга на более новую также не решает эту границу: это смешало бы
два разных предметных контракта.

## Решение

Единственным каноническим недельным входом отчёта считается полный
`snapshot_bundle`, уже построенный существующим report-engine из его собственного
закрытого `registry`, накопительного ledger, точных Google-источников, формул и
доступного пакета исторических рекомендаций. Вместе с ним сохраняется независимый
backup `identity.sqlite`.

`report-worker` после каждой штатной попытки проверяет дату самого захвата.
Если это четверг по календарю `Asia/Kamchatka`, первый полный комплект дня
атомарно переносится в `data/reports/archives/WEEKLY-YYYY-MM-DD/`. Более поздний
комплект того же четверга не заменяет уже запечатанный.

Сохранение недели не равно допуску отчёта. Комплект допускается архивировать и из
`NOT_ISSUED`-attempt, если сам вход и identity backup полны и проходят проверку
целостности. При последующем запросе исторического Word он заново проходит обычный
расчёт, независимые проверки и release gates. Блокированный отчёт не становится
успешным только потому, что его первичка сохранена.

Архиватор не обращается к Google повторно и не читает текущий ledger. Он копирует
ровно уже завершённый атомарный захват attempt либо соответствующий неизменяемый
published release, сверяет источник до и после копирования, проверяет сохранённый
bundle через существующий `load_frozen_input`, синхронизирует файлы и только затем
делает атомарный rename.

При старте worker сканирует сохранённые `attempts/*/status.json` и может таким же
образом восстановить недельные архивы для ранее удержанных полных четверговых
attempts. Отсутствующая или неполная неделя не восстанавливается догадкой, ближайшей
датой или текущими данными.

## Граница с оперативной страницей

`weeklyTableContext` остаётся доказательством того, что оперативная страница
действительно сняла свой полный набор master/monitoring-данных в четверг. Он полезен
для истории интерфейса и независимой сверки, но не является входом Word.

Канонический Word-архив намеренно использует тот же Python source contract, что и
живой выпуск. Различия между оперативным TypeScript-путём и Python-моделью поэтому
не маскируются объединением двух несовместимых снимков.

## Сохранность и идемпотентность

На один календарный четверг создаётся один каталог `WEEKLY-YYYY-MM-DD`.
Повторный запуск только проверяет уже существующий архив и возвращает его
`snapshot_id`. Перезапись не разрешена.

Архив содержит только необходимое для воспроизведения входа:
`snapshot_bundle/`, `identity.sqlite` и закрытый `import.json` с происхождением.
Чистовые Word-файлы не копируются как источник истины: они должны строиться заново
из замороженных данных.

Повреждённый published release считается ошибкой. Полузаписанный attempt считается
ещё не готовым и может быть повторён следующим циклом. Ошибка архивирования не
останавливает живой polling worker; она записывается отдельным безопасным статусом.

## Что это не доказывает

Этот механизм не восстанавливает недели, для которых полный attempt никогда не
сохранялся. Для более старых периодов остаётся отдельный проверяемый импорт
оригинальных XLSX/ZIP по ADR-009.

Механизм также не доказывает равенство расчётов оперативной страницы и Python.
Устранение дублирующей предметной логики остаётся отдельной задачей.

## Приёмка

Тесты обязаны доказывать, что полный четверговый attempt после удаления временного
attempt и живой identity-базы всё равно воспроизводится через `run-archive`; оба
точных листа процедур и восемь master-источников присутствуют; более поздний attempt
не заменяет первый архив дня; неполный и непятничный/нечетверговый вход не
продвигается; повторное восстановление идемпотентно.

Производственная приёмка по-прежнему требует read-only rehearsal на реальном томе.
Наличие этого кода не является утверждением, что VPS уже прошёл репетицию.

## 16.10.2026 — ограниченный recovery journal и защищённые корни

Факты: каталог99 выпусков содержит218MB receipts; второй legacy plan получил
OOM. Отдельный synthetic journal всего4 записей вырос до16.8MB; старый reader
разбирает этот файл целиком ради одного `readers_ready`. Это отдельная
воспроизведённая проблема, не установленная причина production OOM. Принятая копия покрывает
92 из95 предварительных кандидатов, ещё3 должны остаться полными. Nullable
identity signatures восстановлены отдельной CAS-транзакцией38891326813;
независимое native чтение38891473586 подтвердило0 пропусков для95 snapshots.

Новый writer хранит большой recovery payload по записям во временном SQLite
журнале внутри прежнего `.retirement`, а небольшой `journal.json` содержит
контрольный хеш, число записей и прежние phase/reader flags. Это внутренний
формат восстановления, не новая база бизнес-сущностей. Старый v1 journal
остаётся читаемым на границе recovery; новые операции используют один текущий
формат. Итерация повторяема и ограничена одной записью, CAS и проверка всех
источников предшествуют мутации. Сбой до публикации journal не разрешает
двигать originals; после неё восстанавливается только доказанный transaction.

Неизменяемые оставляемые файлы внутри published release допускается связать
hardlink при staging на том же файловом разделе. Primary SQLite, mutable
состояние и незавершённые attempts не участвуют. Хеши и адреса документов
сохраняются, а rollback/finalize не пишут в содержимое общих inode.

План обслуживания дополнительно защищает корни, которых нет в проверенной
backup. Это условие доказанной восстанавливаемости, не новый срок хранения:
неподкреплённые3 корня не сокращаются ради освобождения места. Защищённый
набор входит в итоговые keep/targets и revision; gate под locks пересчитывает
тот же набор. Приёмка требует legacy-reader compatibility, late-conflict,
реальных process-death/rollback/finalize и замера памяти/места до применения.

Дорогой план вычисляется один раз внутри native locks. Backup-проверка получает
этот же объект через внутренний callback; внешнего входа с готовым планом нет.
Read-only preview может получить итоговую revision от того же preflight;
actual apply всегда сравнивает явную ожидаемую revision до изменения данных.

### Квалификация инструмента и проверка установленного приложения

CI38894166136 дляb6dc вновь получил live43 READ_UNAVAILABLE/METRIC_READ
TimeoutError. Maintenance tool ещё не установлен; общий failed CI не становится
успешным. Допуск public maintenance source использует тот же канонический
`.github/ci/source_ci_gate.py`, что controlled release: три обязательных exact
PR-SHA задания исходников/engine/native-image должны завершиться SUCCESS.
Аутентифицированный job сохраняет исходный run вместе с фактически полученными
jobs этого run, без подмены conclusion. Native CLI проверяет тот же критерий,
source helper включён в полный transport hash; root executor сверяет его с
уже pinned каноническим helper. Полный green CI остаётся допустимым прежним
свидетельством. Failed source/не тот SHA/не тот job/run не допускаются.

Доступность actual43, exact source hashes, reader behavior, capacity, backup
coverage/restore, locked plan, recovery и независимый finalize остаются
отдельными обязательными gates. Source qualification не является приёмкой UI,
установленного приложения, новой публикации или разрешением на очистку.
