# Word, RecommendationLedger и единый проверенный выпуск

**Статус:** proposed distillation. Операционный первоисточник: `docs/report-engine-operating-contract.ru.md`; не заменяет оригинальный контракт.

## Один выпуск — один замороженный набор доказательств

`capture primary + private ledger → validate schema/formulas/identity → independent check → ReportModel → main.docx + appendix.docx + dashboard projection → publish atomically → readback`.

Сохранить: `release_id`, `snapshot_id`, `rules_version`, source signatures, полную историю рекомендаций, диагностический протокол, checksum каждого документа и asOf `Asia/Kamchatka`. Нельзя показывать Word и экранные KPI из разных снимков без явной пометки.

## История рекомендаций

- `RecommendationLedger` — накопительная официальная история рекомендаций УЭР, а не генератор желаемого результата. Новая редакция не переписывает опубликованный старый выпуск.
- `принята рекомендация`, `связанная закупка определена`, `мероприятие осуществлено`, `контракт заключён`, `оплата произведена` — независимые события. Косвенное совпадение текстов или номера не доказывает исполнение.
- Конкурентная правка ledger требует версии/хеша и 409 вместо потери данных; атомарное сохранение, backup и readback; приватный JSON не должен появляться в публичном Git.

## Узкое исключение для обезличенных регрессионных фикстур

Из прежнего корневого `CLAUDE.md` сохраняется явно утверждённое владельцем **29.07.2026** исключение: в Git допустимы **только** проверенные выжимки плановых закупочных строк вида `packages/core/src/report/__fixtures__/week-*.json` для регресса «расчёт против ручного отчёта», без ключей, персональных данных, служебных учётных данных и приватной истории. Перед добавлением новой фикстуры проверить её источник, минимизацию, состав полей, отсутствие секретов и смысловую сопоставимость со снимком. Это не разрешение коммитить исходные Word, полный реестр, приватный RecommendationLedger, JSON сервисного аккаунта, персональные данные или другие отчёты. При сомнении — не публиковать.

## Гейт отчётности

1. Проверить frozen capture всех нужных источников (включая 8 masters и действующий ledger), версии схем и дату.
2. Проверить правильность сумм, год/квартал, все объекты со статусом `UNKNOWN`, отсутствие непроверенных обещаний в деловом тексте.
3. Сформировать основной DOCX и дополнение **из одной** модели; проверить текст, числовые инварианты, OOXML-структуру, checksum.
4. Проверить успешную публикацию нового комплекта как атомарной пары. При провале оставить предыдущий принятый комплект неизменным.
5. На целевом VPS — два самостоятельных успешных рабочих цикла worker, restart/readback, явное заключение о доступности и rollback. Один CI или тестовые документы не подтверждают production.
6. На странице «Отчёт» — тот же release_id и те же числа; оперативный журнал изменений может иметь иной asOf, это подписано.

**Внимание:** ADR-0010/0011 описывают кандидаты и этапы PR; наличие такого текста в main не подтверждает выпуск в production. ADR-0012 также `proposed` на 22.10 и не должен появляться в STATUS как внедрённый без новой проверки.
