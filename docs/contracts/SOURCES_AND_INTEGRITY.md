# Контракт первичных данных и проверяемой целостности

**Статус:** редакционная кандидатура. **Версия основания:** Git `9d0ceda` + выборочная сверка кода `main@c4b792a` 22.10.2026. Производственные таблицы и Apps Script в этой ревизии не перечитаны.

## Источники и их роль

- Восемь master-книг ГРБС являются первичными носителями собственных плановых/фактических строк. Сводная книга содержит официальные листы и проекции; реестр процедур — другую предметную схему. Приватный RecommendationLedger — история рекомендаций, не строки закупок.
- Идентификаторы рабочих книг разрешай через реальную конфигурацию `packages/server/src/config.ts` и `packages/shared/src/department-registry.ts` с подтверждением MIME, sheetId, header fingerprint, даты и пределов. По похожему имени не выбирай архив.
- При несовпадении зеркала и оригинала показывай **две величины и расхождение с provenance**, пока не установлена причина. `#REF!` в зеркале — ошибка источника, не содержательная строка или пустой реестр.
- Данные разных книг считываются не атомарно по умолчанию. Для выпуска используй frozen capture, source signatures и сравнимые времена; не называй разновременный срез согласованным.

## Полная подтверждённая база → webhook → вычисляемый diff (требуемое поведение)

**Статус внедрения:** требование к будущей реализации, **не доказано для `main`/VPS**. Черновик PR #150 от 22.10.2026 обсуждал этот механизм, но **закрыт без merge**. Не считать текст доказательством работающего инкрементального обновления.

1. Начальный baseline принимается только из **полного** согласованного набора обязательных источников: все 8 актуальных master-книг, необходимые официальные листы/реестр процедур, контрольные диапазоны и применимые источники отчёта. Зафиксировать source IDs, schema/header fingerprints, `asOf`, `rules_version`, список диапазонов, покрытие (`sourceCoverage=100%` по объявленному составу) и проверяемый receipt/подпись. Само наличие файла или старого cache — не доказательство полноты. Состав набора зависит от сценария: просмотр одной строки не требует захвата всей отчётной модели.
2. Google Drive `changes.watch`/webhook обычно сообщает **какой файл** изменён, но не предоставляет надёжный изменённый A1-диапазон. При известном изменённом `fileId` перечитай только **необходимую книгу/диапазоны**, сравни с проверенной базой по ключам и версиям, вычисли содержательный diff. Не обещай «получать только изменённые ячейки», пока отдельный достоверный журнал изменений с непрерывным курсором не подтверждён тестом.
3. Готовь candidate следующего **полного** согласованного состояния из `last_good_baseline + verified_changed_book`. До атомарной замены проверь схему, все диапазоны изменившейся книги, cross-source зависимости, completeness/receipt и потребителей. В одном commit/publish заменить baseline, watermark/курсор, read-model и связанный выпуск. Новое состояние обязано сохранять 100% необходимого покрытия; **partial delta не становится новым baseline**.
4. Если любой источник/диапазон не читается, есть mismatch схемы, несогласованная ревизия или отказ записи, **не обновлять** подтверждённый baseline, watermark, опубликованный release и last-good model; событие оставить для повтора. Последнюю неудачную попытку показывать отдельно от `last_verified_at` и причины сбоя. Предыдущее состояние может обслуживать чтение только с оригинальным `asOf` и явным `STALE`, не выдавая старый успех за свежий.
5. Повторный webhook, конкурентные события и перезапуск должны быть идемпотентны. Проверяй, что обработанный cursor соответствует зафиксированному complete baseline, а crash между вычислением diff и commit не «подтверждает» событие. Не ставь новую полную Google-выгрузку после каждого рестарта по умолчанию; восстанавливай доказанное состояние из durable storage и планируй адресный retry.
6. Контрольные **отрицательные** сценарии: 7 из 8 книг; недоступен `СВОД`; изменилась схема A:AH; Google сообщил `fileId` без диапазона; зависимые формулы ошибочны; webhook пришёл дважды; отказ SQLite на commit; restart между delivery и acknowledge; старый snapshot частичный. В каждом случае предыдущий подтверждённый baseline остаётся byte/receipt-identical, ошибка видна, отсутствуют новые ложные `PASS`, `0` и release.

Этот контракт не разрешает изменять таблицы, добавлять новые служебные листы, отключать опрос или объявлять полную production-приёмку без точного HEAD, реального источника и rollback.

## Каноническая схема master-строки (34 поля)

| Графы | Смысл / опасность |
|---|---|
| A–C | номер позиции (человеческий, не UID), ГРБС, подведомственная организация |
| D–G | программа, подпрограмма, тип деятельности, предмет; D не подменять предметом |
| H–K | плановое финансирование ФБ/КБ/МБ/итог (не автоматически НМЦК) |
| L–M | способ закупки, основание/комментарий к ЕП |
| N–P | ручная плановая дата; производные квартал/год — формулы, отсутствие формулы не = отсутствие финансирования |
| Q–T | дата факта и производные признаки/отклонение; наличие Q не = доказательство оплаты/исполнения |
| U | комментарий/причина отклонения, не превращать свободный текст в юридический факт без подтверждения |
| V–Y | фактические суммы по бюджетам и итог, не подменять ценой торгов |
| Z–AC | арифметические составляющие и итог экономии; их учёт дополнительно зависит от AD |
| AD | флаг учёта утверждённой экономии |
| AE–AH | необходимость и три раздельных комментария, включая ГРБС, УЭР, УФБП; не терять AG/AH |

**Разрешение исторического конфликта:** `docs/METRICS_CONTRACT.md` ранее ошибочно описывает `D` как description и `E` как программу. `packages/shared/src/column-map.ts` текущего `main` называет `D=PROGRAM_NAME`, `E=SUBPROGRAM`, `F=TYPE`, `G=SUBJECT` и AF/AG/AH — комментариями. Исправление старых описаний оформлять отдельным PR и тестом по заголовкам; не «чинить» живые книги под старую документацию.

## Правила работы с Sheets

- До записи — снимок фактических значений, формул, валидаций, note, прав доступа, именованных диапазонов и revision/barrier. Уважай чужую конкурентную правку (409/conflict, не blind overwrite).
- Не смешивать формулы с ручными вводами: селектор `ID→имя` не должен содержаться в ячейке, которую оператор перезапишет выбором. Ровно эта ошибка обнаружена в пилоте справочника УО/процедур 10.10.
- Каждая запись — минимально затронутый диапазон, адресный readback до/после, проверка соседних ячеек/границ. Пользовательские данные и историю не удалять при консолидации.
- Отсутствие одного источника, ошибка formula, недоступная подписка webhook или сбой сохранения — видимый статус, а не `success:true` или «0 строк».

## Специальный риск 11.10

Задокументировано физическое удаление 24 переходных листов `Settings`, `Контроль`, `_Справочник` в восьми master-книгах после замены проверок на `_Настройки`. В документированном срезе проверено 34 119/34 119 проверок ввода C:E, 74 представления и отсутствие битых формул в охваченных областях. **Но** bound Apps Script, внешние потребители, установленные триггеры и доставка `_ChangeLog` не получили независимого полного подтверждения. Не восстанавливать старые листы ради старого кода; сначала карта зависимостей и согласованная перенастройка скриптов. Старый `scripts/etalon-sync/canon.cjs` содержит ссылку на `Settings!$B$6`, которую нельзя исполнять без исправления.

## Порог приёмки изменения источника

1. Конкретный source identity + `asOf` + schema/version + контрольная сумма и заголовки.
2. Независимый readback первички и зависимой проекции, метрик, агрегации, формул, истории.
3. Негативные сценарии: 1/8 masters отсутствует; `#REF!`; missing O/P при корректной N; новое имя учреждения; две похожие строки; сломанный Apps Script; конкурентная запись.
4. Fail-closed при неизвестном поле/неполной выдаче; backup/rollback; никаких массовых live-правок из документа.
