# Генератор проверяемых отчётов

Продолжение существующей v1.4, перенесённое в общий репозиторий. Считает
показатели по сохранённым первичным данным, формирует основной DOCX,
дополнение и JSON-проекцию дашборда. Языковая модель при выпуске не нужна.

## Запуск

Python 3.11+; для хранения публикаций нужен Linux и локальный постоянный том.

```sh
python -m pip install -e 'packages/report-engine[test]'
python -m pytest packages/report-engine/tests -q
python -m ruff check packages/report-engine
proc-report run-google --registry /private/registry.json --ledger /private/ledger.json --state /private/report-state
```

Реестр источников и нормализованный реестр рекомендаций — закрытые входы
из проверенного пакета передачи проекта. Реальные данные, SQLite и документы
не добавляются в Git. Исторический `recommendation_ledger_v3.json` имеет другой
формат; подходящий нормализованный файл — `RecommendationLedger_25.09.2026.json`.

Авторизация использует `GOOGLE_SERVICE_ACCOUNT_EMAIL` и `GOOGLE_PRIVATE_KEY`
либо `GOOGLE_APPLICATION_CREDENTIALS`. Токены обновляются автоматически;
`GOOGLE_ACCESS_TOKEN` остаётся вариантом для краткого однократного запуска.
Аккаунту нужен доступ на чтение зарегистрированных книг и метаданных Drive.
Ключ передаётся средой выполнения, не аргументом командной строки.

## Диагностика исторических связей перед внедрением (кандидат rc23)

Новый контракт `verified-original-and-current-plan-v13` используется **только для
новых сборок**. Датированная ручная привязка UID может подтвердить текущую связь,
только если независимо проверено происхождение исходного DOCX. Если
автоматическая и датированная связи указывают на разные UID, обе считаются
недоказанными; исполнение рекомендации не утверждается. Старые контракты
v1–v12 не изменяются и остаются воспроизводимыми при проверке своих входов.

Для безопасной диагностики на существующей публикации:

```sh
python -m procurement_engine.rehearsal --state /private/report-state --coverage-summary
```

Этот режим читает проверенную публикацию и полную историю через временную
копию; выводит только агрегированные причины и сравнение статусов рекомендаций
на одном сохранённом снимке. Номера строк, UID, предметы закупок и тексты
источников не выводятся. Отдельно указывается
`weekly_replay=NOT_CHECKED`: этот диагностический режим **не является**
полной приёмкой архива.

Полный выпускной контроль выполняется прежней командой
`python -m procurement_engine.rehearsal --state /private/report-state --coverage`.
Она по-прежнему отклоняет неисправные исторические входы. Для экономии
повторной генерации кандидата в read-only CI этот же строгий контроль архива
можно выполнить отдельно:

```sh
python -m procurement_engine.rehearsal --state /private/report-state --weekly-only
```

`--weekly-only` проверяет именно замороженный недельный архив, не создаёт новый
официальный выпуск и возвращает ненулевой код при его ошибках. Поэтому
успех `--coverage-summary` не отменяет отказ `--weekly-only`.
Известный архивный дубль процедуры от 08.10.2026 нельзя исправлять
данными из более позднего живого реестра.

Диагностика не чинит старые данные, не публикует отчёты и не изменяет production SQLite.

## Результат попытки

`status.json` сообщает исход и время попытки. `attempts/<id>/capture.json`
сохраняет прочитанные данные; `attempts/<id>/bundle/` — диагностический комплект.
Код завершения 2 означает, что новый выпуск не опубликован; предыдущая
публикация не меняется. Код 0 означает успешную публикацию. Уже идущий запуск возвращает
ALREADY_RUNNING и код 2; существующий статус при этом не меняется.

`PublicationStore.latest()` возвращает последний опубликованный комплект
после проверки его целостности. Реестр публикаций в SQLite становится видимым
только после записи всех файлов. Повтор, параллельный запуск и отказ перед
фиксацией покрыты тестами. Обязательны резервные копии состояния целиком.

## Расписание и доступ к выпуску

Образ сервера содержит Python-движок. После размещения закрытых `registry.json`
и `ledger.json` в `data/reports/inputs` постоянного тома и положительной приёмки:

```sh
cd deploy
docker compose --env-file .env.production --profile reports up -d --build
docker compose --env-file .env.production exec -T server /opt/report-env/bin/proc-report run-google --registry data/reports/inputs/registry.json --ledger data/reports/inputs/ledger.json --state data/reports
```

`report-worker` выполняет попытку при старте и затем через `REPORT_POLL_SECONDS`
(по умолчанию 900 секунд) после завершения предыдущей. Для сохранения профиля
при последующих развёртываниях задаётся `COMPOSE_PROFILES=reports` в `.env.production`.
Сервис использует существующую авторизацию сервера. `deploy/enable-reports.sh`
однократно подключает закрытые входы из точно названного файла
`aemr-report-runtime-inputs-v1.json` в Google Drive, выполняет полный запуск и
включает worker только после успеха. Файл должен быть доступен сервисному аккаунту
на чтение; существующие входы не перезаписываются. Скрипт включён в шаг deploy CI.
Журналы bootstrap и первого выпуска остаются в закрытом томе сервера. Само наличие
этого скрипта не подтверждает успешного производственного развёртывания.

За существующим контуром авторизации доступны:

- `GET /api/report-releases` — последняя попытка и последний проверенный выпуск.
- `GET /api/report-releases/<release_id>/dashboard` — сохранённая проекция.
- `GET /api/report-releases/<release_id>/main.docx` — основной документ.
- `GET /api/report-releases/<release_id>/supplement.docx` — дополнение.

Все части читаются по одному `release_id`. При повреждении комплекта API отвечает
503; незарегистрированный выпуск — 404. Исходные матрицы через этот API не выдаются.
`REPORT_STATE_DIR` меняет путь состояния API; при изменении нужно согласовать
путь worker. `REPORT_ENGINE_BIN` нужен для локального запуска вне образа.

Страница «Отчёт» показывает сохранённый выпуск, дату чтения источников и дату
публикации. Отказ следующей попытки не меняет дату доступных документов.
Оперативные выгрузки ниже панели явно названы черновиками; проверенные документы
загружаются с сервера с той же авторизацией, что и данные.

## Зависимости формул

В снимок сохраняются формулы всей сетки и метаданные именованных диапазонов.
`formula_dependencies` перечисляет зависимости и конкретные пробелы: непрочитанный
лист, неполную ширину, изменение контекста или непроверенную функцию. Локальные
LET/LAMBDA проверяются в своей области действия. Успешная проверка снимает только
блокировку зависимых импортов; она не подтверждает остальные предметные разделы.
Поддерживающие справочники должны быть явно зарегистрированы и прочитаны вместе
с основными листами. Старые снимки без формул остаются диагностическими.

## Предметный допуск и граница готовности

Выпуск отражает подтверждённое состояние первичных реестров. Неизвестная связь
исторической рекомендации остаётся явным пробелом; она не становится утверждением
об исполнении. Основания сопоставления сохраняются в отдельном diagnostic_protocol.json;
чистовые документы сохраняют исторические ответы и решения без технических статусов. Ошибки
обязательных данных, незакрытые зависимости, потеря раздела и расхождение пересчёта
блокируют выпуск. PublicationStore повторно проверяет предметный контракт и
пересчитывает показатели по сохранённым первичным матрицам перед публикацией.

В rc7 независимый пересчёт охватывает также каждый ГРБС, все кварталы,
проценты и календарный факт. Отдельно проверяются будущий план, активные и закрытые
процедуры, баланс долей совместной процедуры, таблицы рекомендаций и показатели
дополнения. Текстовые статусы и основания рекомендаций воспроизводятся из
сохранённых матриц и накопительного реестра. Эти проверки подтверждают реализованные предметные показатели. В rc9 они
не охватывали каждое текстовое утверждение: проверка содержимого усилена в кандидате rc10 (см. ниже).

В rc8 производственный путь автоматически читает единственный приватный
`aemr-report-recommendation-history-v1.json`, доступный сервисной учётной записи.
Пакет содержит оригиналы DOCX и координаты точных исторических текстов. После
проверки байтов, даты, ГРБС и текстов он дополняет копию реестра, сохраняя прежние
ответы и решения. Оригиналы и ревизия пакета входят в неизменяемый снимок;
ревизия повторно проверяется перед публикацией.

Текущая связь подтверждается только при единственном совпадении полного предмета,
его собственной суммы, явно указанного номера, управления и периода, с доказанным
постоянным UID. Миграция предыдущего снимка восстанавливается автоматически из
проверенных сохранённых матриц. Проверяющий публикацию независимо читает backup
SQLite и отвергает идентификаторы, выдуманные в модели. Происхождение, текущая
связь и исполнение — отдельные результаты: найденная закупка не доказывает
исполнение рекомендации. Групповые рекомендации и записи без достаточного
подтверждения остаются с конкретными основаниями в протоколе. Это не заявление
о завершении проверки исполнения всех накопительных рекомендаций.

Сравнение использует только проверенный опубликованный выпуск за более раннюю
дату. При смене квартала сравнивается год; при смене правил или года причина
несопоставимости указана явно. Изменение суммы не объявляется событием закупки.

Панель опубликованного выпуска и Word используют один идентификатор выпуска.
Оперативная страница продолжает иметь отдельный TypeScript-путь расчёта; полная
предметная эквивалентность двух путей на одинаковом срезе не заявляется. Синтетический положительный
путь выполняет реальный capture/build/render/publish/read без подмены модели.
Производственное расписание требует сквозной проверки с сервисным аккаунтом и
закрытыми входами. Локальные проверки не означают включение его в целевой среде.

## Конфигурируемый контракт rc9

`grbs_order` в закрытом реестре задаёт состав и порядок управлений; без него
сохраняется прежний состав из восьми. Пропавший источник не сокращает состав
автоматически. `header_rows` используется во всех стадиях, включая независимую
проверку и восстановление истории. Дробные периоды и невозможные даты отклоняются.

Контракт связей v2 подтверждает каждую позицию группы отдельно, только по полному
предмету, собственной сумме и постоянной идентичности. Это не доказательство
исполнения объединения. Сохранённые выпуски v1 повторно проверяются по старым
правилам. Новый выпуск имеет собственную версию правил и не переименовывает старый.

Работа сотрудника, расчётные определения, границы эвристики, эксплуатация,
резервирование и миграции описаны в [рабочем контракте](../../docs/report-engine-operating-contract.ru.md).


## Кандидат rc10: пояснения и содержание Word

Код кандидата исправляет потерю M/AE/AG/AH, доставку `business_finding`, неполный
контроль карты происхождения, подмену Word при корректном хеше и вставки в саму
текстовую модель. Пояснения сохраняются с происхождением, но не заменяют факт,
плановый год или доказательство исполнения. Технические инструкции остаются
в диагностике, а не в управленческом тексте. Финансовая доля названа денежным
фактом к плановой сумме: наличие суммы без даты не доказывает заключение договора.

Добавлены контракт упорядоченных абзацев/ячеек и проверка реального OOXML.
Новый выпуск обязан иметь полный ожидаемый каталог следов происхождения.
Перед публикацией проверяется непрерывность всех строк шапки относительно
последнего целостного выпуска. Старый формат rc9 продолжает читаться.

Архитектурное решение, границы и требуемая производственная приёмка:
[ADR-007](../../docs/decisions/0007-source-context-and-document-content-contract.md).
Кандидат не следует считать внедрённым до проверки конкретного commit в штатном
CI и нового живого выпуска. Локальные тесты не подтверждают абсолютную
безошибочность, всю предметную полноту или работоспособность произвольной таблицы.


## Канонический недельный архив входов

`report-worker` сохраняет первый полный канонический захват каждого четверга
(календарь `Asia/Kamchatka`) в `data/reports/archives/WEEKLY-YYYY-MM-DD`.
Используется уже построенный report-engine attempt: все зарегистрированные master-
и procedure-источники, формулы, source contract, накопительный ledger, доступные
доказательства истории рекомендаций и backup `identity.sqlite`. Повторного чтения
Google ради архива нет.

Архив первички и публикация отчёта — разные состояния. Даже `NOT_ISSUED`-attempt
может сохранить честный недельный вход, но исторический Word позднее всё равно
пересчитывается и проходит все обычные release gates. Более поздний attempt того
же четверга не перезаписывает первый замороженный комплект.

При старте worker также проверяет удержанные старые четверговые attempts и
запечатывает только полные. Пропавшая неделя не подменяется ближайшей датой или
сегодняшними данными. Оперативный `weeklyTableContext` TypeScript-страницы остаётся
отдельным контрольным снимком интерфейса и не считается заменой Python source
contract. Подробности: [ADR-010](../../docs/decisions/0010-canonical-weekly-report-archive.md).

## Уточнение границы продукта, 06.10.2026 (rc15)

Старые XLSX/ZIP и ревизии Drive используются только для восстановления методологии
и её автономных тестов (`tests/archive_tools`). Их импорт не входит в CLI, API,
worker или производственные гейты. Выбор архивной даты читает исключительно
сохранённый полный снимок входов генератора; отсутствие снимка не вызывает
обращение к старым файлам либо текущим источникам.

Накопительный реестр рекомендаций и доказательства происхождения рекомендаций
сохраняются: это отдельный предметный вход, не источник KPI из старого Word.
Проверка байтов ранее запечатанных XLSX-выпусков оставлена только для совместимости
чтения и автономного воспроизведения уже сохранённых комплектов.

Восстановление идентичности читает также запечатанные недельные снимки. Повреждённые
временные попытки пропускаются с числом пропусков и невосстановленных снимков
в `identity_recovery` статуса попытки. Повреждённый опубликованный или запечатанный
комплект остаётся блокирующей ошибкой. Код SQLite проходит конечный словарь Python
SQLite, а не только проверку написания.

Готовность полного продукта подтверждается живым выпуском, двумя нативными DOCX,
повтором по недельному снимку и отсутствием нерешённых задач движка. Успешные
программные тесты и самостоятельный пересчёт не подменяют эти проверки.
