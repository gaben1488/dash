# DASH / AEMR — обязательные правила для AI-разработки

> **DRAFT 2026-10-22.** Предложение новой корневой инструкции; не внедрена в рабочий Git. Для любой задачи читать нужный предметный контракт, но не требовать чтения всего архива.

## Продукт и граница знания

- Dash — система доказуемых данных и подготовки управленческого отчёта о закупках восьми ГРБС. Критерии пользы: больше обоснованных конкурентных закупок, меньше ручного свода, лучшая дисциплина и единая инфраструктура (`PRODUCT.md`).
- Код, документ, CI, merge, VPS и приёмка владельцем — **разные состояния**. Никогда не объявляй рабочий результат готовым по тексту спецификации или зелёному CI.
- Утверждение о сегодняшнем статусе подтверждай точным commit/snapshot, временем, источником и readback; если данных нет — `UNKNOWN`, не ноль и не «готово».
- Старые спеки и аудиты не становятся действующими инструкциями только потому, что они в Markdown. При конфликте проверяй принятое решение, код и актуальное доказательство.

## Источники, деньги, сущности

- Первичные строки ГРБС, СВОД, книга процедур и RecommendationLedger имеют отдельные контракты. Не смешивай разные периоды, зеркала и книги; не исправляй бизнес-строки ради красивой аналитики.
- Основной master-контракт — **A:AH / 34 колонки**. `D` = программа, `E` = подпрограмма, `F` = вид деятельности, `G` = предмет, `Q` = дата факта, `Z:AB` = составляющие экономии, `AD` = отметка её учёта. Сверяй с `packages/shared/src/column-map.ts` и заголовками живой книги до записи.
- `economy_total` — только суммы `Z+AA+AB` строк с доказанной датой факта и `AD="да"`. План−факт — **не** экономия; `amount_deviation = fact_total − plan_total`. Не путай НМЦК, цену победителя, факт и бюджетную экономию.
- № строки, составной номер вроде `173/1`, внутренний item UID, ИКЗ, код процедуры и UUID учреждения — разные идентификаторы. Не связывай сущности по похожему тексту или одному номеру автоматически.
- Ноль, пусто, формула без результата, недоступный источник, неприменимый период и отсутствие пары для сравнения имеют разные статусы. Ошибка чтения не равна пустому листу.
- Не добавляй ручные UUID, колонки, вкладки или новые «технические дома» в рабочие Google Sheets без отдельного разрешения и миграционного контракта. Сохраняй формулы и историю, проверяй адресные readback.

## Изменения и проверка

- В совместной работе с Claude/Codex не коммить в `main` напрямую: отдельная ветка/отдельный worktree/один PR на независимую задачу; никогда не переносить чужой stash/WIP между worktree. Правило исходит из `docs/AGENTS.md` (исходник 14.06) и применяется без привязки к Windows-путям.
- Для дефекта сначала определи **класс** и все его носители. Проследи пользовательский путь, подготовь отрицательный тест и примени наименьшее изменение, исправляющее причину. Не повторяй поверхностные точечные заплатки или масштабную перепись без доказанного выигрыша.
- До рефакторинга UI зафиксируй сохранённые функции и состояния, включая навигацию, оригинальные макеты, темы, фильтры и комментарии. Не заменяй их произвольным типовым шаблоном; «Пульс» не менять без согласованной области.
- Метрики, фильтры, графики и переходы должны использовать один паспорт отбора и сопоставимый источник/момент чтения. При клике переходить к тому же набору строк, а не к приблизительной выборке.
- Перед распространением изменений источников проверь схему, формулы, валидацию, триггеры, Apps Script, потребителей и негативные сценарии. В особенности после удаления технических листов 11.10 не восстанавливай их без анализа зависимостей.
- Базовые проверки по релевантному изменению: `pnpm lint`, `pnpm typecheck`, `pnpm -r test`, `pnpm build`, при зависимости/безопасности `pnpm audit --audit-level moderate`; Python-генератор проверяется своим test/runner. Объясняй неприменимые проверки, не запускай дорогостоящий полный цикл ради опечатки.
- Для изменений выпуска требуются отдельные доказательства frozen input → ReportModel → два Word → публикация и чтение, два успешных реальных цикла worker и сохранение предыдущего комплекта при отказе.
- Никогда не коммить ключи, приватные данные, SQLite, оригинальные отчёты или приватный ledger. Не отключай fail-closed. Проверяй `deploy_scope` перед merge: новый путь в main может запустить runtime deploy.

## Маршрутизатор нужного контекста

- Источник/формулы/Google Sheets → `docs/contracts/SOURCES_AND_INTEGRITY.md`.
- Арифметика/классификация/юридические пороги → `docs/contracts/METRICS_AND_MONEY.md`.
- Идентификаторы, организации, история → `docs/contracts/IDENTITY_AND_HISTORY.md`.
- Word, RecommendationLedger, выпуск → `docs/contracts/REPORT_RELEASE.md`.
- Фильтры, карточки, навигация, макеты → `docs/contracts/UI_AND_FILTERS.md`.
- Правка сложного поведения → `docs/engineering/CHANGE_PROTOCOL.md`; повторные ошибки → `docs/engineering/FAILURE_PATTERNS.md`.
- VPS, Docker, восстановление → существующий `docs/RUNBOOK.md` и `docs/operations/RELEASE_GATES.md`.

**Финальный ответ:** что изменено; где; какой тест/срез это доказывает; что НЕ принято; какой безопасный следующий шаг. Не принуждай владельца повторять уже известные ограничения.
